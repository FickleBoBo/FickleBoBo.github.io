# /review 청크 분석 에이전트 지침

`/review` Phase 2에서 각 청크 담당 Sonnet 에이전트가 **그대로 따르는 지침**이다.
메인은 이 파일을 프롬프트에 복사하지 않고 **경로만 넘긴다** — 에이전트가 직접 읽는다.

메인이 쓰는 규칙(등급 정의·판정 절차·기록 명령)은 여기 없다. `SKILL.md`에 있다.
단 아래 **공간복잡도 관례**는 메인도 Phase 3 (b)에서 그대로 쓰므로, 표를 확정할 때
메인 역시 이 파일을 읽는다.

---

PS 블로그 포스트를 분석한다. **등급은 매기지 않는다 — 분석만.** **파일을 수정하지 않는다.**

리뷰 대상은 호출 프롬프트에 파일 절대경로 목록으로 주어진다. 순서대로, 하나 끝내고 다음.

## 문제 인지 (정직성 게이트 — 먼저)

각 포스트마다 문제를 확실히 아는지 판정해 리뷰 최상단에 표시:

- ✅ 확실히 앎 → 그대로 진행
- ⚠️ 대략만 앎 / ❌ 모름 → 포스트의 문제 링크를 **WebFetch로 원문 확인** 후 진행
- fetch 실패 시 "신뢰도 낮음" 명시. **아는 척 금지** — 모르면 모른다고 적는다.
- (원문은 검토용으로만 읽고, 포스트에 복붙하지 않는다.)

## 분석 기준

### 아이디어

- 논리적 완결성: "왜 이렇게 하면 되는지"가 있는가? 비약·오류는?
- 독자 이해도: 설명만 읽고 구현할 수 있는가?
- 수식/오타 일관성.
- 비어있으면 "아이디어 비어있음"만 적고 넘어간다.
- **표준 알고리즘의 일반 이론은 요구하지 않는다** — 정당성 증명·내부 동작(크루스칼이 왜 최소를
  보장하는지, 유니온 파인드가 사이클을 어떻게 거르는지 등)은 **별도 알고리즘 개념 포스팅 몫**이다.
  요구 대상은 **이 문제 고유의 통찰**뿐 — 예: "이 문제가 MST로 환원된다"는 인식은 요구하되,
  "크루스칼이 왜 성립하는가"는 요구하지 않는다.
- **자명한 코드는 설명 생략을 허용한다.** 독자가 문맥으로 메울 수 있으면 누락이 아니다.
  "설명 부족" 계열은 **비-trivial한데 빠진 경우로 한정**한다.
- **단 사실 오류는 강도와 무관하게 지적한다.** 결론이 맞아도 논거는 따로 검증할 것 —
  수치가 맞다고 그 수치를 정당화하는 문장까지 맞는 건 아니다(반례를 찾아볼 것).

### 코드

- 정확성: 정상이면 "정확", 틀리면 상세히(반례 포함).
- 엣지 케이스: 경계값(N=1, 빈 입력, 최댓값 등)을 구체적으로 검증.
- 개선점: 적극 제안. "없음"은 구체적 근거 필수. 특히 **미사용 코드**(선언만 하고 안 쓰는
  변수·함수, `include`했으나 안 쓰는 헤더)와 **명명 일관성**(같은 역할인데 이름이 들쭉날쭉)을
  놓치지 말 것. 단 이런 건 대개 사소 지적이므로 개선점 노트로만 남긴다(등급은 메인이 매긴다).
- 다국어: 로직 동일 → 하나만 상세 + 차이점. 로직 상이 → 각각.

### 대안 풀이

- 사용자 풀이보다 더 효율적이거나 더 표준적인 **알려진 접근**이 있으면 제시한다 —
  핵심 아이디어 한두 줄 + 복잡도 비교(전체 구현 코드까지는 불필요).
- 사용자 풀이 자체에서 불필요한 비효율(과한 자료구조, 중복 계산·순회, 점근적으로
  더 나은 방법이 뻔한 경우)이 보이면 구체적으로 지적한다.
- 이미 최적이거나 이 문제 규모에서 대안이 실익 없으면 "대안 없음"만 적고 넘어간다.
  없다고 대충 넘기지 말 것 — 실제로 아는 게 없을 때만 "대안 없음".

### 복잡도

- **접근마다 시간·공간 값을 직접 계산해 반드시 명시한다.** 표가 이미 차 있든 비어 있든 마찬가지다.
  표가 비어 있으면 여기서 낸 값이 그대로 파일에 기록될 후보가 되므로, "미기입"만 적고 넘어가지 말 것.
- 그 위에서 표와 대조: 표가 비어 있으면 `미기입 → 제안값 X`, 값이 다르면 `불일치 → 정정 제안`,
  같으면 `일치`.
- 접근이 여러 개면 각 풀이의 표를 개별 계산·개별 검증.
- **기호를 쓰면 그 기호가 무엇인지 반드시 밝힌다** — `$N$ = \`nums\` 길이` 식으로.
  값과 함께 이 정의가 표 아래에 기록된다. 코드의 다른 변수와 대소문자만 다르거나
  이름이 겹치면 그 점도 적는다.

**공간복잡도 관례 (이 블로그 고정):**

- **auxiliary space로 적는다 — 입력도 출력도 제외**하고, 알고리즘이 추가로 잡는 공간만 센다.
  **← 이것만이 발행본 실측에서 나온 규칙이다**(120809는 길이 $N$ 배열을 새로 만들어 반환하는데
  $O(1)$로 표기돼 있다). 기존 글과 충돌하지 않음이 확인된 유일한 항목.
- **복사본은 두 조항으로 가른다 (2026-07-28 확정):**
  - **시그니처가 준 복사본은 무조건 제외.** C++ 값 전달 파라미터, Java 오토박싱 — 플랫폼이
    시그니처를 정하므로 선택의 여지가 없다. 변형해서 쓰더라도 제외한다(242 풀이 2가 값 전달
    복사본을 정렬하고도 $O(1)$인 근거).
  - **코드가 만든 복사본은 용도로 가른다.** 원본을 훑기 위한 **순회 관용구면 제외** —
    `for (char c : s.toCharArray())`는 `charAt` 인덱스 루프로 바꿔도 알고리즘 설명이
    한 글자도 안 바뀐다. **저장·변형해서 알고리즘 데이터로 쓰면 포함** — leet_9의
    `new StringBuilder(str).reverse().toString()`은 뒤집은 문자열을 비교 대상으로
    보관해야 풀이가 성립하므로 $O(\log x)$다. `Arrays.sort(s.toCharArray())`처럼
    정렬해서 쓰면 후자에 해당한다.
  - 참고: LeetCode 공식 해설은 `toCharArray()`를 세는 더 엄격한 기준이다. 이 블로그는
    위 기준을 쓰며, 그래서 값이 다를 수 있다.
- 재귀는 **호출 스택 깊이를 포함**(깊이 $N$ 재귀는 $O(N)$). 2026-07-25에 정한 기본값이지만
  **아직 값이 실제로 갈린 사례가 없어 시험된 적은 없다.** 재귀만 있고 배열이 없어 이 규칙이
  단독으로 값을 결정하는 풀이면, 값과 함께 **"이 규칙이 처음 실제로 적용되는 사례"임을 명시**한다
  (메인이 사용자에게 확인할 수 있도록).
- 이 관례로도 값이 갈리면 **단정하지 말고 두 관점을 근거와 함께 제시**한다. 관례가 덮는 범위
  안에서는 시간복잡도처럼 확정적으로 적는다.

### 구조

- front matter / 섹션 / 코드블록 언어태그 등 템플릿 준수.
- 빈 아이디어·미기입 복잡도 표·TODO 제목/링크·언어태그 없는 코드블록·콜아웃 손상은
  **기계 검사가 이미 잡는다.** 다시 적지 않는다.

## 지적하지 않는 PS 관용 패턴

- C++ `sizeof(arr)`, `find() != -1`, scanf/printf·cin/cout 혼용
- 학술적 C++ 스타일 제안(`std::transform + toupper` 등)
- Java `BufferedWriter` vs `StringBuilder`+`System.out` (동등)
- 출력 끝 trailing newline
- 인라인 수식 뒤 공백(`$d$라`) — 기계 검사가 행 번호까지 잡으므로 중복 지적 불필요
  (무시 대상이라는 뜻은 아니다)
- 통과 코드의 이론적 worst-case(문제 제약 밖 "만약 N이 더 크면")
- C++ 만능 헤더(`bits/stdc++.h`)·플랫폼(프로그래머스 등) 제공 헤더 — 미사용처럼 보여도 PS 관용,
  dead code로 지적 금지(진짜 미사용은 사용자가 개별 `include`한 뒤 안 쓴 경우로 한정)
- **`1+X` 형태의 패딩 위치 표기**(`new int[1+60000]`, `new int[1+len][1+len]`) — 사용자 스타일이다.
  매직넘버·불필요한 상수로 지적 금지.
- **전역 고정 배열**(`int p[100]` 등 문제 제약 상한에 맞춘 크기) — 유니온 파인드·방문 배열 등에서
  경쟁 프로그래밍 표준 관용이다. 하드코딩·재사용 위험으로 지적 금지.
- **예약어·표준 이름 충돌로 강제된 언어 간 명명 차이** — Java `union`/C++ `unite`(`union`은 C++
  예약어), Java `map`/C++ `mp`(`using namespace std;` 아래 `std::map`과 충돌), `set`/`st` 등.
  "명명 일관성" 항목으로 지적 금지.
- **플랫폼이 고정한 시그니처의 미사용 파라미터** — 프로그래머스 등은 `solution(...)` 인자 목록을
  문제 쪽에서 정하므로 안 쓰더라도 지울 수 없다. dead code로 지적 금지.
- **프로그래머스 풀이의 `static`(Java)/전역(C++) 컬렉션이 `solution()` 안에서 초기화 안 되는 패턴** —
  DFS/BFS로 후보를 static 리스트·전역 벡터에 쌓고 clear 없이 쓰는 식(84512 모음사전이 계기,
  2026-08-03). "여러 테스트케이스가 같은 프로세스에서 돌면 값이 누적돼 오답"이라는 우려는
  **LeetCode류(브라우저가 한 프로세스에서 여러 테스트를 연달아 호출) 아키텍처를 전제한 것이고,
  프로그래머스가 실제로 그렇게 도는지는 확인된 바 없다.** 오히려 `/ps` 파이프라인은 이미 Accepted된
  코드만 가져오므로, 진짜 문제였다면 애초에 통과하지 못했을 것 — 이게 반증에 가깝다. **지적 금지.**

> 위 세 항목의 공통 원리: **선택의 여지가 없는 코드는 지적 대상이 아니다.**
> 진짜 미사용·진짜 불일치는 사용자가 스스로 선언하고 스스로 이름 붙인 것으로 한정한다.

**문장 하나만 떼어 보고 지적하지 말 것** — 같은 글의 다른 문장과 어법이 일관되면 문맥상
모호하지 않은 경우가 많다(12900 "가로로 배치"를 타일 1장으로 오독한 사례).

```
**문제 인지**: ✅/⚠️/❌ (한 줄)
### 아이디어
...
### 코드
**정확성**: ... / **엣지 케이스**: ... / **개선점**: ...
### 대안 풀이
... (또는 "대안 없음")
### 복잡도
(접근마다 한 줄) 풀이 N: 시간 $O(?)$, 공간 $O(?)$ — 근거 한 줄 — 일치 / 불일치 / 미기입
### 구조
OK / (상세)
```
