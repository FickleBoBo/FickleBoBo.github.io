# PS 포스트 프로즈·표기 컨벤션

`ps`가 만든 스캐폴드의 프로즈 필드(`description`, `## 1. 아이디어`, `## 2. 복잡도`의 변수 설명, `## 3. 코드`의 블록 설명)를 **사람이 직접 쓰거나 `review-post`가 채울 때** 따르는 단일 규칙. `ps/SKILL.md`(사람이 손으로 쓸 때)와 `review-post/SKILL.md`(서브에이전트가 채울 때)가 이 파일을 정본으로 참조한다 — 같은 규칙을 각 SKILL.md에 다시 적지 않는다.

## 어투·시제

- 다체(평서체 — "~이다", "~된다")로 통일. 합니다체 금지.
- 시제는 문맥 기준으로 구분: 알고리즘이 왜 성립하는지 논증하는 문장은 현재형(`~한다`/`~된다`), 여러 방법 중 이걸 택했다는 서술(구현·전략 선택)은 과거형(`~했다`).
- `해주다`/`~해줬다` 계열은 방향과 무관하게 배제(항상 캐주얼함).

## 용어 표기

- **오버플로우** (not 오버플로). 마찬가지로 언더플로우.

## 백틱 vs 수식(`$...$`)

- **백틱**: 코드에 그 형태 그대로 등장하는 리터럴·변수·함수명(`array`, `solution`).
- **`$...$`**: 코드에 그 형태로는 없는 파생·서술 표기 — `$2ab$`, `$a \oplus b$`, 좌표 `$(i, j)$`·`$(1, 1)$`(코드엔 `dp[i][j]` 인덱싱으로만 등장하지 튜플로는 없음).
- 변수가 코드에 실제로 있어도, 그 변수를 쓴 공식·유도는 표현 전체를 수식으로 — "총 `k` $= (n + 1) / 2$개"(X) → "총 $k = (n + 1) / 2$개"(O). 공식 맥락에서 백틱-수식 혼용은 어색함.

## 수식 표기 세부 (복잡도 섹션 포함, 수식 전체에 적용)

- 변수명은 대문자 관용: $N$, $M$. 코드에 소문자 파라미터로 등장해도 프로즈·수식·표에서는 대문자로 승격(`m` → `$M$`).
- 이항 연산자 `+` `-` `/`(나눗셈)는 양쪽에 공백: `$N / 2$`(not `$N/2$`), `$(i - 1, j)$`(not `$(i-1, j)$`). 지수(`n^2`)·아래첨자처럼 항상 붙여 쓰는 표기는 예외.
- 1,000 이상 숫자는 `{,}`로 콤마: `$10{,}000$`(not `$10000$`). 그냥 `,`만 쓰면 KaTeX가 콤마 뒤에 여백을 넣어 어색해짐. 연도처럼 원래 콤마를 안 쓰는 표기는 예외.
- 곱셈 결합:

  | 형태                 | 표기                               | 예                               |
  | -------------------- | ---------------------------------- | -------------------------------- |
  | 맨몸 변수 하나 × log | 붙여씀                             | `$O(N \log N)$`, `$O(N \log M)$` |
  | 맨몸 변수 두 개 곱   | 사이에 `\times`                    | `$O(N \times M)$`                |
  | 변수곱 + log         | 곱에만 `\times`, log 앞뒤는 붙여씀 | `$O(N \times M \log K)$`         |

  `\cdot`나 그냥 붙여쓰기(`$O(NM)$`)는 쓰지 않는다.

- 로그 밑은 생략한다 — 점근 표기에서 밑은 상수배라 무의미(`$O(N \log N)$`, `$O(\log \log N)$`). 밑이 값을 실제로 좌우할 때만 표시하며, 특히 **10진 자릿수**는 `$\log_{10}$`. `$O(\cdot)$` 안에 명시적 밑을 같이 쓰지 않는다 — O가 밑을 흡수하므로 `$O(\log_{10} N)$`(X) → `$O(\log N)$`, 또는 O를 빼고 `$\approx \log_{10} N$`.
- 자릿수를 복잡도 인자로 쓰면 표에 `$\log$`를 직접 박지 않고 문자 `$D$`로 두고, 변수 설명에서 `($D$ = `n`의 자릿수 $\approx \log_{10} n$)`으로 푼다.

## `description`

- 완성된 본문 기준 TL;DR. **한 문장, 대략 60자 이내**를 목표로 한다 — 넘어가면 문제의 규칙을 다 담으려는 것이다. 최종 산출물 하나만 짚고 부수 규칙(연산 정의, 경계 조건, 반복 절차)은 버린다.
- **풀이 방법이 아니라 문제 자체를 서술** — 다중 접근이어도 접근법을 나열하지 않는다.
- `title`에 이미 있는 정보(언어 브라켓 `[Java][C++]` 등)는 반복하지 않는다.
- **순수 평문** — 백틱·`$...$` 등 마크다운/수식 표기를 넣지 않는다. Chirpy가 부제목·홈 목록 미리보기·`<meta>`에 그대로 렌더링하므로 `` `n` ``이 백틱째로 노출된다. 변수는 그냥 `n`/`i`로 쓴다.
- 문장 종결은 명사형: `~를 구하는 문제.`, `~를 판별하는 문제.`, `~를 반환하는 문제.` (`~한다`/`~구한다`처럼 서술형으로 끝내지 않는다 — 홈 목록에서 라벨처럼 훑기 좋게). 다만 매 편이 `~하는 문제.` 한 리듬으로 굳지 않게 대상·동사를 바꿔 쓴다.
- 난이도를 라벨로 붙이지 않는다 — `warm up` 태그가 있어도 `~워밍업 문제.`로 끝내지 않고 다른 문제와 똑같이 문제 자체만 서술한다.

## `## 1. 아이디어`

- **"무엇"이 아니라 "왜"를 쓴다.** 코드가 어떤 연산을 하는지는 `## 3. 코드`가 이미 보여준다 — 그걸 산문으로 옮기면 중복이다. 독자(와 나중의 나)가 납득하려면 이 방법이 왜 옳은 답을 주는지, 문제의 어떤 조건이 이 접근을 가능하게/유리하게 만드는지가 있어야 한다. 코드와 문제를 요약하는 데서 멈추지 않는다.
- 그렇다고 부풀리지도 않는다 — 필요한 논증만 담고, 기법 자체의 교과서 설명이나 코드 줄 단위 워크스루로 늘리지 않는다(장황함도 결함).
- 서술(풀이 해설) 중심. 제약조건을 표로 따로 정리하지 않는다. 서브헤딩 없음. 지문 원문을 복붙하지 않는다(자기 말로 요약 — 저작권).
- **언어 무관하게 쓴다.** 특정 언어가 어떤 함수·트릭·자료구조로 구현하는지는 아이디어에 넣지 않는다("Python 풀이는 `replace`로 ~", "Java는 `StringTokenizer`로 ~" 전부 금지 — 비교가 아니어도 한 언어 단독 언급도 안 됨). 한 언어만 접근이 눈에 띄게 다르면, 세 풀이를 아우르는 공통 알고리즘을 아이디어에 쓰고(부호 있는 항의 합처럼 추상화), 그 언어만의 구현 설명이 꼭 필요하면 `## 3. 코드`의 해당 코드 블록 아래 프로즈로 뺀다.
- **대상 독자 전제**: 알고리즘/자료구조의 기본 개념(DP·이분탐색·차분 배열이 뭔지 등)은 안다고 전제하고 재설명하지 않는다. 대신 **이 문제에 특화된 추론**(왜 이 점화식이 성립하는지, 초기값·경계를 왜 그렇게 잡는지, 왜 이 기법을 이 문제에 적용할 수 있는지)은 생략 없이 풀어쓴다.
- **다중 접근**: 접근마다 그 접근을 쓰는 이유를 밝힌다 — 특히 뒤 접근은 앞 접근의 어떤 한계(복잡도·특정 입력 규모 등) 때문에 나오는지. 기법 동작 자체가 아니라 "이 문제에서 그 기법이 왜 통하는지(적용 조건)"를 쓴다.
- 제약 수치가 풀이 근거로 실질적으로 중요하면 문장 안에 자연스럽게 녹이고, 안 중요하면(사소한 워밍업 등) 생략한다.
- 알고리즘/풀이 레벨만 쓴다. 복잡도 변수가 뭘 가리키는지는 여기가 아니라 `## 2. 복잡도`에 적는다.
- **금지 패턴(AI가 쓴 티가 나는 지점)**:
  - 오프닝을 문제 재진술로 시작하지 않는다 — `~를 구하는(하면 되는) 문제다`, `전형적인 X 문제다`, 지문 한 줄 요약. `title`·`description`이 이미 한 말이다. 첫 문장부터 이 풀이의 핵심 관찰로 들어간다.
  - `~가 성립하는 이유는 ~ 때문이다` 식 정리-증명 템플릿 어투를 반복하지 않는다 — 논증은 하되 평범한 서술로.
  - 코드가 한 일을 순서대로 옮긴 문장·문단을 쓰지 않는다(`먼저 해시맵으로 ~ 셌다`, `~로 남겼다`, 끝에 `배열 버전은 ~, 최적화 버전은 ~`). 그건 `## 3. 코드`가 보여준다.
  - 모든 경계·초기값·모듈러 연산을 같은 비중으로 설명하지 않는다 — 비자명한 것 하나만 짚고 나머지는 넘어간다.
- **분량은 문제의 실제 난이도에 비례한다.** 통찰이랄 게 없는 워밍업·기계적 문제는 1~2문장으로 끝낸다(억지로 한 문단으로 늘리지 않는다). 비자명한 관찰이 있는 문제만 문단 단위로 쓰되, 그 경우도 crux 하나 — 코드만 봐서는 안 드러나는, 이 풀이가 옳은 이유 — 에 집중하고 기법의 교과서 설명이나 줄 단위 워크스루로 늘리지 않는다.
- `review-post`가 빈 아이디어를 채울 때:
  - 채운 아이디어는 사용자가 다시 쓸 초안이다 — 완성본을 목표로 부풀리지 말고 뼈대(핵심 관찰 + 꼭 필요한 논증)만 남긴다.
  - 원문(플랫폼 공식 문제 페이지)을 항상 직접 재확인한다 — 이미 아는 유명한 문제여도 예외 없음(제약조건 수치를 잘못 기억해 조용히 틀리는 걸 막기 위함).
  - 제약조건에 지수/첨자(`$10^k$`류)가 보이면 WebFetch 결과를 믿지 말고 `curl -s <url> | grep -o '<sup>[^<]*</sup>'`로 원본 HTML의 `<sup>`/`<sub>`를 직접 확인한다.
  - Claude가 겪지 않은 시행착오("처음엔 이렇게 생각했는데")를 지어내지 않는다 — 바로 최종 아이디어부터 쓴다.
  - 커뮤니티에서 실제로 쓰이는지 확인 안 된 용어를 "~라고 불린다"로 인용하지 않는다 — 확실치 않으면 검증하거나 서술적 표현으로 순화.

## 다중 접근 — 접근 이름

드래프트에 `### 풀이` 헤딩이 2개 이상이면 각 접근에 이름을 붙인다(`ps` 스캐폴드는 번호만 만들고 이름은 비워 둔다).

- **코드 섹션 헤딩**: `### 풀이 N: 이름 [Java][C++]...` — 번호 + 콜론 + 이름, 뒤에 언어 브라켓. 첫 접근도 `### 풀이 1: 이름`으로 번호를 붙인다.
- **`## 2. 복잡도` 표 "접근" 열**: 접두어(`풀이 N:`) 없이 이름만 (`직접 순회`, `차분 배열`). 표 아래 변수 프로즈에서 특정 접근을 가리킬 때도 이름으로 (`차분 배열 풀이의 diff가 ...`).
- 이름은 코드를 읽고 그 접근을 한마디로 식별하는 표현으로 — 알고리즘·자료구조명(`차분 배열`, `DP`, `투 포인터`), 전략(`완전 탐색`, `그리디`), 또는 핵심 연산(`구간 직접 순회`).
- 접근이 하나뿐이면 `### 풀이 [langs]` 그대로 두고 이름을 붙이지 않는다.
- `sync`의 헤딩 매칭은 `### 풀이 N` 뒤의 접미어(`: 이름`, 언어 브라켓)를 무시하므로 이름을 붙여도 코드 동기화에 영향 없다.

## `## 2. 복잡도` — 셀 값과 변수 설명

이미 AC된 코드의 복잡도는 판단이 아니라 사실이다 — 누가 채우든 같은 표가 나와야 한다. 아래 절차와 예시를 그대로 따른다.

### 지배 변수 고르기

1. 코드가 실제로 순회·복사·정렬·재귀하는 자료구조를 나열한다.
2. 각각의 크기를 문제 제약에서 확인한다.
3. 실행 시간을 지배하는 것을 변수로 잡는다. 독립적으로 커지는 게 여럿이면 각각 별도 문자.
4. 입력 파라미터 등장 순서로 $N$을 배정하지 않는다 — 코드가 실제로 도는 대상 기준.
5. 전체 중 일부만 쓰면(부분 문자열, 상위 $K$개 등) 전체 크기가 아니라 그 부분 크기가 변수.
6. 변수명은 문제의 대상을 가리키는 관용 문자로 — 격자는 행 $N$·열 $M$, 그래프는 정점 수에 문제 용어를 그대로 승격(`n` = 컴퓨터 수 → $N$)하고 간선 수는 $E$. 교과서 $V$를 습관적으로 쓰지 않는다.

### 반복 형태별 고정 예시

| 코드 형태                    | 시간            | 공간            | 변수 설명 프로즈                     |
| ---------------------------- | --------------- | --------------- | ------------------------------------ |
| 배열·문자열 한 번 순회       | $O(N)$          | $O(1)$          | ($N$ = `arr`의 길이)                 |
| 정렬 후 순회                 | $O(N \log N)$   | $O(N)$          | ($N$ = `arr`의 길이)                 |
| 모든 쌍 이중 루프            | $O(N^2)$        | $O(1)$          | ($N$ = `arr`의 길이)                 |
| 격자 순회·DP                 | $O(N \times M)$ | $O(N \times M)$ | ($N$ = `board`의 행 수, $M$ = 열 수) |
| 그래프 BFS/DFS (인접 리스트) | $O(N + E)$      | $O(N + E)$      | ($N$ = 정점 수, $E$ = 간선 수)       |
| 그래프 BFS/DFS (인접 행렬)   | $O(N^2)$        | $O(N)$          | ($N$ = 정점 수)                      |

공간은 입력을 제외하고 **추가로** 쓰는 메모리 기준(정렬이 $O(N)$ 보조 배열을 쓰면 $O(N)$, 제자리면 $O(1)$·$O(\log N)$). 재귀는 최대 깊이가 공간에 들어간다.

### 변수 설명 프로즈 포맷 (표 아래)

**아래는 예시가 아니라 고정 포맷이다.**

- 셀이 $O(1)$뿐이면 프로즈 줄을 아예 쓰지 않는다.
- 그 외에는 표 바로 아래 **한 줄**, **괄호로 감싼 평서형**: `($N$ = <가리키는 대상>)`. 불릿(`- `)·문장 종결형(`~이다.`/`~를 의미한다.`) 금지.
- 대상 표기: 코드 식별자면 백틱(`` `my_string`의 길이 ``), 입력 파라미터면 ``입력값 `n` ``, 파생값이면 서술(`결과 리스트의 길이`).
- 변수 2개 이상: 쉼표로 나열하고, 필요하면 마침표로 끊어 부연 — `($N$ = `s`의 길이, $M$ = `m`. 결과 문자열의 길이는 $N / M$이다)`. 부연도 괄호 안에서 끝내고 닫는 `)` 뒤에 마침표를 붙이지 않는다.

## `## 3. 코드` — 블록 설명 프로즈

- 언어별로 특징적으로 설명할 게 있으면 `### 풀이 N` 헤딩 바로 아래(그 접근법의 모든 언어 공통) 또는 각 코드 블록 바로 아래(그 언어 전용)에 프로즈를 넣어도 된다. 위치로 스코프를 구분한다. 이미 사람이 써둔 설명은 그대로 두고 덮어쓰지 않는다.
- **필수가 아니다** — 대부분의 포스트는 이 프로즈가 없다. 코드가 스스로 설명되면 넣지 않는다.
- **표준 라이브러리 심볼 표기**:
  - C++ 표준 라이브러리 **자유 함수·타입**은 `std::` 접두어를 붙인다(`std::rotate`, `std::reverse`, `std::gcd`, `std::swap`, `std::string`) — 코드가 `using namespace std;`라 접두어 없이 등장해도. "코드에 그 형태 그대로" 백틱 규칙(위 `## 백틱 vs 수식`)의 의도적 예외로, 표준 심볼임을 드러내고 검색성을 높이려는 것. **멤버 함수**는 접두어 없이 호출된 형태대로(`my_string.find()` → `find`).
  - Python 모듈 함수는 코드의 실제 import 스타일을 따른다: `import math` → `math.gcd`, `from itertools import groupby` → `groupby`(맨이름). 메서드는 호출된 형태대로 — 클래스 호출이면 `str.maketrans`/`dict.fromkeys`, 인스턴스면 맨이름(`swapcase`), 관용형은 `"".join`.
  - Java 메서드도 호출 형태대로: `Arrays.sort`(클래스 호출), 인스턴스 메서드는 맨이름(`toCharArray`).

## 언어 비교·언급 금지 (아이디어·코드 섹션 모두, 예외 없음)

어느 섹션에서도 언어끼리 비교하거나 "언어들이 같다"는 식의 서술을 하지 않는다. 표준 함수/슬라이스를 쓴다는 사실은 코드가 이미 보여준다. **아이디어 섹션은 여기서 한발 더 나아가 비교가 아니어도 특정 언어 구현 자체를 언급하지 않는다** — 위 `## 1. 아이디어`의 "언어 무관하게 쓴다" 참고.

- 금지 문구(예): "Java·C++처럼 ~", "~와 달리", "다른 언어는 ~", "각 언어가 ~ 제공", "대부분의 언어가 ~", "각 언어가 제공하는 슬라이스 기능을 그대로 쓴다", "대부분의 언어가 이 비교를 표준 함수로 제공한다".
- 코드 섹션 프로즈는 **그 언어 코드가 하는 일만 단독으로** 서술한다. 예: C++ `std::rotate` 블록 아래엔 `std::rotate`가 `[first, last)` 구간을 어떻게 회전시키는지만 쓰고, "Java는 수동 시프트한다" 같은 대조는 쓰지 않는다. `break` 대응 관계 등도 "이 코드는 첫 조건에서 순회를 멈춘다"처럼 그 언어 안에서만 서술한다.
