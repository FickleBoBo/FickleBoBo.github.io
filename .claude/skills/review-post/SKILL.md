# review-post — PS 포스트 완성도 리뷰

`_drafts/`의 PS 포스트를 완성도 관점에서 평가하고, 비어 있는 `description`/`1. 아이디어`/복잡도 셀 등을 직접 채운다. 프로즈·표기 규칙은 [`STYLE.md`](STYLE.md)가 정본이다.

`review-post`가 채우는 프로즈(`description`, `1. 아이디어`, 코드 블록 설명)는 **사용자가 다시 쓸 초안**이다 — 특히 `1. 아이디어`는 완성된 통찰을 목표로 하지 않고 핵심 관찰과 꼭 필요한 논증만 담은 뼈대를 만든다. 등급도 이 초안의 문장력·통찰을 평가하지 않는다(아래 `### 등급`). 복잡도 표는 반대로 사실이라 누가 채우든 같은 값이 나와야 하며, `STYLE.md`의 절차·예시가 그걸 강제한다.

## 오케스트레이터 (서브에이전트는 이 절을 건너뜀)

1. `python3 <review-code 스킬의 base directory>/scripts/chunk_drafts.py --mode post [경로 ...]`로 대상 드래프트를 청크로 분할(스크립트는 `review-code` 스킬 소유 — 그대로 가져다 씀, `sync`가 `ps`의 스크립트를 쓰는 것과 같은 패턴). 사용자가 특정 포스트를 지목하면 `_drafts/{platform}/`에서 매칭해 절대경로로 넘기고, 안 지목하면 인자 없이 호출(전체 배치).
2. 청크마다 백그라운드 서브에이전트 하나씩 dispatch: Agent 도구, `subagent_type` 생략, `run_in_background: true`, **`isolation: "worktree"`는 쓰지 않음**(이 스킬은 드래프트 `.md`를 직접 Edit하므로, 격리 워크트리에서 돌면 수정이 그 복사본에만 남고 실제 레포에 반영되지 않음). 프롬프트엔 다음만 전달:
   - 이 `SKILL.md` 경로 + [`STYLE.md`](STYLE.md) 경로 — **둘 다 읽고 `## 처리 절차`·`## 출력 형식`을 따르라**고 지시
   - 그 청크에 배정된 드래프트 파일 절대경로 목록
   - 체크리스트/규칙 텍스트를 프롬프트에 옮겨적지 않음 — 위 두 파일이 유일한 출처(안 그러면 나중에 갈라짐)
3. 모든 서브에이전트 종료 후 취합: 드래프트별 결과표 + 등급 + 배치 요약표.
   - 취합 전 **`git status`/`git diff`로 각 드래프트의 실제 변경을 대조 확인** — 서브에이전트 자기 보고("Edit 안 함", "제안만 함")를 그대로 믿지 않음(read-only 규칙을 어기고 몰래 Edit한 사례 있었음).
   - 서브에이전트 서술 중 "이 코드는 X를 한다"처럼 구체적 구현을 근거로 든 지적은 **최소 1~2건 직접 파일을 Read**해 스팟체크(요약 과정에서 왜곡되는 경우 있음).

**기본은 인자 없이 전체 배치.** 스킵 조건 없음 — `## 1. 아이디어`가 비어 있어도 직접 채우는 게 정상 동작이라 `review-code` 이후로는 항상 전체 대상.

**이미 발행된 `_posts/`도 대상 가능**: `sync`로 코드가 갱신된 뒤 코드-설명 정합성을 재확인할 때 `_posts/` 절대경로를 넘김(1단계는 자연히 검증 위주). 일부만 고를 땐 알고리즘/로직이 실제로 바뀐 것만 — 표기 통일·스타일 한 줄 변경은 스킵. 어떤 파일을 골랐는지는 사용자에게 먼저 확인.

## 처리 절차 (드래프트 1개당 — 서브에이전트 몫)

### 1단계 — 빈 필드 채우기

이미 채워져 있으면 그대로 둔다(사람이 쓴 프로즈를 덮어쓰지 않음 — `sync`와 같은 원칙). **단, 사람이 쓴 프로즈의 명백한 오타·맞춤법·백틱 누락은 고친다** — 어투·논리 흐름·구조에 대한 이견은 고치지 말고 2단계에서 리포트만.

- **`description`**: 비어 있으면 완성된 본문 기준으로 작성. 포맷은 `STYLE.md` — 순수 평문, 한 문장·60자 이내, 명사형 종결, 풀이가 아니라 문제 자체 서술, `title` 정보 반복 금지, 난이도 라벨(`~워밍업 문제.`) 금지.
- **`1. 아이디어`**: 보통 사람이 직접 씀. 비어 있으면 코드를 읽고 이해해서 `STYLE.md`의 "`## 1. 아이디어`" 규칙대로 채운다 — **사용자가 다시 쓸 초안**이므로 뼈대만: 문제 재진술로 시작하지 않고 첫 문장부터 핵심 관찰, 분량은 난이도에 비례(워밍업은 1~2문장), 금지 패턴(정리-증명 어투·코드 나레이션) 회피. 원문 직접 재확인, 지수 표기 `curl` 확인, 시행착오 지어내지 않기, 미검증 용어 인용 금지 등 나머지 규칙도 전부 `STYLE.md`.
- **`2. 복잡도` 표**: 빈 셀만 코드 기준으로 채운다(채워진 셀은 그대로). 복잡도는 사실이라 누가 채우든 같은 표가 나와야 한다 — `STYLE.md`의 "지배 변수 고르기" 절차와 "반복 형태별 고정 예시"를 그대로 따르고, `$...$` 표기·변수 대문자·변수 설명 프로즈 포맷도 `STYLE.md`.
- **다중 접근 이름**: `### 풀이` 헤딩이 2개 이상인데 이름이 안 붙어 있으면(`### 풀이`, `### 풀이 2`) 각 접근에 이름을 붙인다 — 코드 섹션 헤딩과 `## 2. 복잡도` 표 "접근" 열 모두. 규칙은 `STYLE.md`의 "다중 접근 — 접근 이름". 접근이 하나뿐이면 건드리지 않는다.
- **`math` 플래그**: `ps`가 스캐폴드 시점에 항상 `true`로 채움 — 여기서 다시 판단할 필요 없고, 혹시 `false`로 바뀌어 있으면 고침.
- **`mermaid` 플래그**: 최종 본문 기준으로 옳게 세팅(맞으면 두고 틀리면 고침).
- **mermaid 다이어그램**: Claude가 직접 채운 `1. 아이디어`엔 필요하다 판단되면 자율 삽입. 사람이 이미 쓴 프로즈엔 이 배치 패스에서 삽입하지 않음 — 사용자가 대화 중 명시적으로 요청했을 때만.
- **`3. 코드` 블록 설명**: `STYLE.md`의 "`## 3. 코드` — 블록 설명 프로즈" 참고. 필수 아님 — 대부분의 포스트는 이 프로즈가 없다.

### 2단계 — 전체 평가

1단계에서 방금 채운 것 포함, 예외 없이 전부 평가한다("방금 내가 쓴 거니 봐주기" 없음). **설명이 그럴듯한지가 아니라 실제 코드와 맞는지** 코드를 직접 열어 대조하고, 직전 배치에서 지적됐던 축으로 점검 범위를 좁히지 말고 매번 아래 전체를 본다.

- **`1. 아이디어`/회고/참고**: 사람이 쓴 것이면 명확성·논리 흐름, "무엇"이 아니라 "왜"를 담는지, 다중 접근이면 뒤 접근의 도입 이유가 있는지(`STYLE.md`의 `## 1. 아이디어`)를 본다. **이번 실행에서 `review-post`가 채운 아이디어는 문장력·통찰·완성도로 평가하지 않는다**(방금 쓴 초안이라 순환) — 아래 "코드-설명 일치"의 사실 정합성과 표기만 본다.
- **표기 컨벤션**: `STYLE.md` 기준 — 백틱 vs 수식, 복잡도 수식 표기(변수 대문자, `\times`, 공백, 콤마), 맞춤법/문법.
- **코드-설명 일치**:
  - 아이디어에서 말한 로직 ↔ 실제 코드.
  - 복잡도 표 값 ↔ 실제 코드.
  - 복잡도 표의 변수 기호가 **실제로 복잡도를 좌우하는 값**인지 — 파라미터가 여럿이면 먼저 등장한 것에 습관적으로 $N$을 붙이지 말고, 코드가 실제로 순회/복사하는 대상을 본다(전체 문자열 중 일부만 잘라 쓰면 전체 길이가 아니라 그 부분 길이가 변수).
  - 인덱싱 오프셋(0-indexed vs 1-indexed) 불일치 주의 — 서술은 `money[i]`인데 실제 코드는 `money[i - 1]`인 식으로 기준이 갈리면 백틱 수식이 코드 리터럴과 안 맞음.

### 등급

정확성 전제 하에 **검증 가능한 축**만으로 매긴다 — 코드-설명 사실 정합성, 표기 컨벤션, 구조 완결성(빈 필드 없음). 프로즈의 문장력·통찰은 등급 대상이 아니다(LLM 초안이든 사람 글이든).

| 등급  | 기준                                                                                                                                                                      |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S** | **사람이 직접 쓴** 아이디어에 이 문제만의 통찰(왜 이 방법이 성립하는지, 놓치기 쉬운 함정)이 있고 나머지도 A. `review-post`가 채운 초안 단계에선 안 나온다 — 흔해선 안 됨. |
| **A** | (기본값) 코드-설명 불일치 없음, 표기 이슈 없음, 빈 필드 없음.                                                                                                             |
| **B** | 표기 이슈 1~2건, 또는 경미한 코드-설명 불일치.                                                                                                                            |
| **C** | 표기 이슈 3건 이상, 또는 로직 수준의 코드-설명 불일치(아이디어가 설명한 알고리즘과 코드가 실제로 다름).                                                                   |

코드 자체 품질(더 나은 알고리즘 여부 등)은 `review-code`의 몫 — 두 스킬은 서로의 판단을 참조하지 않는다.

## 규칙

- **PS 레포 소스 코드는 절대 안 건드림** — 이 스킬은 드래프트 `.md` 파일 하나만 보고 끝나 PS 레포 경로에 접근하지 않음.
- **태그는 여기서 안 다룸** — `review-code`가 후보만 언급, 적용은 사용자가 대화 중 요청했을 때.
- **게이트 아님** — 등급이 낮아도 `publish`는 막지 않음. 결과는 대화로만 전달, 파일로 저장 안 함(다음 수정 한 번에 stale해져 저장 실익이 없음).

## 출력 형식

드래프트별로:

| 항목                     | 처리        | 코멘트                 |
| ------------------------ | ----------- | ---------------------- |
| description              | 채움 / 평가 |                        |
| 1. 아이디어              | 채움 / 평가 |                        |
| 2. 복잡도                | 채움 / 평가 | $O(N \log N)$ / $O(N)$ |
| 컨벤션(백틱/수식/맞춤법) | 평가        | 이슈 N건               |
| 코드-설명 일치           | 평가        | 일치 / 불일치          |

"처리" 열은 `채움`(비어 있어 새로 씀) 또는 `평가`(이미 있어 검토만) 중 하나. `채움`인 `description`/`1. 아이디어`/코드 설명은 코멘트에 `초안 — 검토 요망`을 적는다. 회고/참고 섹션이 본문에 없으면 그 행을 넣지 않는다.
