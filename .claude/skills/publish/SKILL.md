# publish — 완료된 PS 포스트 발행

## 실행

```
python3 <이 스킬의 base directory>/scripts/publish.py [경로 ...]
```

**기본은 인자 없이 전체 배치.** `_drafts/{platform}/`(platform ∈ `PLATFORM_MAP`: programmers/leetcode/codeforces 등) 전체를 스캔해서 "완료" 판정된 드래프트를 전부 각각 독립적으로 발행함. 이 블로그엔 PS 아닌 포스트도 생길 수 있어서, 스캔 범위는 항상 `_drafts/{platform}/`로만 한정 — 다른 종류의 드래프트 폴더는 존재 자체를 모름(안전하게 무시).

사용자가 "이 포스트들 발행해줘"처럼 특정 포스트를 지목하면, `_drafts/{platform}/`에서 그 포스트에 해당하는 파일(제목/번호로 매칭)을 찾아 절대경로로 스크립트에 넘김 — 이 경우에도 "완료 판정"은 동일하게 적용(지목했다고 미완료 드래프트를 강제로 발행하지 않음).

## 완료 판정

드래프트 파일 하나가 "발행 준비 완료"인지는 순수 내용 검사로 결정 — 별도로 `ready: true` 같은 플래그를 사람이 켜줄 필요 없음:

- `## 1. 아이디어` 섹션 본문(HTML 주석·구분선 제외)이 비어있지 않음
- `## 2. 복잡도` 표의 모든 행(접근법별)에서 시간/공간 셀이 둘 다 채워짐

회고/참고는 선택 섹션이라 비어있어도(주석만 있어도) 무시 — 발행을 막지 않고, 발행 시에도 그대로 둠(자동 삭제 안 함). 위 조건 중 하나라도 안 맞으면 그 드래프트는 조용히 스킵(에러 아님, "미완료"로만 보고).

## 발행 1건의 처리 순서

1. front matter의 `date`/`slug`로 PS 레포 원본 폴더를 재구성 + 존재 검증(`sync` 스킬의 `resolve_source_folder` 재사용). **여기서 실패하면 블로그 레포는 아직 아무것도 안 건드린 상태**라 그 건만 에러 보고하고 다음 드래프트로 넘어감.
2. `_drafts/{platform}/{파일명}` → `_posts/{platform}/{파일명}`로 이동(플랫폼 서브폴더 유지 — Jekyll은 `_posts/` 하위 폴더 구조와 무관하게 다 수집함).
3. 이동한 포스트 파일 + (있으면) `assets/img/posts/{slug}/` 에셋 디렉토리 전체를 블로그 레포에 `git add` 후 커밋. 메시지: `feat: {title 필드 그대로}` (예: `feat: [Programmers] #154538 - 숫자 변환하기 [Java][C++]`).
4. PS 레포에서 그 문제 폴더 전체를 `git add` 후 커밋. 메시지는 블로그 커밋과 완전히 동일 — 과거 PS 레포 커밋들은 `154538번` 형식이었지만, 이 블로그를 중심으로 커스텀해나가는 흐름이라 PS 레포도 여기 컨벤션에 맞춤. 이후 PS 레포 로그는 이 시점부터 새 포맷으로 바뀜(과거 커밋까지 소급 변경은 안 함).
5. 두 커밋 다 `Co-Authored-By: Claude <noreply@anthropic.com>` 트레일러를 붙임 — 과거 PS 레포 커밋 컨벤션과 동일한 형태로, 모델 버전을 안 박아둬서 나중에 모델이 바뀌어도 stale 안 해짐.
6. **push는 안 함** — 로컬 커밋까지만. 실제 배포(GitHub Pages 빌드 트리거)로 이어지는 push는 사람이 직접.

이미 커밋된 상태(재실행 등으로 해당 경로에 git 변경사항이 없는 경우)면 그 레포 쪽 커밋은 건너뛰고 "이미 커밋된 상태"로 보고 — 에러 아님.

## 실패 처리

- **1번(PS 레포 폴더 검증)에서 실패** → 아무것도 안 건드림, 그 건만 에러로 보고
- **3번(블로그 커밋)에서 실패** → 파일은 이미 `_posts/`로 이동된 상태로 에러 보고(사람이 직접 `git add`/`commit` 필요) — 자동으로 원래 자리로 되돌리지 않음
- **4번(PS 레포 커밋)에서 실패** → 블로그는 이미 커밋된 상태로 에러 보고(PS 레포만 직접 확인 필요)

각 실패 메시지에 정확히 어느 단계까지 진행됐는지 명시해서, 사람이 뭘 수동으로 마무리해야 하는지 바로 알 수 있게 함. 배치 중 한 건이 실패해도 그 건만 에러로 보고하고 나머지는 계속 진행(ps/sync와 동일한 철학).

## 출력

드래프트별로 다음 중 하나를 한 줄씩:

- **`발행함: {경로} — {블로그 커밋 여부}, {PS 커밋 여부}`** — 각각 `블로그 커밋함`/`블로그 이미 커밋된 상태`, `PS 레포 커밋함`/`PS 레포 이미 커밋된 상태` 중 하나
- **`에러({드래프트 경로}): {메시지}`** — 위 "실패 처리" 3가지 케이스 중 하나가 터진 경우
- **`미완료라 스킵: {드래프트 경로} — {사유}`** — "완료 판정" 조건 중 하나라도 안 맞아서 애초에 시도하지 않은 경우

마지막에 `--- 총 N개 발행, M개는 미완료라 스킵, E개 에러 ---` 총계 한 줄.

## 규칙

- git add 범위는 두 레포 다 "관련된 것 전체"(블로그: 포스트 파일 + 에셋 디렉토리, PS 레포: 문제 폴더 전체) — 파일 단위로 세밀하게 고르지 않음. 과거 PS 레포 커밋들도 실제로 이렇게 폴더 단위였음.
- push는 절대 자동으로 안 함
- PS 레포 원본 소스 파일 내용 자체는 건드리지 않음(커밋만 함) — 코드 정리/변환은 `ps`/`sync`의 몫
