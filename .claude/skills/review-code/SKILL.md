# review-code — PS 포스트 코드 리뷰

`_drafts/`의 PS 포스트에 임베드된 코드를 리뷰한다. 코드는 안 고친다(제안만) — 수정은 PS 레포에서 사용자가, 포스트 반영은 `sync`.

## 오케스트레이터 (서브에이전트는 이 절을 건너뜀)

1. `python3 <이 스킬의 base directory>/scripts/chunk_drafts.py --mode code [경로 ...]`로 대상 드래프트를 청크로 분할. 사용자가 특정 포스트를 지목하면 `_drafts/{platform}/`에서 매칭해 절대경로로 넘기고, 안 지목하면 인자 없이 호출(전체 배치).
2. 청크마다 백그라운드 서브에이전트 하나씩 dispatch: Agent 도구, `subagent_type` 생략(= general-purpose), `run_in_background: true`. 프롬프트엔 **이 `SKILL.md` 경로 + `## 체크 항목`·`## 출력 형식`을 따르라는 지시 + 그 청크에 배정된 드래프트 절대경로 목록**만. 체크리스트 텍스트를 프롬프트에 옮겨적지 않음(이 파일이 유일한 출처, 안 그러면 갈라짐).
3. 모든 서브에이전트 종료 후 취합: 드래프트별 표 + 배치 요약표. 취합 전:
   - **`git status`/`git diff`로 실제 파일 변경을 대조 확인** — 서브에이전트가 "제안만 했다"고 보고하고 드래프트 `.md` 프로즈를 몰래 Edit한 사례 있었음.
   - "이 코드는 X를 쓴다"처럼 구체적 구현을 근거로 든 지적(구현 세부/매직넘버/특정 API 미사용)은 **최소 1~2건 직접 Read**해 스팟체크 — 요약 과정에서 왜곡됨(실사례: 실제로는 `c - 'a' + 'A'` 문자 리터럴 산술인데 "±32 매직넘버"로 서술).

**기본은 인자 없이 전체 배치.** `_drafts/{platform}/`(platform ∈ `PLATFORM_MAP`) 전체가 대상 — 프로즈 완성도와 무관하게 전부(코드만 보는 리뷰라 프로즈 상태를 가릴 이유가 없음, `review-post`와 다른 점).

청크 분할 파라미터(드래프트 최대 4개 / 총 약 1200줄)와 그 근거는 `scripts/chunk_drafts.py` 도크스트링 참고.

## 체크 항목 (서브에이전트 몫)

**전제**: 코드는 전부 AC까지 확인된 것이다. 정확성은 보장된 것으로 놓고 **표준적이거나 더 나은 방법이 있는데 안 썼는지**를 본다 — 시간/공간복잡도, 성능 병목, 그 문제의 정석 구현, 언어 관용 기법, 놓친 변칙·심화 테크닉 여지. 실용 수준이 목표지 억지 우아함이 아니다. "정적 리뷰라 실행은 안 했다"류 면책은 생략한다.

**스타일은 검사하지 않는다.** 변수명, 표기(천단위 구분자·`1 + n` 같은 패딩 크기 표현 등), 동치인 관용구 중 무엇을 골랐는지(`import` vs `from ... import`, 스트림 vs 수동 배열, 안 쓰는 변수 `_` 마스킹 여부 등) — 이런 취향 수준의 선택은 어느 방향으로도 지적하지 않는다. 코드가 정확한지, 더 나은 풀이·복잡도·표준 라이브러리 활용이 있는지, 문제의 정석 풀이인지, 놓친 변칙·심화 테크닉이 있는지, 불필요한 요소가 없는지 — 코드 자체의 품질만 본다. 단 그 선택이 실제 버그를 부르면(아래 "정확성"의 내장명 섀도잉) 그건 정확성 이슈다.

경계가 애매하면 **"이게 실력 없어 보이나"가 아니라 "더 나은 구체적 대안을 댈 수 있나"로 판단한다** — 동치인 대안뿐이면(어느 쪽도 더 낫지 않으면) 지적하지 않는다.

**설명·근거가 그럴듯한지가 아니라 실제 코드와 맞는지** 코드를 직접 열어 대조한다. 직전 배치에서 지적됐던 축(깊이·어투 등)으로 점검 범위를 좁히지 말고 매번 아래 전체 항목을 돈다.

**시작 전 원문(플랫폼 공식 문제 페이지)을 직접 확인한다** — 유명한 문제여도 예외 없음(제약조건·엣지케이스·예제 입출력을 모르면 정확성을 판단할 수 없음). 플랫폼별 조회 방법:

- **Programmers**: WebFetch 정상(제한사항까지 파싱). 지수/첨자 표기(`$10^k$`류)가 보이면 WebFetch를 믿지 말고 `curl -s <url> | grep -o '<sup>[^<]*</sup>'`로 원본 HTML의 `<sup>`/`<sub>`를 직접 확인(WebFetch가 위첨자를 평탄화해 `10^l`을 `10l`로 뭉갬).
- **LeetCode**: WebFetch는 403 → GraphQL이 통과. `curl -s https://leetcode.com/graphql -H 'Content-Type: application/json' --data '{"query":"query q($t:String!){question(titleSlug:$t){title difficulty content}}","variables":{"t":"<slug>"}}'` (slug은 URL의 `/problems/<slug>/`).
- **Codeforces**: 지문 텍스트는 이 환경에서 전부 실패(WebFetch·curl 403, 미러도 안티봇 챌린지) → 사용자에게 복사/`! curl`로 요청. `curl -s https://codeforces.com/api/problemset.problems`는 통과하지만 이름·CF 공식태그·레이팅만 주고 지문은 없다(공식태그는 우리 택소노미와 별개라 그대로 옮기지 말 것).

대상은 각 드래프트의 `## 3. 코드` 섹션(`### 풀이`/`### 풀이 N`별 그룹).

### 정확성

- 원문 제약조건·예제 입출력 기준으로 버그, 엣지케이스 누락.
- 채점 하네스 내부 동작(함수 재호출, 전역/static 상태 잔존 등)을 근거로 버그를 단정하지 않는다 — 검증 안 된 추측이면 "이론적 리스크"로 톤을 낮추고 AC를 반증으로 고려.
- **프로그래머스 예외**: 전역/static 배열이 호출 간 초기화 안 되는 패턴은 프로그래머스 C++ 코드에서 이론적 리스크로도 올리지 않는다(이 패턴이 프로그래머스에서 문제된 사례가 확인되지 않음). 실제 로직 버그면 예외.
- **AC에 영향 없는 출력 바이트 차이는 이슈로 올리지 않는다** — trailing/spurious newline, `cout`(자동 개행 없음) vs `println`/`print`(자동 개행 있음)처럼 각 언어 기본 출력 함수를 그대로 쓴 차이는 정당하다(플랫폼이 trailing whitespace를 채점에서 무시).
- **내장명 섀도잉**: Python에서 `list`/`sum`/`max`/`id` 등 내장명을, C++에서 `using namespace std;` 상태로 `std::` 함수명과 겹치는 이름을 변수로 쓰면 그 스코프에서 원래 심볼이 가려진다. 코드가 이후 그 이름을 함수로 호출하면 실제 버그(C++은 컴파일 에러)라 정확성 이슈, 호출하는 곳이 없으면 이론적 리스크로만 톤을 낮춘다.

### 최선의 접근인지

- 시간/공간복잡도가 더 나은 접근, 더 관용적인 표준 라이브러리 기법이 있는데 안 썼으면 잡는다(다중 접근에 없으면 "추가 고려"로 제안).
- **Java 스트림/메서드 참조**: 취향이라 그 자체로는 지적하지 않는다(위 "스타일은 검사하지 않는다"). 성능이 실제 병목인 자리(큰 배열을 매번 스트림으로 도는 등)에서만 "선택지 중 하나" 톤으로 언급.
- **Python 컴프리헨션/제너레이터/핵심 언어 내장함수**(`math.prod`, `next(iter())` 등): CPython에서 실제로 더 빠르고 PEP8 관례라 "더 나은 접근"으로 힘줘서 지적해도 됨. 단 중첩 `for`/`if`가 2개 이상 겹치거나 부수효과가 있어 한 줄로 안 읽히면 명시적 루프가 맞으니 억지 한 줄 골프는 지양.
- **범용 편의 모듈**(`statistics`, `itertools`의 무거운 조합기 등)은 직접 구현보다 느릴 수 있어 이 우대에서 제외 — Java 스트림과 같은 "선택지 중 하나" 톤까지만.

### 언어별 관용 · 오탐 주의

- 그 언어에서 비관용적이라 실력자 코드로 안 읽히는 부분(더 관용적인 표준 기법이 있으면 "최선의 접근"과 같이). 표기·네이밍 스타일 자체는 위 "스타일은 검사하지 않는다"대로 넘어간다.
- **오탐으로 확인된 패턴 — 그 자체로 이슈 삼지 않는다**:
  - Java `public class Solution` vs `class Solution` — 프로그래머스가 문제(레벨/유형)별로 다른 기본 템플릿을 내려줌. 기존 발행 포스트와 단순 대조만으로 "컨벤션 이탈"을 단정하지 않는다.
  - 언어별 입력 읽는 방식 차이(C++ `cin >>` 토큰 단위 / Java `BufferedReader.readLine()` 라인 단위 / Python `sys.stdin.readline()` 재할당) — 각 언어의 표준 PS 관용구. 단 `\n`을 안 벗겨 이중 개행이 나는 실제 사용 버그는 예외 없이 지적.
  - Codeforces 포스트에 Java/Python 풀이가 없는 것 — 코포는 C++ 단독으로 싣는다(독자가 거의 다 C++). "언어 누락"으로 지적하지 않는다. PS 레포 코포 폴더에서 `Main.java`/`Main.py`가 삭제돼 있어도 의도된 것.

### 불필요한 요소

안 쓰는 import/using, 선언만 되고 실제로 안 읽히는 변수, 호출되지 않는 함수/헬퍼. AC엔 영향 없어 넘어가기 쉬운데 리팩터링 잔재로 남는 경우가 많으니 명시적으로 확인.

### 다중 접근/언어 간 일관성

같은 문제 안에서 접근끼리·언어끼리 **실제 로직/구조가 갈리는** 차이(한 언어만 배열을 직접 mutate해 부수효과가 생기는 등 "동작이 실제로 갈리는" 케이스)만 지적. 각 언어 관용구를 그대로 쓴 정당한 차이(출력 바이트 등)나 표면적 스타일 차이는 넘어간다.

### 태그 후보

**정본은 `<이 스킬의 base directory>/tags.yaml` — 어휘집 + 헤더 주석(사용법 0~6)과 `boundary_notes`를 읽고 그대로 따른다.** 자유 태그 생성 금지, 후보만 언급. 요지:

- 코드가 실제 쓰는 기법에 가장 구체적인 태그 → `parents` 재귀로 조상까지 후보(다중부모면 양쪽 라인 다, `contextual`이면 그 판단 기준까지).
- `math`/`implementation`은 핵심 난이도일 때만(tags.yaml 0 — `string`/`geometry` 같은 도메인 태그는 이 바 없이 도메인에 속하면 붙임). 이 바를 통과하는 기법 태그가 하나도 안 남을 때만 `constructive`/`ad hoc`/`warm up`, 판단은 접근 단위.
- 다중 접근이면 접근별로 나눠 제시(`풀이1: warm up / 풀이2: math`), front matter엔 합집합.
- **파일엔 안 씀** — 사용자가 "태그 달아줘"라고 명시했을 때만 그 자리에서 front matter에 적용(전부 큰따옴표).

## 규칙 — 코드 수정 절대 금지

**PS 레포 소스 파일을 절대 Edit하지 않는다.** review-code는 PS 레포 경로에 접근하지 않고 드래프트 `.md`에 이미 임베드된 코드 블록만 읽는다. 이슈/제안만 리포트하고 실제 수정은 사용자가 PS 레포에서 직접(AC 재확인 포함). 수정된 코드가 포스트에 반영되는 유일한 경로는 `sync`.

## 출력 형식

드래프트별로 이상 없으면 "이상없음"만, 이슈 있으면:

| 구분        | 위치          | 내용 |
| ----------- | ------------- | ---- |
| 버그/정확성 | 풀이 2 · Java | ...  |
| 언어 관용   | 풀이 1 · C++  | ...  |
| 접근 제안   | —             | ...  |
| 태그 후보   | —             | ...  |

위치는 `풀이 N · 언어`(단일 접근이면 `풀이 · 언어`), 포스트 전체에 걸리면 `—`.

| LeetCode #42        | 이슈 2건 |
