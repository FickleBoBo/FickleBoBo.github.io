# PS 포스트 프로즈·표기 컨벤션

`ps`가 만든 스캐폴드의 프로즈 필드(`## 1. 아이디어`, `## 2. 복잡도`의 변수 설명, `## 3. 코드`의 블록 설명)를 **사람이 직접 쓰거나 `review-post`가 채울 때** 따르는 단일 규칙. `ps/SKILL.md`(사람이 손으로 쓸 때)와 `review-post/PROCEDURE.md`(서브에이전트가 채울 때)가 이 파일을 정본으로 참조한다 — 같은 규칙을 각 문서에 다시 적지 않는다.

정규식으로 판정되는 일부 규칙(합니다체, `해주다`, em-dash, 오버플로우·`안 되다`·`필요 없다`·`둘 다`·`하는게`·`될거`류 띄어쓰기, `\frac`, 복잡도 `O()` 안 `\cdot`, 천 단위 콤마, 이항 연산자(`/`·`+`·`-`) 공백, `### 풀이` 헤딩 형식, 수식 뒤 조사·단위 띄어쓰기, `패널티`·`뭉탱이` 어휘, 태그 어휘·조상 누락, 폐기된 `description`, 복잡도 표에 쓴 변수의 정의 누락·변수 설명 고정 포맷·출력 버퍼 주석)은 `scripts/lint_post.py`가 기계적으로 검사한다. 규칙을 바꾸면 그 스크립트의 같은 항목도 같이 바꾼다.

## 어투·시제

- 다체(평서체 — "~이다", "~된다")로 통일. 합니다체 금지.
- 시제는 문맥 기준으로 구분: 알고리즘이 왜 성립하는지 논증하는 문장은 현재형(`~한다`/`~된다`), 여러 방법 중 이걸 택했다는 서술(구현·전략 선택)은 과거형(`~했다`).
- `해주다`/`~해줬다` 계열은 방향과 무관하게 배제(항상 캐주얼함).
- **em-dash(`—`)로 문장 뒤에 부연절을 매다는 패턴을 쓰지 않는다** — "특정 원소만 더 굴릴 수 없다 — 모든 원소가 ..." 식. 보충할 내용은 마침표로 끊어 다음 문장으로 쓴다. (이 규칙은 세 프로즈 자리 전부에 적용. 표·머리말의 대시는 무관.)

## 맞춤법 · 띄어쓰기

사람이 쓴 프로즈를 검토할 때 매번 기본으로 스캔하는 체크리스트(세 프로즈 자리 모두 + 대회 후기 총평 등). 한글 맞춤법이 흔들리는 자리만 모았다.

- **의존명사(것/게/거/걸)는 예외 없이 띄운다.** 관형사형 어미(-는/-(으)ㄴ/-(으)ㄹ) 뒤의 "것" 축약형은 항상 띄어쓴다: `하는게`→`하는 게`, `될거`→`될 거`, `본거`→`본 거`, `아닌거`→`아닌 거`. 보조 용언 붙여쓰기(`할만하다`)가 허용돼도 뒤의 "거"는 독립 의존명사라 또 띄운다(`할만했던 거`).
- **`안 되다`는 띄운다.** `안되다`는 "잘 안되다/곤란하다"라는 별도 뜻이고, 단순 부정("되지 않다")은 띄어쓴다: `해결이 안 됐고`, `AC가 안 돼서`.
- **`필요 없다`는 띄운다.** `필요없다`는 표제어가 아니다.
- **`못 + 동사`는 띄운다.** `못 봤다`(보지 못했다)는 띄우고, 별도 단어 `못하다`(잘하지 못함)만 붙인다.
- **`둘 다`는 항상 띄운다.**
- **`한 번`/`한번`은 의미로 가른다.** 횟수를 셀 때는 `한 번`, "시도해본다"는 뜻이면 `한번`.
- **붙여쓰는 예외(반대 방향)**: `쓸데없다`(붙임), `부분집합`(수학 용어, 붙임).
- **조사 정확성.** 문장을 고쳐 쓰다 조사가 어긋나는 경우가 실제로 나온다. `배열에 내림차순인지`(오류, "에"는 위치 조사) → `배열이 내림차순인지`.
- **수식(`$...$`) 뒤 조사·단위는 붙인다.** `$N$ 이`→`$N$이`, `$A$, $B$ 의`→`$B$의`, `$N$ 단`→`$N$단`. 평문 숫자 뒤 조사와 같은 원리(`10으로`)이고, 공백이 끼면 조사가 따로 떨어져 읽힌다.
- **어휘 표기**: `페널티`(not 패널티), `뭉텅이`(not 뭉탱이, 비표준어), `오버플로우`·`언더플로우`(not 오버플로·언더플로).

## 평문 · 백틱 · 수식(`$...$`)

값·수량·식을 프로즈에 쓸 때 셋 중 하나를 고른다. **`## 1. 아이디어`·`## 2. 복잡도` 변수 설명·`## 3. 코드` 블록 설명에 동일하게 적용**되는 규칙이다. **기본값은 평문** — 한국어 서술로 풀 수 있으면 마크업하지 않는다("2씩 증가", "7로 나눈 몫", "-1을 반환", "인덱스 0, 5, 10", "1부터 `n`까지"에서 `1`). 아래 두 트리거에 걸릴 때만 마크업한다.

섹션별로 이 규칙 위에 얹히는 것: **복잡도 표·변수 설명**에서는 복잡도 변수를 대문자 `$N$`으로 승격한다(`## 2. 복잡도` 안 `### 수식 표기 세부` 1번), **코드 블록 설명**에서 C++ 표준 자유 함수는 `std::` 접두어를 붙인다(아래 "`## 3. 코드` — 블록 설명 프로즈" 절, 백틱 규칙의 의도적 예외).

- **백틱 — 코드의 토큰을 코드로서 가리킬 때.**
  - 코드에 그 형태로 있는 식별자·함수명(`array`, `solution`, `dp`), 문자·문자열 리터럴(`"Z"`, `"EMPTY"`).
  - 코드 어법으로 쓴 식 하나를 통째로 — 배열·테이블 인덱싱, 점화식 포함: `` `arr[i]` ``, `` `n % 10` ``, `` `dp[i][j] = max(dp[i - 1][j], dp[i][j - 1]) + cost` ``. 어법 유지: `max`(not `\max`), `*`(not `\times`). 식 안의 숫자·기호는 식과 함께 백틱(`` `dp[0][1] = 1` ``).
  - **숫자 리터럴이 "값 토큰"일 때** — 데이터(원소·문자·행렬 칸·배열에 심는 마커)가 그 값을 갖거나, 그 값과 비교하거나, 그 값으로 바꿀 때. 문자열 리터럴과 같은 취급이다: 이진 문자열·인접 행렬의 `` `0` ``·`` `1` ``, `{-1, 0, 1}` 배열의 원솟값, 배열에서 지움을 표시하는 `` `-1` ``, MEX가 걸리는 원소 `` `0` ``, 숫자열에서 세는 자릿값(`` `3` ``·`` `7` ``). 값을 계속 언급하는 문제면 백틱이 빽빽해져도 그대로 간다(문제 성격이라 정상).
  - **반대로 수량·출력은 평문** — 개수·인덱스·산술 결과(나머지·몫·합)·함수 출력(MEX 값, "예각이면 1" 같은 반환 코드값)·임계치. "없음/못 찾음/불가능"을 뜻하는 sentinel도, 데이터에 든 마커가 아니라 반환·부재 답이면 평문("-1을 반환", 못 찾으면 -1로 저장, `dist`가 0이면 미방문). 같은 `0`이라도 "그 멀티셋에 `0`이 하나는 있어야"(원소, 백틱) vs "빈 멀티셋의 MEX는 0"·"4로 나눈 나머지가 0"·"-1을 반환"(수량·출력, 평문)으로 갈린다.
  - **원소 값의 정의역·스펙 상수도 평문** — "원소가 0 이상", "공격력이 5", "값이 50보다 작은 홀수", "원소가 최대 9"처럼 데이터를 그 값과 견주는 문장 꼴이어도, 알고리즘이 그 값을 원소로 심거나 특정 원솟값을 겨냥하는 게 아니라 **입력 범위·문제 스펙을 서술**한 것이면 제약 수치와 같이 평문이다. 백틱은 그 값이 알고리즘이 직접 다루는 대상일 때만 — MEX가 걸리는 `` `0` ``, 숫자열에서 세는 `` `7` ``, 인접 행렬 칸의 `` `1` ``. ASCII 코드포인트(문자가 65~90에 놓인다)·비트 오프셋(32만큼 차이)도 인코딩 서술이라 평문. 애매하면 평문이 기본값이다.

- **수식(`$...$`) — 프로즈로 못 치는 수학 표기이거나 대수 유도일 때.**
  - 코드에 없는 표기: `\lfloor\rfloor`·`\lceil\rceil`, `\sum`·`\prod`, `\sqrt`, `\binom`, 위·아래첨자(`$2^k$`, `$x_1$`), 분수, `\log`·`\gcd`, 그리스 문자, 논리·집합 연산(`$x_1 \lor x_2$`), 비트 연산 서술 표기(`$a \oplus b$`).
  - 변수를 쓴 대수 유도는 표현 전체를 수식으로 — "총 `k` $= (n+1)/2$개"(X) → "총 $k = (n + 1) / 2$개"(O). 백틱-수식 혼용은 어색함.
  - 좌표·구간 튜플: `$(i, j)$`, `$(1, 1)$`, `$[l, r]$`(코드엔 인덱싱으로만 있고 튜플로는 없음).
  - 공식의 일부인 숫자: `$k^2$`, `$2k$`, `$10^9 + 7$`.

- **타이브레이커 — 쓴 형태가 마크업을 정한다.** 같은 연산을 코드 어법으로 쓰면 백틱(`` `n % 10` ``), 한국어로 풀면 평문("10으로 나눈 나머지"). 어느 쪽으로 쓸지는 자유. "1부터 `n`까지"의 비대칭(`1` 평문, `n` 백틱)도 이걸로 설명된다 — `1`은 값, `n`은 식별자.

- **경계.**
  - **지문이 정한 변수명이 코드와 다를 때**(BOJ 입문 문제는 지문이 `A`, `B`, `N` 대문자, 코드는 `a`, `b`, `n` 소문자인 경우가 많다) — `## 1. 아이디어` 본문은 **지문의 이름을 수식**(`$A$`, `$B$`, `$N$`)으로 쓴다(수학적 대상, 언어·코드 무관 서술). 코드 변수를 직접 가리키는 `## 3. 코드` 블록 설명에서만 코드 이름을 백틱으로 쓴다. 지문과 코드 이름이 같으면(Codeforces 대부분) 이 구분이 필요 없다.
  - 리터럴 나열에 섞인 항은 그 나열의 마크업을 따른다 — `` `zero` ``~`` `nine` ``를 `` `0` ``~`` `9` ``로 치환(양쪽 다 리터럴).
  - 한 포스트에서 수학적 대상은 수식, 그걸 다루는 코드 변수는 백틱으로 갈릴 수 있다 — 순서쌍 $(a, b)$를 코드가 루프 변수 `i`로 훑는 식. 혼용이 아니라 스코프 구분이다.

## `description`

**PS 포스트는 `description`을 쓰지 않는다** — 폐기된 필드(PS 입문 문제는 `title`이 이미 다 말해 제목 재탕뿐). 스캐폴드가 안 만들고, 옛 드래프트에 `description:` 줄이 남아 있으면 삭제한다. 사람도 `review-post`도 채우지 않고 `publish` 완료 판정에서도 빠졌다.

## `## 1. 아이디어`

- **"무엇"이 아니라 "왜"를 쓴다** (설명할 "왜"가 있는 문제라면). 코드가 어떤 연산을 하는지는 `## 3. 코드`가 이미 보여준다 — 그걸 산문으로 옮기면 중복이다. 독자(와 나중의 나)가 납득하려면 이 방법이 왜 옳은 답을 주는지, 문제의 어떤 조건이 이 접근을 가능하게/유리하게 만드는지가 있어야 한다. 코드와 문제를 요약하는 데서 멈추지 않는다. 단 통찰이랄 게 없는 트리비얼 문제는 예외 — 아래 "분량은 난이도에 비례" 참고.
- 그렇다고 부풀리지도 않는다 — 필요한 논증만 담고, 기법 자체의 교과서 설명이나 코드 줄 단위 워크스루로 늘리지 않는다(장황함도 결함).
- 서술(풀이 해설) 중심. 제약조건을 표로 따로 정리하지 않는다. 서브헤딩 없음. 지문 원문을 복붙하지 않는다(자기 말로 요약 — 저작권).
- **오프닝은 문제가 뭘 요구하는지 자기 말로 1~2문장 요약하고 시작한다.** 곧장 crux부터 던지면 어색하다 — 접근에 앞서 문제를 세팅하는 한두 문장은 아래 "금지 패턴"의 재진술 낭비가 아니다(늘어지는 게 문제지 세팅은 정상). 그 뒤 바로 crux로 넘어간다. 트리비얼 워밍업이면 이 요약 한 문장이 곧 아이디어 전체다.
- **언어 무관하게 쓴다.** 특정 언어가 어떤 함수·트릭·자료구조로 구현하는지는 아이디어에 넣지 않는다("Python 풀이는 `replace`로 ~", "Java는 `StringTokenizer`로 ~" 전부 금지 — 비교가 아니어도 한 언어 단독 언급도 안 됨). 한 언어만 접근이 눈에 띄게 다르면, 세 풀이를 아우르는 공통 알고리즘을 아이디어에 쓰고(부호 있는 항의 합처럼 추상화), 그 언어만의 구현 설명이 꼭 필요하면 `## 3. 코드`의 해당 코드 블록 아래 프로즈로 뺀다.
  - 단 **이 문제의 정석 사고방식**을 서술하는 건 "특정 언어 구현"이 아니다 — 언어 이름을 안 대고, 대부분의 언어가 그대로 그렇게 푸는 접근이면 아이디어에 써도 된다(예: "정수에서 자리를 뽑으면 낮은 자리부터 나오니 마지막에 뒤집는다" — `% 10` 루프의 자연스러운 서술). 한 언어가 라이브러리로 그 단계를 건너뛰더라도(문자열 변환 등) 그 지름길은 해당 코드 블록 프로즈에서 다루고 아이디어는 정석대로 둔다. 금지 대상은 어디까지나 언어를 지목한 서술·대조이지, 언어 중립적인 알고리즘 묘사가 우연히 한 언어의 지름길과 안 겹치는 것이 아니다.
- **대상 독자 전제**: 알고리즘/자료구조의 기본 개념(DP·이분탐색·차분 배열이 뭔지 등)은 안다고 전제하고 재설명하지 않는다. 대신 **이 문제에 특화된 추론**(왜 이 점화식이 성립하는지, 초기값·경계를 왜 그렇게 잡는지, 왜 이 기법을 이 문제에 적용할 수 있는지)은 생략 없이 풀어쓴다.
- **다중 접근**: 접근마다 그 접근을 쓰는 이유를 밝힌다 — 특히 뒤 접근은 앞 접근의 어떤 한계(복잡도·특정 입력 규모 등) 때문에 나오는지. 기법 동작 자체가 아니라 "이 문제에서 그 기법이 왜 통하는지(적용 조건)"를 쓴다.
- 제약 수치가 풀이 근거로 실질적으로 중요하면 문장 안에 자연스럽게 녹이고, 안 중요하면(사소한 워밍업 등) 생략한다.
- 알고리즘/풀이 레벨만 쓴다. 복잡도 변수가 뭘 가리키는지는 여기가 아니라 `## 2. 복잡도`에 적는다.
- 본문 수식의 코드 변수는 **소문자 그대로** — 대문자 승격은 복잡도 섹션에서만(`## 2. 복잡도` 안 `### 수식 표기 세부` 참고).
- **금지 패턴 — AI 슬롭 어투.** 타깃은 재진술 자체가 아니라 재진술로 **늘어지는 것**이다. 사람이 직접 쓴 짧고 담백한(친근해도 됨) 프로즈는 여기 안 걸린다:
  - 지문 한 줄 요약 뒤에 `~가 성립하는 이유는 ~ 때문이다` 식 정리-증명 템플릿 어투로 이어지는 것 — 논증은 하되 평범한 서술로.
  - 코드가 한 일을 순서대로 옮긴 문단(`먼저 해시맵으로 ~ 셌다`, `~로 남겼다`, 끝에 `배열 버전은 ~, 최적화 버전은 ~`) — 그건 `## 3. 코드`가 보여준다. 접근을 한 문장으로 가볍게 짚는 건 괜찮다.
  - 모든 경계·초기값·모듈러 연산을 같은 비중으로 훑는 것 — 비자명한 것 하나만 짚고 나머지는 넘어간다.
- **분량은 문제의 실제 난이도에 비례한다.** 트리비얼 워밍업은 통찰이 없으면 친근한 한 줄 재진술로 끝내도 된다(`~하면 되는 간단한 문제다` OK) — 억지로 문단으로 부풀리거나 없는 crux를 지어내지 않는다. 비자명한 문제만 문단 단위로, 문제 요약 한두 문장(위 "오프닝") 뒤 곧바로 crux(코드만 봐선 안 드러나는, 이 풀이가 옳은 이유) 하나에 집중한다 — 요약을 문단으로 늘이지 않는다.
- `review-post`가 빈 아이디어를 채울 때:
  - 채운 아이디어는 사용자가 다시 쓸 초안이다 — 완성본을 목표로 부풀리지 말고 뼈대(핵심 관찰 + 꼭 필요한 논증)만 남긴다.
  - 문체는 사용자 본인 톤에 가깝게 뽑는다(그래야 다시 쓰는 왕복이 준다): "~는데 / ~이므로 / 따라서 / 반대로 / 결국"으로 절을 이어붙인 **긴 연결 문장**으로 한 호흡에 추론을 따라가고, 문단은 최소로(보통 2문단 — 불변식 논증과 충분성 논증을 각각 한 문단으로 뭉침), 독립 테제 문장은 첫 문장 안으로 흡수하고, 알고리즘 요약은 별도 문단이 아니라 마지막 문단 끝에 "결국 ~하면 된다"로 붙인다. 바꾸는 건 문장 길이·문단 수·연결어뿐이고 내용 비트와 이 문서의 나머지 규칙은 그대로다. 참고 레퍼런스: 손대지 않은 #2148A 아이디어.
  - Claude가 겪지 않은 시행착오("처음엔 이렇게 생각했는데")를 지어내지 않는다 — 바로 최종 아이디어부터 쓴다.
  - 커뮤니티에서 실제로 쓰이는지 확인 안 된 용어를 "~라고 불린다"로 인용하지 않는다 — 확실치 않으면 검증하거나 서술적 표현으로 순화.

### SQL 전용 포스트(`## 2. 쿼리`)의 아이디어

쿼리의 모든 절이 첫 문장에서 설명됐는지를 기준으로 쓴다. 쉬운 문제인지는 기준이 아니다.

- **구조**: 첫 문장에서 조회 대상(출력 컬럼·조회 조건·정렬)을 자연어로 재진술하고 "~하는 문제다"로 끝맺는다. 쿼리에 실제로 등장하는 컬럼명·테이블명·리터럴은 백틱. 쉼표로 이어붙인 단문("~는 문제로, ~하면 된다")이 아니라 마침표로 끊은 두 문장("~다. ~다.") 구조를 쓴다.
- **두 번째 문장은 필요할 때만.** 조건이 자연어로 이미 다 드러나면(예: "3월에 태어난 여성 회원"이 `MONTH() = 3 AND GENDER = 'W'`를 커버) 한 문장으로 끝낸다.
- **자연어만으로 SQL 동작이 안 드러나면 두 번째 문장에서 그 조건을 백틱으로 직접 적는다.** 특히 NULL 처리를 빠뜨리기 쉽다: `IS NULL`/`IS NOT NULL`/`IFNULL`, `COUNT(DISTINCT)`의 NULL 미집계, `BETWEEN`의 NULL 자동 제외. "조건이 숨어 있다"처럼 무엇인지 안 밝히는 얼버무림은 금지하고 항상 리터럴 조건을 적는다.
- **두 번째 문장이 실제 통찰을 담을 수 있으면 그렇게 쓴다**(`GROUP BY` 뒤 행 순서가 보장되지 않아 `ORDER BY`가 필요한 이유 등). 조건 명명 수준이면 부연 없이 조건만 짧게 적는다.
- **금지**: 첫 문장을 다른 말로 반복하는 동어반복("구하는 문제다" 뒤에 "이 값을 세면 된다"), `COUNT(*)` 같은 함수명을 문장 중간에 억지로 욱여넣기.
- **작성 후 점검**: `WHERE`/`HAVING`/`GROUP BY`/`ORDER BY` 절을 하나씩 짚으며 프로즈의 어디에 대응되는지 확인한다. NULL 관련 절을 먼저 본다.

## 다중 접근 — 접근 이름

드래프트에 `### 풀이` 헤딩이 2개 이상이면 각 접근에 이름을 붙인다(`ps` 스캐폴드는 번호만 만들고 이름은 비워 둔다).

- **코드 섹션 헤딩**: `### 풀이 N: 이름 [Java][C++]...` — 번호 + 콜론 + 이름, 뒤에 언어 브라켓. 첫 접근도 `### 풀이 1: 이름`으로 번호를 붙인다.
- **`## 2. 복잡도` 표 "접근" 열**: 접두어(`풀이 N:`) 없이 이름만 (`직접 갱신`, `차분 배열`). 표 아래 변수 프로즈에서 특정 접근을 가리킬 때도 이름으로 (`차분 배열 풀이의 diff가 ...`).
- 이름은 **"이 풀이를 한마디로 뭐라 부르나"**에 답한다 — 풀이의 핵심 아이디어(알고리즘·자료구조·수학 성질) 하나를 가리킨다. 아래 순서로 가장 위 tier의 이름을 고른다. 각 tier의 목록은 지금까지 쓴 이름의 기록이고, 새 이름이 필요하면 아래 원칙으로 지은 뒤 목록에 추가한다:
  1. **명명된 알고리즘·자료구조·공식을 쓰면 그 이름.** `review-code/tags.yaml` 어휘를 재사용하되 한글 관용명이 있으면 한글(`BFS`, `DFS`, `유니온 파인드`, `에라토스테네스의 체`, `시행 나눗셈`, `차분 배열`, `누적 합`, `이분 탐색`, `스택`, `해시맵`, `해시셋`, `등차수열 합 공식`, `플로이드 사이클 탐지`, `버킷 정렬`, `브라이언 커니핸 알고리즘`) — 풀이 이름과 태그가 어긋나지 않게.
  2. **명명된 기법이 없으면 접근 전략** — `완전 탐색`(제약 안 후보 전부 시도), `제곱근까지 탐색`(√n 경계), `합 공식`(합을 반복 없이 식으로 — 식이 명명돼 있으면 1로, 예 `등차수열 합 공식`), `표준 라이브러리`(직접 구현을 언어 기능으로 대체).
  3. **전략도 애매하고 구현 자체가 정체성이면 그 구현** — `반복 합산`, `직접 갱신`(쿼리마다 구간을 직접 갱신), `이전 값 비교`, `깊이 카운터`(스택을 정수 하나로), `방문 체크`, `카운팅 배열`/`카운팅 맵`, `빈도순 정렬`, `비트 시프트`, `비트 토글`(`c ^ 32`), `XOR 상쇄`(같은 수끼리 XOR로 지움), `ASCII 오프셋`.
- **같은 이름은 같은 기법만 가리킨다.** 같은 구분이 여러 포스트에 나오면 같은 단어를 쓰고(위 목록 재사용, 같은 기법의 호칭도 통일 — `브라이언 커니핸 알고리즘`/`브라이언 커니핸 DP`), 반대로 다른 기법에 같은 이름을 붙이지 않는다(`XOR 상쇄`와 `비트 토글`을 둘 다 "비트 XOR"이라 부르면 구분이 사라진다). "naive 먼저 / 최적화 나중" 쌍이면 naive는 실제 동작에 맞는 2·3(`직접 갱신`/`반복 합산`/`완전 탐색`), 최적화는 1·2의 이름.
- 한 포스트에 같은 tier 이름이 겹치면(표준 기능 풀이 2개 등) 무엇에 적용하는지로 구분(`문자별 표준 함수` / `swapcase 메서드`). 한 접근이 여러 tier에 걸치면(DP인데 포인트가 공간 최적화, 정렬 계열인데 방식이 다름) 겹치는 축을 이름에(`배열 DP` / `공간 최적화 DP`, `빈도순 정렬` / `버킷 정렬`).
- 언어마다 구현이 갈리면 대표 구현(Java·C++) 기준으로 짓고 자료구조 세부에 이름을 묶지 않는다(`방문 체크` — Java·C++는 배열, Python은 `set`). 자료구조 자체가 갈림길인 접근(`카운팅 배열` / `카운팅 맵`)만 예외.
- 접근이 하나뿐이면 `### 풀이 [langs]` 그대로 두고 이름을 붙이지 않는다.
- `sync`의 헤딩 매칭은 `### 풀이 N` 뒤의 접미어(`: 이름`, 언어 브라켓)를 무시하므로 이름을 붙여도 코드 동기화에 영향 없다.

## `## 2. 복잡도` — 셀 값과 변수 설명

복잡도는 알고리즘이 실제로 필요로 하는 비용을 합리적으로 기록한 값이다. 아래 원칙으로 값을 정하고, 표기·서술은 예시 표와 고정 포맷을 그대로 따라 누가 채우든 같은 표가 나오게 한다. 표의 목적은 같은 문제의 풀이끼리 비용을 비교하는 것이라 언어나 입출력 구현이 값을 바꾸지 않아야 한다. 원칙으로 갈리지 않으면 "처음 보는 사람이 이 값을 적절하다고 받아들이는가"로 정한다. 이미 적힌 값은 근거가 아니다. 원칙으로 새로 유도한다.

### 판단 원칙

1. **기준**: 입력 파라미터의 함수로, 최악 기준으로 쓴다. 해시 연산과 동적 배열 추가는 $O(1)$로 보고, 표준 라이브러리는 널리 알려진 복잡도(`sort()`는 $O(N \log N)$)로 본다.
2. **시간**은 코드가 수행하는 연산 횟수다. 읽기·쓰기 호출 한 번은 $O(1)$이고 줄·토큰의 길이는 세지 않는다(호출 횟수는 센다: `n`줄을 읽으면 $O(N)$). 읽은 값을 코드가 순회·복사·정렬·탐색하면 그 비용을 센다.
3. **공간**은 알고리즘이 필요로 하는 자료구조의 크기다.
   - 센다: 읽어서 저장한 컨테이너, 직접 만든 보조 배열·리스트·해시, 코드에 쓴 재귀의 최대 깊이, 함수형 저지에서 새로 만들어 반환하는 값.
   - 안 센다: 읽고 버리는 변수, 호출자가 넘겨준 인자(제자리 수정해 반환하면 $O(1)$), 표준 라이브러리 내부 버퍼·재귀 스택, 언어가 순회를 편하게 하려고 만드는 임시 사본(`for (char c : s.toCharArray())`, `for p in prices[1:]`), 한 번 쓰고 버리는 이름 없는 임시물(`s.toLowerCase()`, `str(n)`, `s.split()`), **출력 버퍼**.
   - 출력 버퍼는 타입이 아니라 용도로 정한다. 답을 출력하려고 모아 두기만 하는 컨테이너는 안 세고, 알고리즘이 다시 읽는 값(dp 표, 정렬 대상, 방문 배열)은 센다. "`StringBuilder`에 모으므로 …" 같은 주석도 쓰지 않는다.
   - 함수형 저지는 입력 인자를 안 세고 반환값을 세며, stdin 저지는 읽어 저장한 입력을 세고 출력을 안 센다. 의도된 비대칭이다.
4. **상수**는 크기·반복 횟수가 코드나 타입 정의로 입력과 무관하게 고정된 경우만 $O(1)$이다(알파벳 26칸 배열, 상수 제수, 개수가 고정된 입력). 입력의 값이나 길이와 관계가 있으면 문제 제약이 상한을 줘도 변수로 둔다(`n ≤ 100`, `T ≤ 10`, 정수의 비트 길이만큼 도는 루프, `gcd`의 $O(\log \min(P, Q))$). 입력 크기 최대치로 잡은 정적 배열(`dp[100001]`)은 $N$ 비례, 값의 범위로 정한 배열은 $O(K)$다. 알파벳이 유계여도 입력 길이가 그 언저리면 $O(1)$로 낮추지 않는다.
5. **변수**는 코드가 실제로 순회·복사·정렬·재귀하는 대상의 크기다. 독립적으로 커지면 별도 문자로 두고, 일부만 쓰면 그 부분 크기가 변수다. 관용 문자를 쓴다(격자 행 $N$·열 $M$, 그래프 정점 $N$·간선 $E$). 지문의 주 스칼라 `n`이 $N$ 우선권을 가지며 다른 대상이 $N$을 차지했으면 그 대상을 $M$·$L$ 등으로 옮긴다. 스칼라 하나에 반복 적용되는 알고리즘은 그 스칼라를 변수로 쓴다(`gcd(p, q)` → $P$·$Q$). 반복 횟수 상한이 입력의 함수로 알려지지 않으면 반복 횟수 $K$를 변수로 둔다.
6. **테스트 케이스 루프**(`t` 입력, 종료 줄·EOF까지 읽는 루프)는 케이스당이 아니라 루프도 복잡도에 넣는다. 변수 `T`는 처리하는 케이스 수이고 종료 줄은 세지 않으며 작아도 상수로 접지 않는다.
   - 케이스 내부가 상수면 $O(T)$.
   - 케이스 내부가 크기에 비례하고 지문이 모든 케이스 크기의 **총합 상한**을 주면 변수를 총합으로 정의하고 $O(T)$를 따로 더하지 않는다.
   - 총합 상한이 없고 케이스당 최댓값만 있으면 케이스당 최댓값 변수에 `T`를 곱한다: $O(T \times N^2 \log M)$.
7. **구현 차이**: 언어 구현이나 내부 최적화로 값이 갈리면 표에는 다수파·기본형 값을 넣고 소수파는 변수 설명에 병기한다(입출력 방식 차이는 제외, 병기 포맷은 아래).

### 변수 설명 프로즈 포맷 (표 아래)

**아래는 예시가 아니라 고정 포맷이다.**

- 셀이 $O(1)$뿐이면 보통 프로즈 줄을 쓰지 않는다.
  - **예외**: 알고리즘만 보면 로그·선형으로 읽히는데 상수 인자·상수 크기라 실제로는 상수여서 의문을 부를 만하면 왜 그런지 한 줄로 짚는다. 예: `(GCD를 유클리드 호제법으로 구하지만 제수가 상수 6이라, 첫 나눗셈 뒤 두 인자가 모두 6 이하로 줄어 `n` 크기와 무관하게 상수 번의 스텝에 끝난다)`.
- 그 외에는 표 바로 아래 **한 줄**, **괄호로 감싼 명사형 개조식**: `($N$ = <가리키는 대상>)`. 불릿(`- `) 금지. 종결은 명사구나 복잡도항($O(\cdot)$)으로 하고 `~이다`/`~한다`/`~된다` 같은 서술 어미로 끝내지 않는다(부연도 마찬가지). 상수성·수렴 근거를 푸는 설명 주석처럼 명사형으로 옮기면 뜻이 뭉개지는 경우만 서술문으로 둔다(위 $O(1)$ 예외).
- **대상 표기는 아래 표대로 고정한다.** 같은 대상을 다르게 풀어 쓰지 않는다(`수의 개수 `n``, `숫자 카드의 개수 `n``, `입력값 `t``은 쓰지 않는다).

  | 대상                                          | 표기                                                                                                                                                                                                            |
  | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 입력 스칼라(`n`, `m`)                         | ``입력값 `n` ``                                                                                                                                                                                                 |
  | 배열·문자열의 길이                            | `` `s`의 길이 ``                                                                                                                                                                                                |
  | 테스트 케이스 수                              | `테스트 케이스 수` (종료 줄까지 읽으면 `종료 줄을 제외한 테스트 케이스 수`). `` `t` ``를 병기하지 않는다                                                                                                        |
  | 모든 케이스의 크기 총합                       | `모든 테스트 케이스에 걸친 <대상>의 총합`                                                                                                                                                                       |
  | 케이스당 최댓값                               | `케이스당 <대상>의 최댓값`                                                                                                                                                                                      |
  | 값의 범위                                     | `값의 범위`. 식이 필요하면 `값의 범위 $2 \times 10^7 + 1$`                                                                                                                                                      |
  | 격자·그래프(대응하는 입력 스칼라가 없을 때만) | `` `board`의 행 수 ``, `정점 수`, `간선 수`. 입력 스칼라(`n`)가 있으면 위 첫 행대로 ``입력값 `n` ``                                                                                                             |
  | 그 밖의 파생값                                | **그 식을 그대로**. 코드 변수 식이면 백틱(`` `num2 - num1 + 1` ``), 복잡도 변수 식이면 `$...$`(`$N / K$`). 식만으로 불투명할 때만 뒤에 2~4단어 주석. 닫힌 식이 없고 합으로만 표현되면 $\sum$ 표기나 서술로 둔다 |

- 변수 2개 이상: 쉼표로 나열하고 필요하면 마침표로 끊어 부연 — `($N$ = `s`의 길이, $M$ = `m`. 결과 문자열의 길이 $N / M$)`. 부연도 명사형으로 끝내고 닫는 `)` 뒤에 마침표를 붙이지 않는다.
- **구현 차이 병기**(판단 원칙 7): 변수 설명 괄호 안에서 마침표 뒤에 `<언어>는 <이유>라 시간|공간 $O(\cdot)$` 꼴로 붙인다. 소수파 언어를 앞세우고 명사형·복잡도항으로 끝낸다 — `($N$ = `nums`의 길이. Python은 `most_common(k)`가 힙 기반이라 시간 $O(N \log K)$)`, `($N$ = `digits`의 길이. Python은 새 리스트를 만들어 반환해 공간 $O(N)$)`. 변수 설명 줄이 없던 $O(1)$ 표에도 병기가 필요하면 이 꼴로 새 줄을 둔다.

### 수식 표기 세부 (이 섹션 안 표기 전체에 적용, `## 1. 아이디어` 수식도 항목별로 일부 적용)

- **변수 대문자 관용($N$, $M$)은 복잡도 표와 그 아래 변수 설명에만** 적용한다(지문이 정한 변수명이 코드와 다르면 위 `## 평문 · 백틱 · 수식`의 "경계" 첫 항목이 우선한다). 코드에 소문자 파라미터로 등장해도 거기서는 대문자로 승격(`m` → `$M$`)하고 `($N$ = 입력값 `m`)`으로 코드 변수와 연결한다.
  - **`## 1. 아이디어` 본문 수식은 코드 변수명을 소문자 그대로** 쓴다: `solution(int n)`이면 `$\gcd(n, 6)$`, `$k = \lfloor n / 2 \rfloor$`. 서술 맥락이라 대문자 승격이 어색하다. 연산자 공백·`{,}` 콤마·곱셈 결합 등 나머지 표기 규칙은 아이디어 수식에도 그대로 적용한다.
  - 소문자 규칙은 대응하는 스칼라 파라미터가 있을 때다. 크기가 배열 길이(`len(names)`)로만 존재하면 아이디어 본문 수식도 표와 같은 대문자 `$N$`을 쓴다(맞출 소문자 리터럴이 없고, 아래 `($N$ = ...)` 정의와 같은 양). 기호가 거추장스러운 워밍업이면 서술로 풀어도 된다.
- math mode 안 코드 식별자는 **1글자면 맨몸**(`$\log_{10} n$`, `$\gcd(n, 6)$`), **2글자 이상이면 `\text{}`로 감싼다**(`$\log_{10}(\text{order})$`, `$\text{numer1} \times \text{denom2}$`). 맨몸 `order`는 `o·r·d·e·r` 문자곱으로 렌더된다. 함수 인자면 괄호도 함께. 아이디어 본문 수식에도 적용.
- 이항 연산자 `+` `-` `/`(나눗셈)는 양쪽에 공백: `$N / 2$`(not `$N/2$`), `$(i - 1, j)$`(not `$(i-1, j)$`). 지수(`n^2`)·아래첨자처럼 항상 붙여 쓰는 표기는 예외.
- 분수는 `\dfrac{}{}`로 쌓을지 인라인 슬래시로 풀지 더 읽기 좋은 쪽을 고른다. 분자·분모가 둘 다 단일 항이면 슬래시(`$n / \gcd(n, 6)$`, `$N / 2$`), 하나가 복잡해 경계가 헷갈리면 `\dfrac`(`$\dfrac{n \times 6}{\gcd(n, 6)}$`). 이미 복잡한 수식에 분수를 또 쌓으면 슬래시가 나을 수 있다. **`\frac`은 쓰지 않는다.** 인라인에서 쓸 거면 디스플레이 크기로 렌더되는 `\dfrac`.
- 1,000 이상 숫자는 `{,}`로 콤마: `$10{,}000$`(not `$10000$`). 그냥 `,`만 쓰면 KaTeX가 콤마 뒤에 여백을 넣어 어색하다. 연도처럼 원래 콤마를 안 쓰는 표기는 예외.
- 곱셈 결합:

  | 형태                 | 표기                               | 예                               |
  | -------------------- | ---------------------------------- | -------------------------------- |
  | 맨몸 변수 하나 × log | 붙여씀                             | `$O(N \log N)$`, `$O(N \log M)$` |
  | 맨몸 변수 두 개 곱   | 사이에 `\times`                    | `$O(N \times M)$`                |
  | 변수곱 + log         | 곱에만 `\times`, log 앞뒤는 붙여씀 | `$O(N \times M \log K)$`         |

  `\cdot`나 그냥 붙여쓰기(`$O(NM)$`)는 쓰지 않는다.

- 로그 밑은 생략한다(`$O(N \log N)$`, `$O(\log \log N)$`). 밑이 값을 실제로 좌우할 때만 표시하며, 특히 **10진 자릿수**는 `$\log_{10}$`. `$O(\cdot)$` 안에는 명시적 밑을 쓰지 않는다: `$O(\log_{10} N)$`(X) → `$O(\log N)$`, 또는 O를 빼고 `$\approx \log_{10} N$`.
- 자릿수를 복잡도 인자로 쓰면 표에 `$\log$`를 박지 않고 문자 `$D$`로 두고, 변수 설명에서 `($D$ = `n`의 자릿수 $\approx \log_{10} n$)`으로 푼다.

## `## 3. 코드` — 블록 설명 프로즈

- 언어별로 특징적으로 설명할 게 있으면 `### 풀이 N` 헤딩 바로 아래(그 접근의 전 언어 공통) 또는 각 코드 블록 바로 아래(그 언어 전용)에 프로즈를 넣어도 된다. 위치로 스코프를 구분한다 — **공통 스코프(아이디어·헤딩 아래)는 언어 중립**(`## 1. 아이디어`의 "언어 무관하게 쓴다"와 동일), **그 언어 전용 블록에서만** 그 언어 얘기를 한다. 전용 블록에서 상대적 어투("표준에 정수 GCD가 없어 직접 구현했다", "C++17부터 `std::gcd` 사용 가능")는 괜찮지만, 다른 언어를 이름 대며 나란히 대조하는 것("Java와 달리 C++는 ~", "다른 언어는 한 줄인데")은 피한다 — 자기 언어만 서술. 이미 사람이 써둔 설명은 그대로 두고 덮어쓰지 않는다.
- **필수가 아니다** — 대부분의 포스트는 이 프로즈가 없다. 코드가 스스로 설명되면 넣지 않는다.
- **표준 라이브러리 심볼 표기**:
  - C++ 표준 라이브러리 **자유 함수·타입**은 `std::` 접두어를 붙인다(`std::rotate`, `std::reverse`, `std::gcd`, `std::swap`, `std::string`) — 코드가 `using namespace std;`라 접두어 없이 등장해도. "코드에 그 형태 그대로" 백틱 규칙(위 `## 평문 · 백틱 · 수식`)의 의도적 예외로, 표준 심볼임을 드러내고 검색성을 높이려는 것. **멤버 함수**는 접두어 없이 호출된 형태대로(`my_string.find()` → `find`).
  - Python 모듈 함수는 코드의 실제 import 스타일을 따른다: `import math` → `math.gcd`, `from itertools import groupby` → `groupby`(맨이름). 메서드는 호출된 형태대로 — 클래스 호출이면 `str.maketrans`/`dict.fromkeys`, 인스턴스면 맨이름(`swapcase`), 관용형은 `"".join`.
  - Java 메서드도 호출 형태대로: `Arrays.sort`(클래스 호출), 인스턴스 메서드는 맨이름(`toCharArray`).
