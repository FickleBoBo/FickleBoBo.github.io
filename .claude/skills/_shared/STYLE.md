# PS 포스트 프로즈·표기 컨벤션

`ps`가 만든 스캐폴드의 프로즈 필드(`## 1. 아이디어`, `## 2. 코드`의 블록 설명)를 **사용자나 `write-post`가 쓸 때** 따르고 `review-post`가 평가할 때 기준으로 삼는 단일 규칙. `ps/SKILL.md`와 `post-reviewer` 에이전트(`.claude/agents/post-reviewer.md`)가 이 파일을 정본으로 참조한다 — 같은 규칙을 각 문서에 다시 적지 않는다.

기계적으로 판정되는 규칙은 `_shared/lint_post.py`가 검사한다. 규칙을 바꾸면 그 스크립트의 같은 항목도 같이 바꾼다. 이슈는 두 종류다.

- **구조**(`publish`가 막는다): front matter 필수 키, 제목 형식·언어 브라켓 순서, 섹션 헤딩(`## 1. 아이디어` → `## 2. 코드`·`## 2. 쿼리`, 구형 `## 2. 복잡도`·`## 3. 코드` 금지, 코드 뒤 선택 섹션 `## 3. 회고`는 허용), `### 풀이` 헤딩 형식, 풀이 헤딩·제목 브라켓과 코드 블록 언어의 일치, 코드 펜스 짝, 이미지(파일 존재·`media_subpath`·파일명 접미사와 `.light`/`.dark` 클래스 일치·라이트/다크 쌍과 같은 alt), 태그 형식(어휘·조상·중복·순서·`sql`·단일 접근 포스트의 `warm up` 병기).
- **표기**(보고만 하고 막지 않는다): 합니다체·해요체, em-dash, 맞춤법 고정 패턴(`안되`·`필요없`·`둘다`·`하는게`류 의존명사), 수식 뒤 조사·단위 띄어쓰기, 수식 표기(`*`·`\{ \}`·`\|`·`\\`·`\frac`·천 단위 콤마·이항 연산자 공백), 용어(`오버플로우`·`언더플로우`·`페널티`).

## 어투

- 다체(평서체 — "~이다", "~된다")로 통일. 합니다체·해요체 금지.
- **em-dash(`—`)는 쓰지 않는다.** "특정 원소만 더 굴릴 수 없다 — 모든 원소가 ..."처럼 이을 내용은 마침표로 끊어 다음 문장으로 쓴다. (두 프로즈 자리 전부에 적용. 표·머리말의 대시는 무관.)

## 맞춤법 · 띄어쓰기

사람이 쓴 프로즈를 검토할 때 매번 기본으로 스캔하는 체크리스트(두 프로즈 자리 모두 + 대회 후기 총평 등). 한글 맞춤법이 흔들리는 자리만 모았다.

- **의존명사(것/게/거/걸)는 예외 없이 띄운다.** 관형사형 어미(-는/-(으)ㄴ/-(으)ㄹ) 뒤의 "것" 축약형은 항상 띄어쓴다: `하는게`→`하는 게`, `될거`→`될 거`, `본거`→`본 거`, `아닌거`→`아닌 거`. 보조 용언 붙여쓰기(`할만하다`)가 허용돼도 뒤의 "거"는 독립 의존명사라 또 띄운다(`할만했던 거`).
- **`안 되다`는 띄운다.** `안되다`는 "잘 안되다/곤란하다"라는 별도 뜻이고, 단순 부정("되지 않다")은 띄어쓴다: `해결이 안 됐고`, `AC가 안 돼서`.
- **`필요 없다`는 띄운다.** `필요없다`는 표제어가 아니다.
- **`못 + 동사`는 띄운다.** `못 봤다`(보지 못했다)는 띄우고, 별도 단어 `못하다`(잘하지 못함)만 붙인다.
- **`둘 다`는 항상 띄운다.**
- **붙여쓰는 예외(반대 방향)**: `쓸데없다`(붙임), `부분집합`(수학 용어, 붙임).
- **조사 정확성.** 문장을 고쳐 쓰다 조사가 어긋나는 경우가 실제로 나온다. `배열에 내림차순인지`(오류, "에"는 위치 조사) → `배열이 내림차순인지`.
- **수식(`$...$`) 뒤 조사·단위는 붙인다.** `$N$ 이`→`$N$이`, `$A$, $B$ 의`→`$B$의`, `$N$ 단`→`$N$단`. 평문 숫자 뒤 조사와 같은 원리(`10으로`)이고, 공백이 끼면 조사가 따로 떨어져 읽힌다.
- **어휘 표기**: `페널티`(not 패널티), `뭉텅이`(not 뭉탱이, 비표준어), `오버플로우`·`언더플로우`(not 오버플로·언더플로).

## 평문 · 백틱 · 수식(`$...$`)

값·수량·식을 프로즈에 쓸 때 셋 중 하나를 고른다. **`## 1. 아이디어`·`## 2. 코드` 블록 설명에 동일하게 적용**되는 규칙이다. **기본값은 평문** — 한국어 서술로 풀 수 있으면 마크업하지 않는다("2씩 증가", "7로 나눈 몫", "-1을 반환", "인덱스 0, 5, 10", "1부터 $n$까지"에서 1). 아래 두 트리거에 걸릴 때만 마크업한다.

섹션별로 이 규칙 위에 얹히는 것: **코드 블록 설명**에서 C++ 표준 자유 함수는 `std::` 접두어를 붙인다(아래 "`## 2. 코드` — 블록 설명 프로즈" 절, 백틱 규칙의 의도적 예외).

- **백틱 — 코드의 토큰을 코드로서 가리킬 때.**
  - 코드에 그 형태로 있는 식별자·함수명(`array`, `solution`, `dp`), 문자·문자열 리터럴(`"Z"`, `"EMPTY"`).
  - 코드 어법으로 쓴 식 하나를 통째로 — 배열·테이블 인덱싱, 점화식 포함: `` `arr[i]` ``, `` `n % 10` ``, `` `dp[i][j] = max(dp[i - 1][j], dp[i][j - 1]) + cost` ``. 어법 유지: `max`(not `\max`), `*`(not `\times`). 식 안의 숫자·기호는 식과 함께 백틱(`` `dp[0][1] = 1` ``).
  - **데이터가 갖는 값(값 토큰)은 백틱.** 원소·문자·칸·마커가 그 값이거나, 그 값과 비교하거나, 그 값으로 바꿀 때다. 문자열 리터럴과 같은 취급이다: 이진 문자열·인접 행렬의 `` `0` ``·`` `1` ``, 배열에서 지움을 표시하는 `` `-1` ``, MEX가 걸리는 원소 `` `0` ``, 숫자열에서 세는 자릿값 `` `7` ``.
  - **수량·출력·스펙 수치는 평문.** 개수·인덱스·산술 결과(나머지·몫·합)·반환값("-1을 반환", "예각이면 1")·임계치·입력 범위("원소가 0 이상", "공격력이 5")다. 같은 `0`이라도 "멀티셋에 `0`이 하나는 있어야"(원소, 백틱)와 "4로 나눈 나머지가 0"(수량, 평문)으로 갈린다. 알고리즘이 그 값을 직접 다루는 대상인지로 가르고, 애매하면 평문이다.

- **수식(`$...$`) — 프로즈로 못 치는 수학 표기이거나 대수 유도일 때.**
  - 코드에 없는 표기: `\lfloor\rfloor`·`\lceil\rceil`, `\sum`·`\prod`, `\sqrt`, `\binom`, 위·아래첨자(`$2^k$`, `$x_1$`), 분수, `\log`·`\gcd`, 그리스 문자, 논리·집합 연산(`$x_1 \lor x_2$`), 비트 연산 서술 표기(`$a \oplus b$`).
  - 변수를 쓴 대수 유도는 표현 전체를 수식으로 — "총 `k` $= (n+1)/2$개"(X) → "총 $k = (n + 1) / 2$개"(O). 백틱-수식 혼용은 어색함.
  - 좌표·구간 튜플: `$(i, j)$`, `$(1, 1)$`, `$[l, r]$`(코드엔 인덱싱으로만 있고 튜플로는 없음).
  - 공식의 일부인 숫자: `$k^2$`, `$2k$`, `$10^9 + 7$`.

- **타이브레이커 — 쓴 형태가 마크업을 정한다.** 같은 연산을 코드 어법으로 쓰면 백틱(`` `n % 10` ``), 한국어로 풀면 평문("10으로 나눈 나머지"). 어느 쪽으로 쓸지는 자유이되 한 포스트 안에서 일관되게.

- **경계.**
  - **변수 하나를 가리킬 때**: `## 1. 아이디어`에서는 수식(`$n$`)으로 쓴다(수학적 대상, 언어·코드 무관 서술). 코드 변수를 직접 가리키는 `## 2. 코드` 블록 설명에서는 백틱(`` `n` ``)이다.
  - **지문이 정한 변수명이 코드와 다를 때**(BOJ 입문 문제는 지문이 `A`, `B`, `N` 대문자, 코드는 `a`, `b`, `n` 소문자인 경우가 많다) — 아이디어 본문은 **지문의 이름**(`$A$`, `$B$`, `$N$`)을 쓰고, 코드 블록 설명에서만 코드 이름(`` `a` ``, `` `b` ``, `` `n` ``)을 쓴다.
  - **지문에 없는 기호**(복잡도에 쓰는 $n$ 등, 코드에 있는 변수여도 마찬가지)는 설명에 필요하면 쓸 수 있지만, 지문에 있는 값처럼 쓰지 않는다. 첫 사용에서 "배열의 길이를 $n$이라 하면"처럼 우리가 붙인 기호임을 밝혀 정의한다("길이가 $n$인 배열"은 지문이 그렇게 준 것처럼 읽힌다).
  - 리터럴 나열에 섞인 항은 그 나열의 마크업을 따른다 — `` `zero` ``~`` `nine` ``를 `` `0` ``~`` `9` ``로 치환(양쪽 다 리터럴).
  - 한 포스트에서 수학적 대상은 수식, 그걸 다루는 코드 변수는 백틱으로 갈릴 수 있다 — 순서쌍 $(a, b)$를 코드가 루프 변수 `i`로 훑는 식. 혼용이 아니라 스코프 구분이다.

## 문장의 목적

프로즈의 모든 문장·설명은 독자의 어느 질문에 답하는지로 존재 이유를 갖는다. 어느 질문에도 답하지 못하면 뺀다. 역할은 아래와 같고, `write-post`가 쓸 때와 `review-post`가 평가할 때 같은 어휘를 쓴다. `없음`은 지적이 아니라 뺄 후보다.

- **아이디어 문장**: `왜 옳은가`(핵심 관찰, 이 문제에 특화된 추론) / `놓치기 쉬운 조건`(성립 조건, 경계, 깨지는 경우, 제약이 접근을 고르는 근거) / `맥락`(문제 요약, 이전 문제와의 관계, 접근 도입 이유).
- **코드 블록 설명**: `함정`(모르면 틀리거나 손해 보는 것, 일견 버그로 보이는 부분의 해명 포함) / `지름길`(알면 줄어드는 내장 기능·트릭).
- **회고 문장**: `사건`(구체적 실수·오답 원인·버린 접근).
- `없음`: 코드가 한 일을 순서대로 옮긴 문장, 기본 개념 재설명, 앞 문장의 되풀이, 호출을 말로 옮긴 설명처럼 어느 질문에도 답하지 못하는 것.

## `## 1. 아이디어`

**목적: 독자가 이 풀이가 왜 옳은지 납득하고, 비슷한 문제를 만났을 때 같은 접근을 떠올릴 수 있어야 한다.** 이 글만 읽고 풀이를 재구성할 수 있어야 한다. 서술(풀이 해설) 중심이고 서브헤딩은 두지 않는다.

### 쓰는 것

- **핵심 관찰(필수).** 코드가 어떤 연산을 하는지가 아니라 이 방법이 왜 옳은 답을 주는지, 문제의 어떤 조건이 이 접근을 가능하게·유리하게 만드는지를 쓴다. 이 문제에 특화된 추론(왜 이 점화식이 성립하는지, 초기값·경계를 왜 그렇게 잡는지, 왜 이 기법을 적용할 수 있는지)은 생략 없이 풀어쓴다. 코드와 문제를 요약하는 데서 멈추지 않는다.
- **곁들이는 것.** 문제의 어떤 조건·형태가 이 접근을 가리키는지(떠올리는 단서), 접근이 성립하는 조건과 깨지는 경우·변형은 원문·코드로 근거가 확인될 때만 쓴다. 항목으로 나누지 않고 문단에 녹인다.
- **오프닝은 문제가 요구하는 것을 자기 말로 1~2문장 요약하고, 바로 핵심 관찰로 넘어간다.** 지문 원문을 복붙하지 않는다(저작권).
- **다중 접근**: 접근마다 그 접근을 쓰는 이유를 밝힌다 — 특히 뒤 접근은 앞 접근의 어떤 한계(복잡도·특정 입력 규모 등) 때문에 나오는지. 기법 동작 자체가 아니라 "이 문제에서 그 기법이 왜 통하는지(적용 조건)"를 쓴다.
- **Follow-up은 별도 문단으로 잇는다.** 지문에 Follow-up이 있고 그 때문에 다중 접근을 두었다면(LeetCode에 흔하다), 첫 문단은 문제 요약과 기본 접근을 쓰고 둘째 문단을 "지문의 Follow-up은 …"으로 시작해 뒤 접근이 왜 나오는지 잇는다. 표기는 `Follow-up`(대문자 F, 하이픈, 발행본 Two Sum과 같음)이고 "추가 질문"으로 풀어 쓰지 않는다. Follow-up에 맞춘 풀이가 포스트에 있으면 이 문단에서 어느 풀이가 그것인지 밝힌다. 풀이에 없는 방법을 Follow-up의 정답이라고 단정하지는 않는다(예: 여러 번 호출 최적화에 대해 "호출 한 번의 비용을 줄이는 방향"이라고만 쓴다).
- **같은 플랫폼의 확실한 시리즈는 앞 문제로 링크한다.** 앞 문제의 조건·아이디어를 이어받거나 넓히는 번호 시리즈(`(1)`→`(2)`, 주사위 게임 1→2→3, House Robber→II)만 해당하고, 제목 번호만 같은 묶음·번호 없는 짝·다른 플랫폼의 같은 문제는 제외한다. 나중 문제의 아이디어 첫 문장에서 바로 앞 문제로만 걸고, 형식은 `[[Platform] #번호 - 제목](/posts/{slug}/)`(제목에서 언어 브래킷만 뺀 것)이며 문장은 포스트마다 다르게 쓴다("~과 달리", "~과 같은 틀이지만" 등). 링크는 보충이므로 변환 규칙·조건처럼 풀이에 필요한 내용은 링크 없이 본문에 직접 쓰고, 앞 문제를 먼저 발행한다. 이전 문제와의 관계는 사용자가 알려 주거나 발행 포스트로 확인될 때만 쓴다.

### 안 쓰는 것

- 코드가 한 일을 순서대로 옮긴 문장(코드 줄 단위 워크스루, `먼저 해시맵으로 ~ 셌다`). `## 2. 코드`가 이미 보여준다.
- 알고리즘·자료구조의 기본 개념 재설명(DP·이분탐색·차분 배열이 뭔지 등). 장황함도 결함이다.
- 풀이 레벨이 아닌 것. 제약 수치와 복잡도는 방법을 고르거나 버리는 근거일 때만 그 자리에 자연스럽게 녹이고(`$O(N \log N)$이라 $N \le 10^5$에서 통과한다), 근거가 아니면 쓰지 않는다. 복잡도 섹션과 제약조건 표는 두지 않는다. 지문이 정한 "없을 때 반환값"(`-1`, `"EMPTY"`)도 쓰지 않는다.
- **언어 특화 서술.** 특정 언어의 함수·트릭·자료구조를 지목한 서술이나 언어 간 대조는 넣지 않는다("Python은 `replace`로 ~", "Java는 `StringTokenizer`로 ~"). 어느 언어든 그대로 취하는 정석 사고방식은 써도 된다("정수에서 자리를 뽑으면 낮은 자리부터 나오니 마지막에 뒤집는다"). 한 언어만 라이브러리로 단계를 건너뛰는 지름길이나 함정은 해당 코드 블록 아래 설명으로 뺀다(`## 2. 코드` 절). 다만 접근의 알고리즘 구조 자체가 언어마다 다르면(한 언어는 정렬된 다중집합, 다른 언어는 힙 두 개와 지연 삭제처럼) 그 구조는 언어 이름 없이 아이디어에 쓰고, 언어 이름과 라이브러리 심볼만 블록 설명에 둔다.
- **AI 슬롭 어투.** 사람이 직접 쓴 짧고 담백한 프로즈는 해당 없다.
  - 지문 한 줄 요약 뒤에 `~가 성립하는 이유는 ~ 때문이다` 식 정리-증명 템플릿으로 이어지는 것.
  - 모든 경계·초기값·모듈러 연산을 같은 비중으로 훑는 것. 비자명한 것 하나만 짚는다.
- Claude가 겪지 않은 시행착오("처음엔 이렇게 생각했는데")와 확인 안 된 관용 표현("~라고 불린다"). 바로 최종 아이디어부터 쓰고, 용어가 확실치 않으면 검증하거나 서술적 표현으로 쓴다.

### 형식

- **시제는 현재형이다.** 아이디어는 왜 옳은지 설명하는 논증이다. 선택을 말하는 과거형은 `## 2. 코드` 블록 설명의 몫이다.
- **분량은 풀이가 필요로 하는 만큼이다.** 난이도가 낮다고 "왜"를 줄이지 않는다. 쉬운 문제도 요구 요약과 핵심 관찰(왜 옳은가)은 쓴다. 다만 정말 쓸 게 없는 단순한 문제는 한 문장으로 충분하다. 없는 crux를 지어내거나 문단으로 부풀리지 않는다.
- **문체는 사용자 본인 톤에 가깝게 쓴다.** "~는데 / ~이므로 / 따라서 / 반대로 / 결국"으로 절을 이어붙인 긴 연결 문장으로 한 호흡에 추론을 따라가고, 문단은 최소로 둔다(보통 1~2문단, 접근이 여럿이면 접근마다). 근거와 결론을 짧은 문장으로 갈라놓지 않고 한 문장에 이어 쓴다(길어도 된다). 짧게 쪼갠 문장의 나열은 사람이 쓴 글보다 읽기 어렵고 어색하다. 일부러 다양하게 바꾸려 하지 않고 자연스러운 작문이면 된다.

## 다중 접근 — 접근 이름

드래프트에 `### 풀이` 헤딩이 2개 이상이면 각 접근에 이름을 붙인다(`ps` 스캐폴드는 번호만 만들고 이름은 비워 둔다).

- **코드 섹션 헤딩**: `### 풀이 N: 이름 [Java][C++]...` — 번호 + 콜론 + 이름, 뒤에 언어 브라켓. 첫 접근도 `### 풀이 1: 이름`으로 번호를 붙인다.
- 이름은 **"이 풀이를 한마디로 뭐라 부르나"**에 답한다 — 풀이의 핵심 아이디어(알고리즘·자료구조·수학 성질) 하나를 가리킨다. 아래 순서로 가장 위 tier의 이름을 고른다:
  1. **명명된 알고리즘·자료구조·공식을 쓰면 그 이름.** `tags.yaml` 어휘를 재사용하되 한글 관용명이 있으면 한글(`BFS`, `유니온 파인드`, `그리디`, `에라토스테네스의 체`, `차분 배열`, `누적 합`, `이분 탐색`) — 풀이 이름과 태그가 어긋나지 않게. 같은 DP라도 표 전체를 저장하면 `배열 DP`, 롤링 배열로 줄이면 `공간 최적화 DP`처럼 구분이 핵심이면 그 축을 이름에 둔다.
  2. **명명된 기법이 없으면 접근 전략** — `완전 탐색`, `제곱근까지 탐색`, `합 공식`, `표준 라이브러리`.
  3. **전략도 애매하고 구현 자체가 정체성이면 그 구현** — `반복 합산`, `직접 갱신`, `카운팅 배열`, `방문 체크`, `비트 토글`, `XOR 상쇄`.
- **이름을 짓기 전에 이미 발행한 포스트의 이름과 대조한다**: `grep -rh '^### 풀이 [0-9]\+: ' <레포 루트>/_posts`(한글 줄 집계는 `LC_ALL=C sort | LC_ALL=C uniq -c`). 같은 기법이면 같은 이름을 재사용하고, 아직 쓴 이름이 없으면 위 tier 원칙으로 짓는다.
- **같은 이름은 같은 기법만 가리킨다.** 같은 구분이 여러 포스트에 나오면 같은 단어를 쓰고(이미 쓴 이름을 재사용하고 같은 기법의 호칭도 통일 — `브라이언 커니핸 알고리즘`/`브라이언 커니핸 DP`), 반대로 다른 기법에 같은 이름을 붙이지 않는다(`XOR 상쇄`와 `비트 토글`을 둘 다 "비트 XOR"이라 부르면 구분이 사라진다). "naive 먼저 / 최적화 나중" 쌍이면 naive는 실제 동작에 맞는 2·3(`직접 갱신`/`반복 합산`/`완전 탐색`), 최적화는 1·2의 이름.
- 한 포스트에 같은 tier 이름이 겹치면(표준 기능 풀이 2개 등) 무엇에 적용하는지로 구분(`문자별 표준 함수` / `swapcase 메서드`). 한 접근이 여러 tier에 걸치면(DP인데 포인트가 공간 최적화, 정렬 계열인데 방식이 다름) 겹치는 축을 이름에(`배열 DP` / `공간 최적화 DP`, `빈도순 정렬` / `버킷 정렬`).
- 언어마다 구현이 갈리면 대표 구현(Java·C++) 기준으로 짓고 자료구조 세부에 이름을 묶지 않는다(`방문 체크` — Java·C++는 배열, Python은 `set`). 자료구조 자체가 갈림길인 접근(`카운팅 배열` / `카운팅 맵`)만 예외.
- 접근이 하나뿐이면 `### 풀이 [langs]` 그대로 두고 이름을 붙이지 않는다.
- `sync`의 헤딩 매칭은 `### 풀이 N` 뒤의 접미어(`: 이름`, 언어 브라켓)를 무시하므로 이름을 붙여도 코드 동기화에 영향 없다.

## 수식 표기 세부

`## 1. 아이디어`·코드 블록 설명의 수식(`$...$`) 전체에 적용한다.

- **코드 변수는 소문자 그대로** 쓴다: `solution(int n)`이면 `$\gcd(n, 6)$`, `$k = \lfloor n / 2 \rfloor$`. 기호가 거추장스러우면 서술로 풀어도 된다.
- math mode 안 코드 식별자는 **1글자면 맨몸**(`$\log_{10} n$`, `$\gcd(n, 6)$`), **2글자 이상이면 `\text{}`로 감싼다**(`$\log_{10}(\text{order})$`, `$\text{numer1} \times \text{denom2}$`). 맨몸 `order`는 `o·r·d·e·r` 문자곱으로 렌더된다. 함수 인자면 괄호도 함께.
- 이항 연산자 `+` `-` `/`(나눗셈)는 양쪽에 공백: `$N / 2$`(not `$N/2$`), `$(i - 1, j)$`(not `$(i-1, j)$`). 표준 LaTeX 소스 관례이고 렌더 결과는 같다. 지수·아래첨자 안은 예외.
- 분수는 기본으로 `\dfrac{}{}`를 쓴다(크게 렌더돼 읽기 좋다). 분자·분모가 단일 항인 간단한 것은 슬래시도 된다(`$N / 2$`, `$n / \gcd(n, 6)$`). **`\frac`은 쓰지 않는다** — 인라인에서 작게 렌더된다.
- 1,000 이상 숫자는 `{,}`로 콤마: `$10{,}000$`(not `$10000$`). 그냥 `,`만 쓰면 MathJax(Chirpy가 쓰는 수식 엔진)가 콤마 뒤에 여백을 넣어 어색하다. 연도처럼 원래 콤마를 안 쓰는 표기는 예외.
- **수식 안 `*` `\{ \}` `\|` `\\`는 쓰지 않는다.** kramdown이 마크다운을 먼저 처리해서 한 단락에 `*`가 둘이면 사이가 `<em>`이 되고, `\{`·`\|`·`\\`는 역슬래시가 사라진다. 이스케이프가 필요 없는 `\ast`(또는 `\times`), `\lbrace` `\rbrace`, `\vert` `\Vert`를 쓴다. 표 셀 안 수식의 `|`는 열이 갈라지므로 `\vert`.
- 로그 밑은 생략한다(`$\log N$`). 값을 실제로 좌우할 때만 밑을 표시하며, 특히 **10진 자릿수**는 `$\log_{10}$`.

## `## 2. 코드` — 블록 설명 프로즈

- 언어별로 특징적으로 설명할 게 있으면 `### 풀이 N` 헤딩 바로 아래(그 접근의 전 언어 공통) 또는 각 코드 블록 바로 아래(그 언어 전용)에 프로즈를 넣어도 된다. 위치로 스코프를 구분한다 — **헤딩 아래(공통)는 언어 중립**, **그 언어 전용 블록에서만** 그 언어 얘기를 한다. 다른 언어를 이름 대며 나란히 대조하는 것("Java와 달리 C++는 ~")은 피한다 — 자기 언어만 서술. 이미 사람이 써둔 설명은 그대로 두고 덮어쓰지 않는다.
- **조미료처럼 넣는다.** 필수가 아니다. 기준은 "이 설명이 없으면 독자가 틀린 코드를 쓰거나 더 긴 코드를 쓰는가?"이고(`함정`·`지름길`), 아니오면 넣지 않는다. 일견 버그로 보이는 부분(범위와 어긋나 보이는 반복 시작점 등)을 해명하는 설명은 넣는다. 기본 문법 수준이 아니거나 모르기·놓치기 쉬운 내장 기능·트릭·함정을 한 줄로 짚는다(C++ `int&`로 받아야 원소가 바뀐다, Java `Arrays.sort`에 `Comparator`를 넘기려면 `Integer[]`여야 한다, Python `str.maketrans`/`translate` 같은 지름길). 코드가 복잡하면 설명해도 되지만 쓸데없는 설명을 우르르 달지 않는다. 호출을 말로 옮겼을 뿐인 설명(`reverse`로 뒤집는다)과 불투명한 변수명을 풀어 주는 매핑 설명은 넣지 않는다. 같은 포스트의 다른 언어에 같은 함정이 있는데 한쪽만 설명이 있으면 불균형이니 맞춘다.
- **버전 요구는 예전 버전에서 깨질 때만 적는다.** 비교적 최신 버전에서만 지원하는 기능을 써서 예전 버전으로 컴파일·실행하면 안 될 만하면 그 기능을 설명하는 자리에 "`contains`는 C++20부터 쓸 수 있다", "`bit_count`는 Python 3.10부터 쓸 수 있다" 같은 한 줄을 적는다. 오래전부터 있던 기능에는 적지 않는다.
- **선택 서술, 과거형으로 쓴다.** 풀이는 작성자가 고른 방법이라 일반론("~하면 ~된다")이 아니라 "이렇게 했다"로 쓴다(`range`의 세 번째 인자로 2씩 건너뛰며 합했다, `long`을 썼다). API 사실 한 줄은 선택 서술에 이어 붙여도 된다(`std::rotate`로 두 번째 인자의 원소가 새 시작이 되도록 구간을 회전시켰다).
- **용어는 개발자들이 실제로 쓰는 표기로 쓴다.** 번역투를 피하고 그 언어의 어휘를 쓴다(Python은 리스트·문자열).
- **표준 라이브러리 심볼은 코드에서 호출된 형태대로 쓴다.** C++ 자유 함수·타입만 `std::` 접두어를 붙인다(`std::rotate`, `std::string`). 코드가 `using namespace std;`라 접두어 없이 등장해도 표준 심볼임을 드러내고 검색성을 높이려는 의도적 예외다. 멤버 함수는 호출된 형태 그대로(`find`, `append`), Python은 코드의 import 스타일(`import math` → `math.gcd`, 클래스 호출은 `str.maketrans`, 인스턴스 메서드는 `translate`), Java도 호출 형태(`Arrays.sort`, `toCharArray`)로 쓴다.

## `## 3. 회고` (선택)

- 아이디어가 정답으로 향한 흐름만 담으므로, 그 밖의 개인 경험을 담는 자리다. 실수·오답 원인, 버린 첫 접근, 다른 문제와 이어지는 깨달음처럼 **구체적 사건이 있을 때만** 코드 섹션 뒤에 둔다. 드물게 쓰며, 쓸 게 없으면 두지 않는다(감상만 있으면 넣지 않는다).
- **사용자가 쓴다.** Claude가 겪지 않은 시행착오를 지어내지 않는다(위 "안 쓰는 것"). 아이디어에 이미 쓴 함정을 되풀이하지 않는다 — 아이디어는 "왜 옳은가", 회고는 "나는 어떻게 헤맸나".
- 어투·표기 규칙은 다른 프로즈와 같다. 시제·1인칭은 제한하지 않는다.
- `publish`가 막지 않고, `review-post`가 평가한다. `review-code`·`sync`는 이 섹션을 건드리지 않는다.
