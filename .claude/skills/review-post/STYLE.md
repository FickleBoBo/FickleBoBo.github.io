# PS 포스트 프로즈·표기 컨벤션

`ps`가 만든 스캐폴드의 프로즈 필드(`## 1. 아이디어`, `## 2. 복잡도`의 변수 설명, `## 3. 코드`의 블록 설명)를 **사람이 직접 쓰거나 `review-post`가 채울 때** 따르는 단일 규칙. `ps/SKILL.md`(사람이 손으로 쓸 때)와 `review-post/SKILL.md`(서브에이전트가 채울 때)가 이 파일을 정본으로 참조한다 — 같은 규칙을 각 SKILL.md에 다시 적지 않는다.

## 어투·시제

- 다체(평서체 — "~이다", "~된다")로 통일. 합니다체 금지.
- 시제는 문맥 기준으로 구분: 알고리즘이 왜 성립하는지 논증하는 문장은 현재형(`~한다`/`~된다`), 여러 방법 중 이걸 택했다는 서술(구현·전략 선택)은 과거형(`~했다`).
- `해주다`/`~해줬다` 계열은 방향과 무관하게 배제(항상 캐주얼함).

## 용어 표기

- **오버플로우** (not 오버플로). 마찬가지로 언더플로우.

## 평문 · 백틱 · 수식(`$...$`)

값·수량·식을 프로즈에 쓸 때 셋 중 하나를 고른다. **`## 1. 아이디어`·`## 2. 복잡도` 변수 설명·`## 3. 코드` 블록 설명에 동일하게 적용**되는 규칙이다. **기본값은 평문** — 한국어 서술로 풀 수 있으면 마크업하지 않는다("2씩 증가", "7로 나눈 몫", "-1을 반환", "인덱스 0, 5, 10", "1부터 `n`까지"에서 `1`). 아래 두 트리거에 걸릴 때만 마크업한다.

섹션별로 이 규칙 위에 얹히는 것: **복잡도 표·변수 설명**에서는 복잡도 변수를 대문자 `$N$`으로 승격한다(아래 `## 수식 표기 세부` 1번), **코드 블록 설명**에서 C++ 표준 자유 함수는 `std::` 접두어를 붙인다(아래 `## \`## 3. 코드\` — 블록 설명 프로즈`, 백틱 규칙의 의도적 예외).

- **백틱 — 코드의 토큰을 코드로서 가리킬 때.**
  - 코드에 그 형태로 있는 식별자·함수명(`array`, `solution`, `dp`), 문자·문자열 리터럴(`"Z"`, `"EMPTY"`).
  - 코드 어법으로 쓴 식 하나를 통째로 — 배열·테이블 인덱싱, 점화식 포함: `` `arr[i]` ``, `` `n % 10` ``, `` `dp[i][j] = max(dp[i - 1][j], dp[i][j - 1]) + cost` ``. 어법 유지: `max`(not `\max`), `*`(not `\times`). 식 안의 숫자·기호는 식과 함께 백틱(`` `dp[0][1] = 1` ``).

- **수식(`$...$`) — 프로즈로 못 치는 수학 표기이거나 대수 유도일 때.**
  - 코드에 없는 표기: `\lfloor\rfloor`·`\lceil\rceil`, `\sum`·`\prod`, `\sqrt`, `\binom`, 위·아래첨자(`$2^k$`, `$x_1$`), 분수, `\log`·`\gcd`, 그리스 문자, 논리·집합 연산(`$x_1 \lor x_2$`), 비트 연산 서술 표기(`$a \oplus b$`).
  - 변수를 쓴 대수 유도는 표현 전체를 수식으로 — "총 `k` $= (n+1)/2$개"(X) → "총 $k = (n + 1) / 2$개"(O). 백틱-수식 혼용은 어색함.
  - 좌표·구간 튜플: `$(i, j)$`, `$(1, 1)$`, `$[l, r]$`(코드엔 인덱싱으로만 있고 튜플로는 없음).
  - 공식의 일부인 숫자: `$k^2$`, `$2k$`, `$10^9 + 7$`.

- **타이브레이커 — 쓴 형태가 마크업을 정한다.** 같은 연산을 코드 어법으로 쓰면 백틱(`` `n % 10` ``), 한국어로 풀면 평문("10으로 나눈 나머지"). 어느 쪽으로 쓸지는 자유. "1부터 `n`까지"의 비대칭(`1` 평문, `n` 백틱)도 이걸로 설명된다 — `1`은 값, `n`은 식별자.

- **경계.**
  - 리터럴 나열에 섞인 항은 그 나열의 마크업을 따른다 — `` `zero` ``~`` `nine` ``를 `` `0` ``~`` `9` ``로 치환(양쪽 다 리터럴).
  - 한 포스트에서 수학적 대상은 수식, 그걸 다루는 코드 변수는 백틱으로 갈릴 수 있다 — 순서쌍 $(a, b)$를 코드가 루프 변수 `i`로 훑는 식. 혼용이 아니라 스코프 구분이다.

## 수식 표기 세부 (복잡도 섹션 포함, 수식 전체에 적용)

- 변수명 대문자 관용($N$, $M$)은 **복잡도 표와 그 아래 변수 설명 프로즈에만** 적용한다 — 코드에 소문자 파라미터로 등장해도 복잡도 셀·변수 프로즈에서는 대문자로 승격(`m` → `$M$`)하고, `($N$ = 입력값 `m`)`으로 코드 변수와 연결한다. **`## 1. 아이디어` 본문 수식은 반대로 코드 변수명을 그대로(소문자) 쓴다** — `solution(int n)`이면 본문도 `$\gcd(n, 6)$`, `$k = \lfloor n / 2 \rfloor$`. 서술 맥락이라 대문자 승격이 오히려 어색하다(이 항목 외 나머지 수식 표기 규칙 — 연산자 공백, `{,}` 콤마, 곱셈 결합 등 — 은 아이디어 수식에도 그대로 적용). 이 소문자 규칙은 코드에 대응하는 스칼라 파라미터가 있을 때다(`solution(int n)`). 크기가 배열 길이(`len(names)`)로만 존재하고 스칼라 파라미터가 없으면, 아이디어 본문 수식도 **복잡도 표와 같은 대문자 `$N$`**을 쓴다 — 맞출 소문자 코드 리터럴이 없고, 바로 아래 `($N$ = ...)` 정의와 같은 양이라 그게 정합적이다. 워밍업이라 기호가 거추장스러우면 아예 서술로 풀어도 된다.
- math mode 안 코드 식별자는 **1글자면 맨몸**(`$\log_{10} n$`, `$\gcd(n, 6)$`), **2글자 이상이면 `\text{}`로 감싼다**(`$\log_{10}(\text{order})$`, `$\text{numer1} \times \text{denom2}$`) — 맨몸 `order`는 `o·r·d·e·r` 문자곱으로 렌더된다. 함수 인자로 들어가면 괄호도 함께. 아이디어 본문 수식에도 그대로 적용(위 항목).
- 이항 연산자 `+` `-` `/`(나눗셈)는 양쪽에 공백: `$N / 2$`(not `$N/2$`), `$(i - 1, j)$`(not `$(i-1, j)$`). 지수(`n^2`)·아래첨자처럼 항상 붙여 쓰는 표기는 예외.
- 1,000 이상 숫자는 `{,}`로 콤마: `$10{,}000$`(not `$10000$`). 그냥 `,`만 쓰면 KaTeX가 콤마 뒤에 여백을 넣어 어색해짐. 연도처럼 원래 콤마를 안 쓰는 표기는 예외.
- 곱셈 결합:

  | 형태                 | 표기                               | 예                               |
  | -------------------- | ---------------------------------- | -------------------------------- |
  | 맨몸 변수 하나 × log | 붙여씀                             | `$O(N \log N)$`, `$O(N \log M)$` |
  | 맨몸 변수 두 개 곱   | 사이에 `\times`                    | `$O(N \times M)$`                |
  | 변수곱 + log         | 곱에만 `\times`, log 앞뒤는 붙여씀 | `$O(N \times M \log K)$`         |

  `\cdot`나 그냥 붙여쓰기(`$O(NM)$`)는 쓰지 않는다.

- 로그 밑은 생략한다 — 점근 표기에서 밑은 상수배라 무의미(`$O(N \log N)$`, `$O(\log \log N)$`). 밑이 값을 실제로 좌우할 때만 표시하며, 특히 **10진 자릿수**는 `$\log_{10}$`. `$O(\cdot)$` 안에 명시적 밑을 같이 쓰지 않는다 — O가 밑을 흡수하므로 `$O(\log_{10} N)$`(X) → `$O(\log N)$`, 또는 O를 빼고 `$\approx \log_{10} N$`.
- 자릿수를 복잡도 인자로 쓰면 표에 `$\log$`를 직접 박지 않고 문자 `$D$`로 두고, 변수 설명에서 `($D$ = `n`의 자릿수 $\approx \log_{10} n$)`으로 푼다.

## `description`

**PS 포스트는 `description`을 쓰지 않는다** — 폐기된 필드. 스캐폴드가 안 만들고, 옛 드래프트·백업에 `description:` 줄이 남아 있으면 삭제한다. 사람도 `review-post`도 채우지 않고 `publish` 완료 판정에서도 빠졌다. (폐기 경위: PS 입문 문제는 `title`이 이미 다 말해 이 필드가 제목 재탕밖에 안 됨. 상세는 메모리 `ps-blog-automation-workflow`.)

## `## 1. 아이디어`

- **"무엇"이 아니라 "왜"를 쓴다** (설명할 "왜"가 있는 문제라면). 코드가 어떤 연산을 하는지는 `## 3. 코드`가 이미 보여준다 — 그걸 산문으로 옮기면 중복이다. 독자(와 나중의 나)가 납득하려면 이 방법이 왜 옳은 답을 주는지, 문제의 어떤 조건이 이 접근을 가능하게/유리하게 만드는지가 있어야 한다. 코드와 문제를 요약하는 데서 멈추지 않는다. 단 통찰이랄 게 없는 트리비얼 문제는 예외 — 아래 "분량은 난이도에 비례" 참고.
- 그렇다고 부풀리지도 않는다 — 필요한 논증만 담고, 기법 자체의 교과서 설명이나 코드 줄 단위 워크스루로 늘리지 않는다(장황함도 결함).
- 서술(풀이 해설) 중심. 제약조건을 표로 따로 정리하지 않는다. 서브헤딩 없음. 지문 원문을 복붙하지 않는다(자기 말로 요약 — 저작권).
- **언어 무관하게 쓴다.** 특정 언어가 어떤 함수·트릭·자료구조로 구현하는지는 아이디어에 넣지 않는다("Python 풀이는 `replace`로 ~", "Java는 `StringTokenizer`로 ~" 전부 금지 — 비교가 아니어도 한 언어 단독 언급도 안 됨). 한 언어만 접근이 눈에 띄게 다르면, 세 풀이를 아우르는 공통 알고리즘을 아이디어에 쓰고(부호 있는 항의 합처럼 추상화), 그 언어만의 구현 설명이 꼭 필요하면 `## 3. 코드`의 해당 코드 블록 아래 프로즈로 뺀다.
  - 단 **이 문제의 정석 사고방식**을 서술하는 건 "특정 언어 구현"이 아니다 — 언어 이름을 안 대고, 대부분의 언어가 그대로 그렇게 푸는 접근이면 아이디어에 써도 된다(예: "정수에서 자리를 뽑으면 낮은 자리부터 나오니 마지막에 뒤집는다" — `% 10` 루프의 자연스러운 서술). 한 언어가 라이브러리로 그 단계를 건너뛰더라도(문자열 변환 등) 그 지름길은 해당 코드 블록 프로즈에서 다루고 아이디어는 정석대로 둔다. 금지 대상은 어디까지나 언어를 지목한 서술·대조이지, 언어 중립적인 알고리즘 묘사가 우연히 한 언어의 지름길과 안 겹치는 것이 아니다.
- **대상 독자 전제**: 알고리즘/자료구조의 기본 개념(DP·이분탐색·차분 배열이 뭔지 등)은 안다고 전제하고 재설명하지 않는다. 대신 **이 문제에 특화된 추론**(왜 이 점화식이 성립하는지, 초기값·경계를 왜 그렇게 잡는지, 왜 이 기법을 이 문제에 적용할 수 있는지)은 생략 없이 풀어쓴다.
- **다중 접근**: 접근마다 그 접근을 쓰는 이유를 밝힌다 — 특히 뒤 접근은 앞 접근의 어떤 한계(복잡도·특정 입력 규모 등) 때문에 나오는지. 기법 동작 자체가 아니라 "이 문제에서 그 기법이 왜 통하는지(적용 조건)"를 쓴다.
- 제약 수치가 풀이 근거로 실질적으로 중요하면 문장 안에 자연스럽게 녹이고, 안 중요하면(사소한 워밍업 등) 생략한다.
- 알고리즘/풀이 레벨만 쓴다. 복잡도 변수가 뭘 가리키는지는 여기가 아니라 `## 2. 복잡도`에 적는다.
- 본문 수식의 코드 변수는 **소문자 그대로** — 대문자 승격은 복잡도 섹션에서만(`## 수식 표기 세부` 참고).
- **금지 패턴 — AI 슬롭 어투.** 타깃은 재진술 자체가 아니라 재진술로 **늘어지는 것**이다. 사람이 직접 쓴 짧고 담백한(친근해도 됨) 프로즈는 여기 안 걸린다:
  - 지문 한 줄 요약 뒤에 `~가 성립하는 이유는 ~ 때문이다` 식 정리-증명 템플릿 어투로 이어지는 것 — 논증은 하되 평범한 서술로.
  - 코드가 한 일을 순서대로 옮긴 문단(`먼저 해시맵으로 ~ 셌다`, `~로 남겼다`, 끝에 `배열 버전은 ~, 최적화 버전은 ~`) — 그건 `## 3. 코드`가 보여준다. 접근을 한 문장으로 가볍게 짚는 건 괜찮다.
  - 모든 경계·초기값·모듈러 연산을 같은 비중으로 훑는 것 — 비자명한 것 하나만 짚고 나머지는 넘어간다.
- **분량은 문제의 실제 난이도에 비례한다.** 트리비얼 워밍업은 통찰이 없으면 친근한 한 줄 재진술로 끝내도 된다(`~하면 되는 간단한 문제다` OK) — 억지로 문단으로 부풀리거나 없는 crux를 지어내지 않는다. 비자명한 문제만 문단 단위로, 오프닝을 재진술로 낭비하지 말고 첫 문장부터 crux(코드만 봐선 안 드러나는, 이 풀이가 옳은 이유) 하나에 집중한다.
- `review-post`가 빈 아이디어를 채울 때:
  - 채운 아이디어는 사용자가 다시 쓸 초안이다 — 완성본을 목표로 부풀리지 말고 뼈대(핵심 관찰 + 꼭 필요한 논증)만 남긴다.
  - 원문(플랫폼 공식 문제 페이지)을 항상 직접 재확인한다 — 이미 아는 유명한 문제여도 예외 없음(제약조건 수치를 잘못 기억해 조용히 틀리는 걸 막기 위함).
  - 제약조건에 지수/첨자(`$10^k$`류)가 보이면 WebFetch 결과를 믿지 말고 `curl -s <url> | grep -o '<sup>[^<]*</sup>'`로 원본 HTML의 `<sup>`/`<sub>`를 직접 확인한다.
  - Claude가 겪지 않은 시행착오("처음엔 이렇게 생각했는데")를 지어내지 않는다 — 바로 최종 아이디어부터 쓴다.
  - 커뮤니티에서 실제로 쓰이는지 확인 안 된 용어를 "~라고 불린다"로 인용하지 않는다 — 확실치 않으면 검증하거나 서술적 표현으로 순화.

## 다중 접근 — 접근 이름

드래프트에 `### 풀이` 헤딩이 2개 이상이면 각 접근에 이름을 붙인다(`ps` 스캐폴드는 번호만 만들고 이름은 비워 둔다).

- **코드 섹션 헤딩**: `### 풀이 N: 이름 [Java][C++]...` — 번호 + 콜론 + 이름, 뒤에 언어 브라켓. 첫 접근도 `### 풀이 1: 이름`으로 번호를 붙인다.
- **`## 2. 복잡도` 표 "접근" 열**: 접두어(`풀이 N:`) 없이 이름만 (`직접 순회`, `차분 배열`). 표 아래 변수 프로즈에서 특정 접근을 가리킬 때도 이름으로 (`차분 배열 풀이의 diff가 ...`).
- 이름은 **"이 풀이를 한마디로 뭐라 부르나"**에 답한다. 아래 순서로 가장 위 tier의 이름을 고른다:
  1. **명명된 알고리즘·자료구조·공식을 쓰면 그 이름.** `review-code/tags.yaml` 어휘를 재사용하되 한글 관용명이 있으면 한글(`BFS`, `DFS`, `유니온 파인드`, `에라토스테네스의 체`, `차분 배열`, `누적 합`, `이분 탐색`, `스택`, `등차수열 합 공식`, `시행 나눗셈`) — 풀이 이름과 태그가 어긋나지 않게.
  2. **명명된 기법이 없으면 접근 전략** — 고정 어휘에서만: `완전 탐색`(제약 안 후보 전부 시도), `제곱근까지 탐색`(√n 경계), `닫힌 공식`(반복 없이 식 하나 — 식이 명명돼 있으면 1로), `표준 라이브러리`(직접 구현을 언어 기능으로 대체).
  3. **전략도 애매하고 구현 자체가 정체성이면 그 구현** — `직접 순회`, `반복 합산`, `롤링 변수`, `비트 XOR`, `ASCII 오프셋`.
- 같은 구분이 여러 포스트에 나오면 같은 단어를 쓴다(위 고정 어휘). "naive 먼저 / 최적화 나중" 쌍이면 naive는 실제 동작에 맞는 2·3(`직접 순회`/`반복 합산`/`완전 탐색`), 최적화는 1·2의 이름.
- 한 포스트에 같은 tier 이름이 겹치면(표준 기능 풀이 2개 등) 무엇에 적용하는지로 구분(`문자별 표준 함수` / `일괄 swapcase`). 한 접근이 여러 tier에 걸치면(DP인데 포인트가 공간 최적화) 겹치는 축을 이름에(`배열 DP` / `롤링 변수`).
- 접근이 하나뿐이면 `### 풀이 [langs]` 그대로 두고 이름을 붙이지 않는다.
- `sync`의 헤딩 매칭은 `### 풀이 N` 뒤의 접미어(`: 이름`, 언어 브라켓)를 무시하므로 이름을 붙여도 코드 동기화에 영향 없다.

## `## 2. 복잡도` — 셀 값과 변수 설명

이미 AC된 코드의 복잡도는 판단이 아니라 사실이다 — 누가 채우든 같은 표가 나와야 한다. 아래 절차와 예시를 그대로 따른다.

### 지배 변수 고르기

1. 코드가 실제로 순회·복사·정렬·재귀하는 자료구조를 나열한다.
2. 각각의 크기를 문제 제약에서 확인한다.
3. 실행 시간을 지배하는 것을 변수로 잡는다. 독립적으로 커지는 게 여럿이면 각각 별도 문자.
4. 입력 파라미터 등장 순서로 $N$을 배정하지 않는다 — 코드가 실제로 도는 대상 기준.
5. 전체 중 일부만 쓰면(부분 문자열, 상위 $K$개 등) 전체 크기가 아니라 그 부분 크기가 변수.
6. 변수명은 문제의 대상을 가리키는 관용 문자로 — 격자는 행 $N$·열 $M$, 그래프는 정점 수에 문제 용어를 그대로 승격(`n` = 컴퓨터 수 → $N$)하고 간선 수는 $E$. 교과서 $V$를 습관적으로 쓰지 않는다. 지문의 주 스칼라(`n`)는 $N$ 우선권을 가진다 — 다른 대상(격자 행, 부분 문자열 길이 등)이 $N$을 먼저 차지했으면 `n`을 $M$으로 밀지 말고 그 다른 대상을 $M$·$L$ 등으로 옮긴다.
7. 제약이 값을 상수로 묶어도(입문 문제 대부분이 `n ≤ 100`, 값 `≤ 1000` 식) 코드가 실제로 순회·재귀하는 양을 자유 변수로 둔다 — 엄밀히 따지면 전부 $O(1)$이 되어 표가 무의미해진다. 스칼라 하나에 반복 적용되는 알고리즘(유클리드 호제법 등)은 그 스칼라를 변수로: `gcd(p, q)` → 시간 $O(\log \min(P, Q))$. 없는 $N$을 지어내지 말고 코드의 `p`·`q`에 대응시키되, 복잡도 표기는 대문자 관용이라 $P$·$Q$로 올리고 표 아래에서 `($P$ = `p`, $Q$ = `q`)`로 잇는다. 단 이는 반복 횟수 상한이 입력의 함수로 알려진 경우다($\log \min(P, Q)$ 등). 상한이 미해결 문제라 입력으로 못 잡으면 실제 반복 횟수 자체를 변수로 둔다 — `($K$ = 반복 횟수)` / `($K$ = 출력 수열의 길이)`.
8. **입력 원소 개수가 상수로 고정**된 건(제약에 "`sides`의 원소는 3개", 좌표 `dot`는 2개, RGB 3개 식) 위 7번의 "값이 상수로 묶임"과 다르다 — 순회량 자체가 늘어날 여지가 없으므로 스칼라 인자와 똑같이 취급해 정렬·순회를 포함해 전부 $O(1)$이다. `sort(sides)` 후 비교해도 $O(1)$ / $O(1)$. `n ≤ 1000`(값 상한)은 7번, `원소 3개`(개수 고정)는 8번.
9. **한 입력에서 여러 테스트 케이스를 처리**하면(코드에 `cin >> t; while (t--) solve();` 형태 — Codeforces 대부분) 그 테케 루프도 복잡도에 넣는다. 케이스당으로 쓰지 않는다: 케이스 내부가 $O(1)$이면 시간 $O(T)$(`($T$ = 테스트 케이스 수)`), 케이스 내부가 입력 길이에 비례하면 변수를 **전체 입력 기준 총합**으로 정의한다(`($N$ = 모든 테스트 케이스에 걸친 초기 단어 길이의 총합)`) — 이때 케이스당 상수 작업은 $T \le N$이라 총합 변수에 흡수되므로 $O(T)$를 따로 더하지 않는다. CF는 `sum of n over all test cases ≤ ...` 식 전역 총합 제약이 흔해 대개 이쪽이고, 표에 $T$가 실제로 남는 건 케이스 내부가 진짜 $O(1)$이거나(값만 읽고 상수식 출력) 전역 총합 제약이 없는 문제로 한정된다. 공간은 케이스마다 재사용되므로 보통 그대로. 프로그래머스·LeetCode는 함수가 케이스당 1회 호출이라 이 항목이 적용되지 않는다.

### 반복 형태별 고정 예시

| 코드 형태                                | 시간            | 공간            | 변수 설명 프로즈                     |
| ---------------------------------------- | --------------- | --------------- | ------------------------------------ |
| 한 번 순회 후 값 하나·불리언 반환        | $O(N)$          | $O(1)$          | ($N$ = `arr`의 길이)                 |
| 제자리 정렬 후 값 하나 반환              | $O(N \log N)$   | $O(1)$          | ($N$ = `arr`의 길이)                 |
| 인자를 제자리 수정해 반환                | $O(N)$          | $O(1)$          | ($N$ = `arr`의 길이)                 |
| $N$개짜리 배열·문자열을 새로 만들어 반환 | $O(N)$          | $O(N)$          | ($N$ = `arr`의 길이)                 |
| 정렬한 사본에서 값을 도출                | $O(N \log N)$   | $O(N)$          | ($N$ = `arr`의 길이)                 |
| 해시·집합에 $N$개 담아 조회              | $O(N)$          | $O(N)$          | ($N$ = `arr`의 길이)                 |
| 모든 쌍 이중 루프                        | $O(N^2)$        | $O(1)$          | ($N$ = `arr`의 길이)                 |
| 격자 순회·DP                             | $O(N \times M)$ | $O(N \times M)$ | ($N$ = `board`의 행 수, $M$ = 열 수) |
| 그래프 BFS/DFS (인접 리스트)             | $O(N + E)$      | $O(N + E)$      | ($N$ = 정점 수, $E$ = 간선 수)       |
| 그래프 BFS/DFS (인접 행렬)               | $O(N^2)$        | $O(N)$          | ($N$ = 정점 수)                      |

공간은 **스크래치 + 반환값 크기**다. 입력은 제외, "입력·출력 다 빼는 auxiliary" 관례가 아니라 "반환값은 포함"하는 쪽을 택한다(PS 풀이 해설에서 더 흔하고 직관에 맞음).

- 입력은 안 센다 — 제약이 값을 묶든, 프로그래머스 C++ 시그니처가 `vector<int>`·`string`을 값으로 받든(그 복사는 입력 경계다, 안 그러면 배열·문자열 받는 모든 C++ 풀이가 $O(N)$이 된다).
- 반환값은 **크기로** 센다 — $N$개짜리 배열·문자열을 새로 만들어 반환하면 $O(N)$, 반환이 값 하나·불리언이면 $O(1)$.
- **예외 — 인자 재사용**: 코드가 인자 배열·문자열을 제자리 수정해 그대로 반환하면(코드에 `return numbers`처럼 보임) 새 할당이 없으니 그 언어는 $O(1)$이다. 이건 stdlib 숨은 차이가 아니라 코드에 드러나는 차이라, 언어끼리 갈리면 아래 "언어별로 갈릴 때"대로 처리한다.
- 표준 라이브러리 내부 구현은 블랙박스 — `sort()`는 언어 무관 시간 $O(N \log N)$, 파이썬 TimSort의 $O(N)$ 임시 버퍼·introsort의 재귀 스택은 안 센다. 그래서 제자리 정렬 후 값 하나만 반환하면 공간 $O(1)$이다.
- **예외 — 순회 전용 `toCharArray()`**: Java가 `for (char c : s.toCharArray())`처럼 문자열을 훑기 위한 수단으로만 char[]를 만들면(= `s.charAt(i)` 루프로 바꾸면 $O(1)$인 자리) 그 버퍼는 알고리즘의 공간이 아니라 이터레이션 문법 설탕이라 안 센다. 단 그 char[]를 제자리 정렬·역순 등으로 **변형**하거나 루프 밖으로 **들고 나가**(반환·필드 저장) 재사용하면 다시 스크래치로 센다 — "만들자마자 훑고 버리는" 경우만 예외다.
- 직접 만든 (반환하지 않는) 배열·리스트·해시, **코드에 직접 쓴** 재귀의 최대 깊이는 센다. 유클리드 호제법을 손으로 재귀 구현했으면 $O(\log \min(P, Q))$ 스택 — 단 깊이가 상수 수준(로그가 20~30)이면 $O(1)$로 봐도 된다.

### 언어별로 갈릴 때

대부분은 세 풀이가 같은 공간이라 한 행으로 끝난다. **코드에 직접 드러나는** 차이로 갈릴 때만 예외 처리한다 — 대표적으로 (1) 한 언어는 인자를 제자리 수정해 반환($O(1)$)하고 다른 언어는 새 컬렉션을 만들거나($O(N)$), (2) 한 언어만 재귀를 손으로 구현해 스택이 무시 못 할 때. 이때 표에는 **다수파·기본형** 값을 넣고 표 아래 변수 프로즈에서 소수파를 한 줄로 짚는다 — 예: "배열 두 배 만들기"는 Java·C++가 인자 제자리 수정이라 표는 $O(1)$, `(... Python은 새 리스트를 만들어 반환하므로 공간 $O(N)$)`.

### 변수 설명 프로즈 포맷 (표 아래)

**아래는 예시가 아니라 고정 포맷이다.**

- 셀이 $O(1)$뿐이면 보통 프로즈 줄을 쓰지 않는다. **예외**: 알고리즘만 보면 로그·선형으로 읽히는데 상수 인자·상수 크기라 실제로는 상수인 경우처럼, 값이 의문을 부를 만하면 왜 그런지 한 줄로 짚는다 — 예: `(GCD를 유클리드 호제법으로 구하지만 제수가 상수 6이라, 첫 나눗셈 뒤 두 인자가 모두 6 이하로 줄어 `n` 크기와 무관하게 상수 번의 스텝에 끝난다)`. 이 예외는 상한이 $N$보다 **훨씬** 작고 자료구조가 진짜 고정일 때(상수 제수, 미리 잡아 두는 52칸 카운트 배열 등)만이다 — 알파벳이 유계라 컬렉션이 그 알파벳 크기(53 등)에서 멈추는데 입력 길이도 그 언저리(`≤ 110`)면 억지로 $O(1)$로 낮추지 말고 그냥 $O(N)$으로 둔다.
- 그 외에는 표 바로 아래 **한 줄**, **괄호로 감싼 명사형 개조식**: `($N$ = <가리키는 대상>)`. 불릿(`- `) 금지. 종결은 명사구나 복잡도항($O(\cdot)$)으로 — `~이다`/`~한다`/`~된다` 같은 서술 어미로 끝내지 않는다(부연도 마찬가지). 예외: 상수성·수렴 근거를 푸는 설명 주석처럼 명사형으로 옮기면 뜻이 뭉개지는 경우만 서술문으로 둔다(위 $O(1)$ 예외 항의 '왜' 등).
- 대상 표기: 코드 식별자면 백틱(`` `my_string`의 길이 ``), 입력 파라미터면 ``입력값 `n` ``. 파생값(파라미터들의 연산 조합으로 정해지는 값)은 **그 식을 그대로** 넣는다 — 코드 변수로 된 식이면 백틱(`` `num2 - num1 + 1` ``), 복잡도 변수로 된 식이면 `$...$`(`$N / K$`). 식만으로 불투명할 때만 뒤에 2~4단어 주석(식이 먼저). 닫힌 식이 없고 합으로만 표현되면($\sum (e_i - s_i + 1)$ 등) 무리해서 닫지 말고 $\sum$ 표기나 서술로 둔다.
- 변수 2개 이상: 쉼표로 나열하고, 필요하면 마침표로 끊어 부연 — `($N$ = `s`의 길이, $M$ = `m`. 결과 문자열의 길이 $N / M$)`. 부연도 명사형으로 끝내고 닫는 `)` 뒤에 마침표를 붙이지 않는다.

## `## 3. 코드` — 블록 설명 프로즈

- 언어별로 특징적으로 설명할 게 있으면 `### 풀이 N` 헤딩 바로 아래(그 접근의 전 언어 공통) 또는 각 코드 블록 바로 아래(그 언어 전용)에 프로즈를 넣어도 된다. 위치로 스코프를 구분한다 — **공통 스코프(아이디어·헤딩 아래)는 언어 중립**(`## 1. 아이디어`의 "언어 무관하게 쓴다"와 동일), **그 언어 전용 블록에서만** 그 언어 얘기를 한다. 전용 블록에서 상대적 어투("표준에 정수 GCD가 없어 직접 구현했다", "C++17부터 `std::gcd` 사용 가능")는 괜찮지만, 다른 언어를 이름 대며 나란히 대조하는 것("Java와 달리 C++는 ~", "다른 언어는 한 줄인데")은 피한다 — 자기 언어만 서술. 이미 사람이 써둔 설명은 그대로 두고 덮어쓰지 않는다.
- **필수가 아니다** — 대부분의 포스트는 이 프로즈가 없다. 코드가 스스로 설명되면 넣지 않는다.
- **표준 라이브러리 심볼 표기**:
  - C++ 표준 라이브러리 **자유 함수·타입**은 `std::` 접두어를 붙인다(`std::rotate`, `std::reverse`, `std::gcd`, `std::swap`, `std::string`) — 코드가 `using namespace std;`라 접두어 없이 등장해도. "코드에 그 형태 그대로" 백틱 규칙(위 `## 평문 · 백틱 · 수식`)의 의도적 예외로, 표준 심볼임을 드러내고 검색성을 높이려는 것. **멤버 함수**는 접두어 없이 호출된 형태대로(`my_string.find()` → `find`).
  - Python 모듈 함수는 코드의 실제 import 스타일을 따른다: `import math` → `math.gcd`, `from itertools import groupby` → `groupby`(맨이름). 메서드는 호출된 형태대로 — 클래스 호출이면 `str.maketrans`/`dict.fromkeys`, 인스턴스면 맨이름(`swapcase`), 관용형은 `"".join`.
  - Java 메서드도 호출 형태대로: `Arrays.sort`(클래스 호출), 인스턴스 메서드는 맨이름(`toCharArray`).
