# /review — PS 포스트 검수

PS 포스트를 **누락 없이 꼼꼼히** 점검하고 등급을 매긴다(무인자면 `_drafts/` 전체,
번호를 주면 `_drafts/` 우선·없으면 `_posts/`).
등급은 발행 게이트다: **S/A면 믿고 바로 `/publish`, B는 개선 권장, C는 수정 필수.**

원칙:
- **파일을 수정하지 않는다.** 검수 결과만 보고한다. **단 하나의 예외가 미기입 복잡도 표**로,
  Phase 3.5에서 확인을 받아 채운다(아래). 그 외 어떤 내용도 고치지 않는다.
- **역할 분담(중요):** 한 번에 많은 포스트를 몰아 보면 뒤쪽이 부실해지므로, **청크별 독립 Sonnet 에이전트가
  분석(analysis)을 실질적으로 짊어진다** — 아이디어·코드·복잡도·구조를 각 청크 신선한 컨텍스트에서 꼼꼼히.
  **메인은 판정(judgment)을 맡는다** — 에이전트 분석을 1차 자료로 받아 등급을 매기되,
  **등급을 가르는 주장(코드 정확성·복잡도)은 원본으로 재확인**한다.
- 이건 옛 스킬과 다른 점이다: 옛 review는 메인이 *전부* 재검토(전체 재read + 전체 mental trace)해서 에이전트와
  중복이 컸다(옛것은 에이전트의 태그 추천이 그 중복을 상쇄했으나, 새 블로그는 태그를 `/tag`로 분리해 상쇄가 없다).
  그래서 메인은 **전부 재trace 하지 않고, 등급-결정적 부분만 타겟 재확인**한다. 에이전트 출력을 통째로 받아쓰지도,
  통째로 재수행하지도 않는다.

## Phase 1. 기계 검사 + 청크 계획

```
python3 .claude/skills/review/review_check.py $ARGUMENTS
```

- 인자 없으면 `_drafts/` 전체, 있으면 해당 번호(`_drafts/` 우선, 없으면 `_posts/`).
- 스크립트가 결정론적으로 처리: 빈 아이디어 / 미기입 복잡도 표 / 누락 섹션 / TODO 제목·링크 / 언어 태그 없는 코드블록 / **콜아웃 문제**를 플래그하고, **청크 계획**(포스트 5개 또는 12,000자 중 먼저 닿는 쪽, 단일 포스트 미분할)을 출력한다.
- 기계 검사 결과를 사용자에게 보고한다.

### 콜아웃 검사

이 레포는 마크다운을 Prettier로 포맷팅하는데(`.vscode/settings.json`), Prettier는
blockquote 뒤의 kramdown IAL을 blockquote 안으로 끌어들여 `> {: .prompt-tip }`으로
만든다. 그러면 클래스가 blockquote가 아니라 안쪽 `<p>`에 붙어 테마 셀렉터
(`blockquote[class^='prompt-']`)가 빗나가고, **에러 없이 콜아웃 스타일만 사라진다.**
유일한 방어는 콜아웃 앞의 `<!-- prettier-ignore -->` 주석이다.

- `콜아웃 깨짐` — 이미 `> {: .prompt-* }` 형태. `>`를 지우고 앞줄에 주석을 넣어 고친다.
- `콜아웃 prettier-ignore 누락` — 아직 멀쩡하지만 다음 저장 때 깨진다. 주석을 추가한다.

둘 다 사용자가 눈으로 잡기 어려운 종류(무관한 파일을 저장하다 조용히 딸려 들어옴)이므로
발견하면 그냥 넘기지 말고 반드시 보고한다.

## Phase 2. 청크 계획 확인 → Sonnet 에이전트

1. 청크 계획(총 포스트 수, 청크 수 = 띄울 에이전트 수)을 사용자에게 알리고 **확인을 받는다**(에이전트 다수 = 비용).
2. **청크마다 Sonnet Agent 하나**를 띄운다:
   - `subagent_type: "general-purpose"`, `model: "sonnet"`, `run_in_background: true`.

   - 프롬프트에 그 청크의 파일 절대경로 목록을 넣는다.
   - 청크가 여러 개면 전부 병렬로 띄우고 완료를 기다린다(자동 깨어남).

## 문제 인지 (정직성 게이트 — 먼저)
각 포스트마다 문제를 확실히 아는지 판정해 리뷰 최상단에 표시:
- ✅ 확실히 앎 → 그대로 진행
- ⚠️ 대략만 앎 / ❌ 모름 → 포스트의 문제 링크를 **WebFetch로 원문 확인** 후 진행
- fetch 실패 시 "신뢰도 낮음" 명시. **아는 척 금지** — 모르면 모른다고 적는다.
- (원문은 검토용으로만 읽고, 포스트에 복붙하지 않는다.)

## 분석 기준
### 아이디어
- 논리적 완결성: "왜 이렇게 하면 되는지"가 있는가? 비약·오류는?
- 독자 이해도: 설명만 읽고 구현할 수 있는가?
- 수식/오타 일관성.
- 비어있으면 "아이디어 비어있음"만 적고 넘어간다.

### 코드
- 정확성: 정상이면 "정확", 틀리면 상세히(반례 포함).
- 엣지 케이스: 경계값(N=1, 빈 입력, 최댓값 등)을 구체적으로 검증.
- 개선점: 적극 제안. "없음"은 구체적 근거 필수. 특히 **미사용 코드**(선언만 하고 안 쓰는
  변수·함수, `include`했으나 안 쓰는 헤더)와 **명명 일관성**(같은 역할인데 이름이 들쭉날쭉)을
  놓치지 말 것. 단 이런 건 대개 사소 지적이라 개선점 노트로만 남기고 등급은 내리지 않는다(Phase 3 참고).
- 다국어: 로직 동일 → 하나만 상세 + 차이점. 로직 상이 → 각각.

### 대안 풀이
- 사용자 풀이보다 더 효율적이거나 더 표준적인 **알려진 접근**이 있으면 제시한다 —
  핵심 아이디어 한두 줄 + 복잡도 비교(전체 구현 코드까지는 불필요).
- 사용자 풀이 자체에서 불필요한 비효율(과한 자료구조, 중복 계산·순회, 점근적으로
  더 나은 방법이 뻔한 경우)이 보이면 구체적으로 지적한다.
- 이미 최적이거나 이 문제 규모에서 대안이 실익 없으면 "대안 없음"만 적고 넘어간다.
  없다고 대충 넘기지 말 것 — 실제로 아는 게 없을 때만 "대안 없음".

### 복잡도
- **접근마다 시간·공간 값을 직접 계산해 반드시 명시한다.** 표가 이미 차 있든 비어 있든 마찬가지다.
  표가 비어 있으면 여기서 낸 값이 그대로 채워질 후보가 되므로(Phase 3.5), "미기입"만 적고 넘어가지 말 것.
- 그 위에서 표와 대조: 표가 비어 있으면 `미기입 → 제안값 X`, 값이 다르면 `불일치 → 정정 제안`,
  같으면 `일치`.
- 접근이 여러 개면 각 풀이의 표를 개별 계산·개별 검증.

**공간복잡도 관례 (이 블로그 고정):**
- **auxiliary space로 적는다 — 입력도 출력도 제외**하고, 알고리즘이 추가로 잡는 공간만 센다.
  **← 이것만이 발행본 실측에서 나온 규칙이다**(120809는 길이 $N$ 배열을 새로 만들어 반환하는데
  $O(1)$로 표기돼 있다). 기존 글과 충돌하지 않음이 확인된 유일한 항목.
- 아래 둘은 **실측이 아니라 2026-07-25에 새로 정한 기본값**이다(해당 사례가 발행본에 없었다).
  실제 사례가 처음 나오면 그대로 갈지 사용자에게 확인한다.
  - 언어 런타임 부산물(C++ 값 전달 복사, Java 오토박싱 등)은 제외 — 시그니처의 부산물이지
    알고리즘의 선택이 아니다.
  - 재귀는 **호출 스택 깊이를 포함**(깊이 $N$ 재귀는 $O(N)$). 발행본 14개에 재귀 풀이가
    하나도 없어 선례가 없다.
- 이 관례로도 값이 갈리면 **단정하지 말고 두 관점을 근거와 함께 제시**한다. 관례가 덮는 범위
  안에서는 시간복잡도처럼 확정적으로 적는다.

### 구조
- front matter / 섹션 / 코드블록 언어태그 등 템플릿 준수. (Phase 1이 잡은 건 중복 지적 불필요)

- Java `BufferedWriter` vs `StringBuilder`+`System.out` (동등)

- 통과 코드의 이론적 worst-case(문제 제약 밖 "만약 N이 더 크면")

  dead code로 지적 금지(진짜 미사용은 사용자가 개별 `include`한 뒤 안 쓴 경우로 한정)

## Phase 3. 메인 에이전트 판정

모든 에이전트 완료 후, 메인이 각 포스트에 등급을 부여한다. **에이전트 분석을 1차 자료로 신뢰하되,
등급을 가르는 주장은 원본으로 재확인한다** — 통째로 받아쓰지도(rubber-stamp), 통째로 재수행하지도(전체 재trace) 않는다.

### 절대 금지 (HARD STOP)
1. **코드 정확성·복잡도를 원본 확인 없이 에이전트 말만으로 등급** — 이 둘은 등급을 직접 가르므로 반드시 원본 대조.
   (에이전트가 "정확/지적 없음"이라 해도 코드·복잡도는 메인이 원본을 본다.)
2. 에이전트 "지적 없음" → 그대로 상위 등급 (rubber-stamp)
3. 기억으로 문제/복잡도 판단 — 불확실하면 확인(WebFetch)
4. 같은 시리즈라고 일괄 동일 등급
5. 분포 맞추려 등급 인위 조정

### 판정 절차 (파일마다)
- **(a) 에이전트 분석 정독** — 그 포스트에 대한 아이디어·코드·복잡도·구조 지적을 먼저 읽는다.
- **(b) 등급-결정적 재확인 (원본 대조)** — 등급을 가르는 지점만 원본으로 직접 확인한다. 전체 라인 trace가 아니라 집중 확인:
  - **코드 정확성**: 핵심 로직·루프 경계·타입·명백한 엣지(N=1·빈 입력·오버플로우)를 원본 코드로 확인. 에이전트의 정확/버그 주장을 검증.
  - **복잡도**: 표가 차 있으면 값이 코드와 맞는지 원본 대조. **표가 비어 있으면 원본 코드로 값을 확정한다**
    — 이 값이 Phase 3.5에서 파일에 기록된다. 기준은 Phase 2 프롬프트의 **공간복잡도 관례**를 그대로 쓰고,
    관례로도 갈리는 경우만 단정을 피해 사용자에게 판단을 넘긴다.
  - 에이전트 값과 메인 값이 **다르면 자동으로 한쪽을 택하지 말고 양쪽을 병기해 사용자에게 묻는다.**
    (같은 대화 안이라 두 계산이 완전히 독립적이진 않다. 그래도 값이 갈렸다는 사실 자체는 확인 가치가 있다.)
- **(c) 아이디어 비판 평가** — 에이전트 분석 + 필요시 원본으로, 핵심 통찰을 설명하는지 판단. 비-trivial인데 한 줄이면 보강 필요.
- **(d) 대안 풀이 판단** — 에이전트가 제시한 대안이 진짜 점근적 개선(예: $O(N^2)\to O(N\log N)$)인지, 아니면
  취향·미세 최적화 수준인지 가른다. 전자는 "진짜 개선점"으로 B 사유가 될 수 있고(등급 정의 참고),
  후자는 등급에 영향 없이 개선점 노트로만 남긴다. 42576/1845 사례처럼 관용·동치인데 에이전트가
  과하게 지적한 경우 기각하고 근거를 보고에 남긴다.
- (b)에서 에이전트 분석과 원본이 어긋나면 **원본을 따르고**, 에이전트가 놓쳤거나 과했음을 보고에 남긴다.

### 등급 정의
| 등급 | 기준 |
|------|------|
| **S** | 완벽. 뛰어난 설명 + 코드. trivial 문제엔 거의 없음 |
| **A** | 깔끔. 정확한 코드·적절한 설명·진짜 흠 없음 |
| **B** | 무난하나 *진짜* 개선점 있음(vague한 핵심 단계, 복잡도 불일치, 핵심 누락) |
| **C** | 수정 필수(코드 오류, idea 명백한 오류, 미기입 스켈레톤) |

- **복잡도 표 미기입: `fill`이 성공했으면 등급에 반영하지 않는다**(등급은 *채운 뒤 상태* 기준).
  **빈 채로 남았으면 종전대로 C다** — 3.5를 건너뛰었든, `fill`이 거부했든, 사용자가 승인하지 않았든
  마찬가지. `/publish`는 복잡도를 검사하지 않으므로 **등급이 유일한 방벽이다.** 판단 근거는 `fill`의
  성공 출력이지, 채웠다는 기억이 아니다.
- 사용자가 직접 적은 값이 코드와 **틀린** 경우는 채우기 대상이 아니라 지적 대상이고 B 사유다.
  (`fill`도 이미 채워진 표는 거부한다.)
- 코드 버그(오답·오버플로우·타입) → **C**
- 핵심 근거 누락으로 포스트만으로 이해 불가 → **B 이하**
- 사소한 지적(변수명 등)만 → **A** 유지
- 기본값은 "A 자격을 *증명*"이지 "흠 없으면 A"가 아니다.

### 재리뷰 일관성
같은 대화에서 파일 미변경 → 이전 등급 유지. 변경하려면 근거 필수(수정으로 지적 해소 / 관례 변경).

## Phase 3.5. 미기입 복잡도 표 채우기

Phase 1이 `복잡도 표 미기입`으로 플래그한 포스트가 없으면 건너뛴다.

1. **확인받는다.** Phase 3에서 확정한 값을 한 표로 모아 보여준다(근거를 붙여 눈으로 검증되게).
   에이전트 값과 메인 값이 갈렸으면 **양쪽을 병기**하고 어느 쪽을 쓸지 묻는다.
   ```
   | 문제 | 풀이 | 시간 | 공간 | 근거 |
   |------|:----:|:----:|:----:|------|
   ```
2. **승인 후 포스트마다 실행한다.** 접근이 여러 개면 `### 1. 풀이`, `### 2. 풀이` 순서대로 쌍을 넘긴다.
   ```
   python3 .claude/skills/review/review_check.py fill <번호> <시간> <공간> [<시간> <공간> ...]
   ```
   값은 LaTeX로 넘긴다(`"O(N \log N)"`). `$…$`는 스크립트가 붙이므로 있어도 없어도 된다.
3. **직접 Edit하지 않는다.** 파일 쓰기는 전부 스크립트가 한다 — 빈 행 위치 판별, 개수 검증,
   순서 대응, 이미 채워진 표·발행본 거부, 기록 후 재검사까지. 거부 메시지가 나오면 그대로 사용자에게
   전달하고 멈춘다. 우회하려 Edit을 쓰지 말 것.

## Phase 4. 결과 보고
1. **에이전트 분석을 청크 순서대로, 요약하지 말고 원문 그대로 전달한다.**
   메인이 압축하면 사용자는 에이전트가 *실제로 무엇을 검증했는지*(트레이스한 반례, 확인한
   엣지 케이스, 복잡도 근거)를 볼 방법이 없어져 "한 줄 요약만 보인다"는 상태가 된다.
   에이전트 출력은 메인 컨텍스트에만 남고 사용자에겐 대조할 원본이 없으므로, 요약은
   검증 가능성을 통째로 없앤다. 메인의 판정 근거는 원문 **뒤에 덧붙이는** 것이지
   원문을 대체하지 않는다.
2. 등급표:
```
| # | 문제 | 등급 | 발행 판단 | 주요 지적사항 |
|---|------|:----:|----------|--------------|
```
   - 발행 판단: **S/A → 발행 가능**, **B → 개선 권장**, **C → 수정 필수**
3. B/C가 있으면 무엇을 고쳐야 하는지 요약.
4. Phase 3.5에서 채운 게 있으면 **어느 포스트에 무슨 값을 썼는지 목록으로 남긴다**(사용자가 확인만 하면 되도록).
   기록을 건너뛴 항목이 있으면 그 이유도 함께.
