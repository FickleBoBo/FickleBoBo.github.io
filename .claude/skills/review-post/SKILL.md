# review-post — PS 포스트 완성도 리뷰

## 실행

1. `python3 <review-code 스킬의 base directory>/scripts/chunk_drafts.py --mode post [경로 ...]`로 대상 드래프트를 청크로 분할(스크립트는 `review-code` 스킬 소유 — 그대로 가져다 씀, `sync`가 `ps`의 스크립트를 그대로 쓰는 것과 같은 패턴). 사용자가 특정 포스트를 지목하면 `_drafts/{platform}/`에서 그 포스트에 해당하는 파일을 찾아 절대경로로 넘김 — 안 지목하면 인자 없이 호출(전체 배치).
2. 청크마다 백그라운드 서브에이전트(`review-code`와 동일한 방식: Agent 도구, subagent_type 생략, `run_in_background: true`) 하나씩 dispatch. **`isolation: "worktree"`는 쓰지 않음** — 이 스킬은 드래프트 `.md` 파일을 직접 Edit하므로, 격리된 워크트리에서 실행하면 수정 내용이 그 격리 복사본에만 남고 실제 레포에는 반영되지 않음(읽기만 하는 `review-code`는 이 문제 없음, worktree 써도 무방). 프롬프트엔 **이 SKILL.md 경로 + 아래 "처리 절차"/"출력 형식"을 따르라는 지시 + 배정된 드래프트 파일 경로 목록**만 전달(체크리스트를 프롬프트에 옮겨적지 않음)
3. 모든 서브에이전트가 끝나면 드래프트별 결과 + 등급 + 전체 배치 요약 표로 보고

**기본은 인자 없이 전체 배치.** 스킵 조건은 없음 — `## 1. 아이디어`가 비어있어도 review-post가 직접 채우는 게 정상 동작이라(아래 "1단계" 참고), `review-code` 이후로는 항상 전체 대상.

**이미 발행된 `_posts/`도 대상이 될 수 있음(2026-08-27 최초 적용)**: `sync`로 이미 발행된 포스트의 코드가 갱신된 뒤, 그 변경이 코드-설명 정합성에 영향을 줄 만한지 재확인하고 싶을 때 `_posts/` 절대경로를 그대로 넘겨도 됨 — 1단계는 "채움"이 아니라 "일치 여부 검증" 위주로 자연히 진행됨(이미 다 채워져 있으므로). 이런 상황에서 대상을 전체가 아니라 일부만 고를 땐, **알고리즘/로직이 실제로 바뀌었거나 아이디어가 통째로 재작성된 경우만 재리뷰 가치가 있음** — 수식 표기 통일, 코드 스타일 한 줄 변경, 단어 하나 수준 표현 다듬기는 코드-설명 정합성에 영향이 없어 스킵. 선별 기준 자체가 판단이 갈리는 지점이라 어떤 파일을 골랐는지는 사용자에게 먼저 확인받을 것.

## 처리 절차 (드래프트 1개당)

**1단계 — 빈 필드 채우기** (이미 채워져 있으면 그대로 둠, 절대 덮어쓰지 않음 — 사람이 쓴 프로즈를 함부로 안 건드린다는 `sync`와 같은 원칙):

- `description`: 완성된 본문 기준으로 TL;DR 작성. `title`에 이미 있는 정보(언어 브라켓 `[Java][C++]` 등)는 반복하지 않음 — 중복이라 정보량 없이 글자수만 차지함. **문장 종결은 명사형으로 고정**(`~를 구하는 문제.`/`~하는 문제.` 등) — `~한다`/`~구한다`처럼 서술형으로 끝내지 않음(홈 목록 미리보기에서 라벨처럼 훑어보기 좋은 쪽이 서사형보다 이 자리에 맞음, 2026-08-24 확정). front matter `tags`에 이미 `warm up`이 붙어있으면(`review-code` 태그 후보를 사용자가 적용한 경우) `~워밍업 문제.`로 종결 — 다른 태그는 이 규칙 대상 아님(태그명을 description에 그대로 노출하는 건 `warm up`에 한정, 남용 방지)
- `1. 아이디어`: 보통 사람이 직접 씀. 비어있으면 코드를 읽고 이해해서 review-post가 대신 채움 — **항상 원문(플랫폼 공식 문제 페이지)을 직접 재확인**하고(이미 아는 유명한 문제여도 예외 없음 — 제약조건 같은 구체적 수치를 잘못 기억해서 조용히 틀리는 걸 막기 위함), 기존 컨벤션(표 없이 서술 중심, `ps/SKILL.md`의 "아이디어 섹션" 참고)대로 채움. **제약조건에 지수/첨자 표기(`$10^k$`류)가 있어 보이면 WebFetch 결과를 그대로 믿지 말 것** — 마크다운 변환 과정에서 위첨자가 뭉개져 `10^l`과 `10l`을 구분 못 하는 경우가 실제로 있었음, `curl -s <url> | grep -o '<sup>[^<]*</sup>'`처럼 원본 HTML의 `<sup>`/`<sub>` 태그로 직접 확인할 것. 원문 번역에 가깝게 쓰지 않도록 주의(저작권 리스크) — 다만 지금은 느슨하게 다루는 영역이라 과하게 방어적인 장치는 안 둠. **"처음엔 이렇게 생각했는데" 같은 시행착오 서술은 지어내지 않음** — Claude가 실제로 겪은 게 아니므로, 시행착오 없이 바로 최종 아이디어부터 씀. **커뮤니티에서 실제로 쓰이는지 확인 안 된 용어를 서술 편의상 지어내 인용하지 않음** — "~라고 불린다"류 표현은 확실치 않으면 검증하거나 그냥 서술적 표현으로 순화. **언어별 구현 차이(이 언어엔 이 내장 함수가 있어서, 저 언어는 반복문으로 대신 등)를 여기서 비교 서술하지 않음** — 알고리즘/풀이 레벨만 쓰고, 그런 디테일은 `3. 코드` 섹션 쪽(코드 블록 아래 설명, 아래 참고)으로 보냄
- `2. 복잡도` 표: 빈 셀만 코드 기준으로 채움(이미 채워진 셀은 그대로). `$O(N \log N)$`처럼 `$...$`로 감싸고 변수는 대문자로 씀($N$, $M$ 등) — 맨 텍스트로 `O(n log n)`이라고 쓰지 않음. $O(1)$이 아니면 표 아래에 그 변수가 뭘 가리키는지 짧게 프로즈로 덧붙임(`ps/SKILL.md`의 "복잡도 섹션" 참고 — 예전엔 이 설명이 아이디어 섹션에 있었음)
- `math` 플래그: `ps` 스킬이 스캐폴드 생성 시점에 이미 `true`로 결정론적으로 채움(복잡도 표가 항상 `$...$` 수식을 쓰므로) — 여기서 다시 판단할 필요 없음, 혹시 `false`로 바뀌어 있으면 고침
- `mermaid` 플래그: 최종 본문 기준으로 옳게 세팅(현재 값과 무관하게, 맞으면 냅두고 틀리면 고침)
- mermaid 다이어그램: Claude가 직접 채운 `1. 아이디어`엔 필요하다 판단되면 자율적으로 삽입. 사람이 이미 쓴 프로즈에는 이 배치 리뷰 패스에서는 삽입하지 않음 — 사용자가 대화 중 명시적으로 요청했을 때만(요청은 이 스킬 실행과 별개의 대화 흐름)
- `3. 코드` 섹션: 언어별로 특징적으로 설명할 게 필요하다고 판단되면 `### 풀이 N` 헤딩 바로 아래(공통 설명) 또는 각 코드 블록 바로 아래(그 언어 전용 설명)에 직접 프로즈를 넣어도 됨(`ps/SKILL.md`의 "코드 섹션 다중 접근" 참고). 이미 사람이 써둔 설명은 그대로 두고 덮어쓰지 않음

**2단계 — 전체 평가** (1단계에서 방금 채운 것 포함, 예외 없이 전부 평가 — "방금 내가 쓴 거니 봐주기" 없음):

- `1. 아이디어`/회고/참고: 명확성, 논리 흐름
- 스타일 컨벤션: 문제에서 나온 변수/특수 용어 백틱 감싸기, 복잡도 수식(`$O(N \log N)$` 등, 변수 대문자) 표기, 맞춤법/문법
- 코드-설명 일치: 아이디어에서 말한 로직과 실제 코드가 맞는지, 복잡도 표 값이 실제 코드와 맞는지. **표에 쓴 변수 기호가 실제로 복잡도를 좌우하는 값인지도 확인** — 파라미터가 여럿이면 먼저 등장한 것에 습관적으로 $N$을 붙이지 말고, 코드가 실제로 순회/복사하는 대상이 뭔지 봐서 고를 것(예: 전체 문자열 중 일부만 잘라 쓰면 전체 길이가 아니라 그 부분 길이가 변수가 돼야 함). **수식/코드 인덱싱을 옮겨 쓸 때 오프셋(0-indexed vs 1-indexed) 불일치 특히 주의** — `dp` 배열은 1-indexed로 서술하면서 원본 배열은 0-indexed 그대로 쓰는 식으로 기준이 갈리면, 백틱 수식이 실제 코드 리터럴과 정확히 안 맞을 수 있음(예: 서술은 `money[i]`인데 실제 코드는 `money[i - 1]`)
- **등급**: **A가 기본값** — 정확성 전제 하에 위 1~2단계의 컨벤션·완성도 조건을 전부 충족하면 A. **S는 A 조건 충족에 더해 이 문제만의 통찰이 있는 경우로 한정** — 왜 이 방법이 성립하는지 단순 나열을 넘어 실제로 이해를 돕는 설명, 또는 놓치기 쉬운 함정·엣지케이스를 짚어주는 등 기본 충족을 넘어서는 무언가가 있어야 함(빠짐없이 다 썼다는 것만으론 S 아님 — 흔해선 안 됨, 2026-08-24 확정: 이전엔 "구글에서 경쟁력 있는 완성도"처럼 절대/상대 기준이 불명확해 S/A 판단이 자주 갈렸음). B(컨벤션·완성도 조건 중 일부가 부족)/C(다수 부족하거나 코드-설명 불일치 등 심각한 문제). **등급은 이 스킬의 스코프(프로즈/구조 완성도)만으로 매김** — 코드 자체 품질(더 나은 알고리즘 여부 등)은 `review-code`의 별도 몫이라 여기서 반영하지 않음(review-code 결과를 이 스킬은 모른 채 완전히 독립적으로 돌아감 — 둘을 연달아 돌려도 서로의 판단을 참조하지 않음)

## 규칙

- **PS 레포 소스 코드는 절대 안 건드림** — `review-code`와 동일 원칙. 애초에 이 스킬은 드래프트 `.md` 파일 하나만 보고 끝나서 PS 레포 경로 자체에 접근하지 않음
- **태그는 여기서 안 다룸** — `review-code`가 후보만 언급, 실제 적용은 사용자가 대화 중 요청했을 때
- **게이트 아님** — 등급이 낮아도 `publish`는 막지 않음, 참고용 피드백일 뿐. 결과는 대화로만 전달, 파일로 저장 안 함(파일로 남기면 다음 수정 한 번에 바로 stale해지는 정보라 저장 실익이 없음)
