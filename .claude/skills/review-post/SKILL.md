# review-post — PS 포스트 완성도 리뷰

`_drafts/`의 PS 포스트를 완성도 관점에서 평가하고, 비어 있는 `1. 아이디어`/복잡도 셀 등을 직접 채운다. 프로즈·표기 규칙은 [`STYLE.md`](STYLE.md)가 정본이다.

`review-post`가 채우는 프로즈(`1. 아이디어`, 코드 블록 설명)는 **사용자가 다시 쓸 초안**이다 — 특히 `1. 아이디어`는 완성된 통찰을 목표로 하지 않고 핵심 관찰과 꼭 필요한 논증만 담은 뼈대를 만든다. 등급도 이 초안의 문장력·통찰을 평가하지 않는다(아래 `### 등급`). 복잡도 표는 반대로 사실이라 누가 채우든 같은 값이 나와야 하며, `STYLE.md`의 절차·예시가 그걸 강제한다.

## 오케스트레이터 (서브에이전트는 이 절을 건너뜀)

1. `python3 <review-code 스킬의 base directory>/scripts/chunk_drafts.py --mode post [경로 ...]`로 대상 드래프트를 청크로 분할(스크립트는 `review-code` 스킬 소유 — 그대로 가져다 씀, `sync`가 `ps`의 스크립트를 쓰는 것과 같은 패턴). 사용자가 특정 포스트를 지목하면 `_drafts/{platform}/`에서 매칭해 절대경로로 넘기고, 안 지목하면 인자 없이 호출(전체 배치).
2. **dispatch 전에 대상 드래프트 스냅샷을 뜬다** — `_drafts/`는 git 미추적이라 `git diff`가 서브에이전트의 내용 변경을 못 잡는다. 대상 `.md`를 전부 스크래치패드 디렉토리로 복사(`cp "<드래프트>" "<스크래치패드>/reviewpost-snap/"`, 파일명 유지)해두고, 취합 단계에서 이 사본과 `diff -u`로 대조한다. 스냅샷 없이 돌리지 않는다.
3. 청크마다 백그라운드 서브에이전트 하나씩 dispatch: Agent 도구, `subagent_type` 생략, `run_in_background: true`, **`isolation: "worktree"`는 쓰지 않음**(이 스킬은 드래프트 `.md`를 직접 Edit하므로, 격리 워크트리에서 돌면 수정이 그 복사본에만 남고 실제 레포에 반영되지 않음). 프롬프트엔 다음만 전달:
   - 이 `SKILL.md` 경로 + [`STYLE.md`](STYLE.md) 경로 — **둘 다 읽고 `## 처리 절차`·`## 출력 형식`을 따르라**고 지시
   - 그 청크에 배정된 드래프트 파일 절대경로 목록
   - 체크리스트/규칙 텍스트를 프롬프트에 옮겨적지 않음 — 위 두 파일이 유일한 출처(안 그러면 나중에 갈라짐)
4. 모든 서브에이전트 종료 후 취합: 드래프트별 결과표 + 등급 + `심화 관찰`(나온 것만) + 배치 요약표.
   - 취합 전 **2단계 스냅샷과 `diff -u`로 각 드래프트의 실제 변경을 한 줄까지 대조 확인**(`_posts/` 대상이면 `git diff`도 병행) — 서브에이전트 자기 보고("Edit 안 함", "복잡도 표만 고침")를 그대로 믿지 않음(read-only 규칙을 어기고 몰래 Edit하거나, 표 외 프로즈를 손댄 사례 있었음). **허용되는 변경은 빈 셀·빈 `## 1. 아이디어`·빈 코드 설명 신규 작성과 접근 이름뿐** — 사람이 쓴 프로즈(특히 `## 1. 아이디어`)에 한 글자라도 변경이 있으면 되돌리고 리포트로 옮긴다.
   - 서브에이전트 서술 중 "이 코드는 X를 한다"처럼 구체적 구현을 근거로 든 지적은 **최소 1~2건 직접 파일을 Read**해 스팟체크(요약 과정에서 왜곡되는 경우 있음).
   - `심화 관찰`의 논증 엄밀성 지적은 **해당 문단을 직접 읽고 타당한지 확인**한 뒤 취합 — 서브에이전트가 없는 구멍을 지어내거나 맞는 논증을 트집잡는 경우가 있음(스팟체크와 같은 이유).

**대상은 사용자가 지목한 포스트.** 리워크(일괄)가 끝난 뒤로는 하루 한두 개를 그날그날 처리하는 흐름이다 — 지목된 포스트는 하나도 빠짐없이 아래 절차를 전부 밟는다. 트리비얼해 보여도 선별·축약하지 않는다(포스트마다 정성껏). 인자 없이 호출하면 `_drafts/{platform}/` 전체가 대상(초기 일괄용, 지금은 드묾).

**이미 발행된 `_posts/`도 대상 가능**: `sync`로 코드가 갱신된 뒤 코드-설명 정합성을 재확인하거나 발행분을 손볼 때. `_posts/` 절대경로를 넘기며, 이 경우 1단계는 자연히 검증 위주다(빈 필드가 없음).

## 처리 절차 (드래프트 1개당 — 서브에이전트 몫)

### 1단계 — 빈 필드 채우기

**사람이 쓴 프로즈는 1단계에서 손대지 않는다** — `## 1. 아이디어` 본문이 대표적이고, 사람이 직접 쓴 코드 블록 설명·복잡도 변수 설명도 포함한다. 명백한 오타·맞춤법, 평문·백틱·수식 오분류까지 전부 **2단계에서 위치와 함께 리포트만** 하고 반영은 사용자가 한다 — 사용자의 글이라 최종 결정권을 넘긴다.

예외는 **agent가 이번 실행에서 새로 채운 프로즈**다(비어 있던 `## 1. 아이디어`, 새로 쓴 코드 블록 설명) — 이건 agent가 STYLE대로 바로 다듬는다. `## 2. 복잡도`의 빈 셀은 사실이므로 채운다(채워진 셀·변수 설명은 그대로, 값이 틀렸으면 2단계 리포트).

어투·논리 흐름·구조에 대한 이견도 고치지 말고 2단계에서 리포트만.

- **`description`**: PS 포스트에서 폐기된 필드. `description:` 줄이 front matter에 남아 있으면(옛 드래프트·백업) 그 줄을 삭제한다. 새로 만들지 않는다.
- **`1. 아이디어`**: 보통 사람이 직접 씀 — 채워져 있으면 그대로 두고 평가만(위 참고). 비어 있으면 코드를 읽고 이해해서 `STYLE.md`의 "`## 1. 아이디어`" 규칙대로 채운다 — **사용자가 다시 쓸 초안**이므로 뼈대만: 분량은 난이도에 비례(트리비얼 워밍업은 친근한 한 줄 재진술로 끝내도 됨, 비자명한 문제는 첫 문장부터 crux), 금지 패턴(정리-증명 어투·코드 나레이션 문단화) 회피. 원문 직접 재확인, 지수 표기 `curl` 확인, 시행착오 지어내지 않기, 미검증 용어 인용 금지 등 나머지 규칙도 전부 `STYLE.md`.
- **`2. 복잡도` 표**: 빈 셀만 코드 기준으로 채운다(채워진 셀은 그대로). 복잡도는 사실이라 누가 채우든 같은 표가 나와야 한다 — `STYLE.md`의 "지배 변수 고르기" 절차와 "반복 형태별 고정 예시"를 그대로 따르고, `$...$` 표기·복잡도 변수 대문자 승격(아이디어 본문 수식은 소문자 유지)·변수 설명 프로즈 포맷도 `STYLE.md`.
- **다중 접근 이름**: `### 풀이` 헤딩이 2개 이상인데 이름이 안 붙어 있으면(스캐폴드는 `### 풀이 1`, `### 풀이 2`처럼 번호만 만든다) 각 접근에 이름을 붙인다 — 코드 섹션 헤딩과 `## 2. 복잡도` 표 "접근" 열 모두. 규칙은 `STYLE.md`의 "다중 접근 — 접근 이름". 붙이기 전에 `grep -rl "### 풀이 1" _posts/`로 같은 구조의 기존 포스트가 어떤 이름을 썼는지 대조해 고정 어휘를 재사용한다. 접근이 하나뿐이면 건드리지 않는다.
- **`math` 플래그**: `ps`가 스캐폴드 시점에 항상 `true`로 채움 — 여기서 다시 판단할 필요 없고, 혹시 `false`로 바뀌어 있으면 고침.
- **`mermaid` 플래그**: 최종 본문 기준으로 옳게 세팅(맞으면 두고 틀리면 고침).
- **mermaid 다이어그램**: Claude가 직접 채운 `1. 아이디어`엔 필요하다 판단되면 자율 삽입. 사람이 이미 쓴 프로즈엔 이 배치 패스에서 삽입하지 않음 — 사용자가 대화 중 명시적으로 요청했을 때만.
- **`3. 코드` 블록 설명**: `STYLE.md`의 "`## 3. 코드` — 블록 설명 프로즈" 참고. 필수 아님 — 대부분의 포스트는 이 프로즈가 없다.

### 2단계 — 전체 평가

1단계에서 방금 채운 것 포함, 예외 없이 전부 평가한다("방금 내가 쓴 거니 봐주기" 없음). **설명이 그럴듯한지가 아니라 실제 코드와 맞는지** 코드를 직접 열어 대조하고, 직전 배치에서 지적됐던 축으로 점검 범위를 좁히지 말고 매번 아래 전체를 본다.

- **`1. 아이디어`/회고/참고**: 사람이 쓴 것이면 명확성·논리 흐름, 다중 접근이면 뒤 접근의 도입 이유가 있는지(`STYLE.md`의 `## 1. 아이디어`)를 본다. 비자명한 문제인데 "무엇"만 요약하고 "왜"가 없으면 지적하되, **트리비얼 워밍업의 짧은 재진술은 지적하지 않는다**(친근한 한 줄이 정상 — `STYLE.md` 금지 패턴 참고). 문장력·친근한 어투는 평가 대상이 아니다. **이번 실행에서 `review-post`가 채운 아이디어는 통찰·완성도로도 평가하지 않는다**(방금 쓴 초안이라 순환) — 아래 "원문·코드 대조"의 사실 정합성과 표기만 본다.
  - 여기 2단계에서 보는 건 "왜가 있나 / 그 왜가 코드와 맞나"까지고, 그게 등급을 좌우한다. 논증이 빈틈없는지(케이스 분석 완결성, 교환 논증 엄밀성 등)·서술이 레퍼런스로 삼을 만큼 탄탄한지는 아래 `### 심화 관찰`에서 별도로 본다 — 등급엔 안 들어가고 관찰로만 낸다.
- **표기 컨벤션**: `STYLE.md` 기준 — 평문·백틱·수식 선택(세 프로즈 자리 모두: 아이디어 본문, 복잡도 변수 설명, 코드 블록 설명), 복잡도 수식 표기(변수 대문자, `\times`, 공백, 콤마), 맞춤법/문법. 사람이 쓴 자리의 이슈는 고치지 말고 위치와 함께 나열(1단계 참고), agent가 채운 자리는 이미 STYLE대로 썼어야 한다.
- **원문·코드 대조**: 평가 대상이 채워져 있든 비어 있든 **문제 원문(플랫폼 공식 페이지)을 직접 연다** — 유명한 문제여도 예외 없음. 조회 방법은 플랫폼마다 다르다 — `review-code/SKILL.md`의 "플랫폼별 조회 방법"을 그대로 따른다(Programmers WebFetch + 지수 표기는 `curl`+`<sup>`, LeetCode는 GraphQL `curl`, Codeforces 지문은 이 환경에서 불가하니 사용자에게 요청).
  - 아이디어·복잡도가 인용·전제하는 제약 수치("`n ≤ 100{,}000`이라...", "좌표는 두 개뿐이라...", "문자는 소문자뿐")가 실제 원문 제약과 맞는지 — 사람이 수치를 잘못 기억해 쓴 걸 여기서 잡는다.
  - 아이디어에서 말한 로직 ↔ 실제 코드.
  - 복잡도 표 값 ↔ 실제 코드.
  - 복잡도 표의 변수 기호가 **실제로 복잡도를 좌우하는 값**인지 — 파라미터가 여럿이면 먼저 등장한 것에 습관적으로 $N$을 붙이지 말고, 코드가 실제로 순회/복사하는 대상을 본다(전체 문자열 중 일부만 잘라 쓰면 전체 길이가 아니라 그 부분 길이가 변수).
  - 인덱싱 오프셋(0-indexed vs 1-indexed) 불일치 주의 — 서술은 `money[i]`인데 실제 코드는 `money[i - 1]`인 식으로 기준이 갈리면 백틱 수식이 코드 리터럴과 안 맞음.

### 심화 관찰 (비자명 포스트만 — 등급과 무관)

발행된 포스트는 전부 레퍼런스다. `publish` 전 자동 게이트가 이 2단계까지뿐이라, 사람이 쓴 논증·서술을 한 겹 더 본다 — 사용자가 아이디어를 직접 쓰는 게 기본이므로 비자명 포스트에선 이 절이 사실상 메인 작업이다. **등급(S/A/B/C)은 절대 안 건드린다** — 관찰만 내고 반영은 사용자가 결정한다.

**작동 조건 (하나라도 해당):**

- `1. 아이디어`가 단순 재진술이 아니라 실제로 뭔가를 설명·논증한다(정당성 논증: 그리디·불변식·케이스 분할·상한·"왜 이게 충분한가")
- `### 풀이` 헤딩이 2개 이상이고 접근 간 트레이드오프가 있다
- `## 회고`/`## 참고` 섹션이 있다

위 어디에도 안 걸리는 트리비얼 워밍업("~하면 되는 간단한 문제다" 류)은 이 절을 **통째로 건너뛴다** — 관찰 0줄, 리포트에 섹션 자체를 안 넣는다.

**대상은 사람이 쓴 프로즈만.** 이번 실행에서 `review-post`가 채운 `1. 아이디어`/코드 설명은 건너뛴다(방금 쓴 초안이라 순환).

**보는 축 (우선순위 순):**

1. **논증 엄밀성** — 케이스 분석이 실제로 exhaustive한가(빠진 경우), 그리디·교환 논증에 "이게 최적/전부"라는 근거가 있는가, 무언의 가정이 있는가, "왜 이 범위/횟수면 충분한가"(√n 상한 등)가 서술됐는가.
2. **추론 명확성** — 논리 사슬에 독자가 못 따라갈 비약이 있는가. 결론이 근거보다 앞서 나오는가.
3. **통찰 공백** — 설명이 "무엇"은 주는데 독자가 여전히 "왜 X이고 Y가 아닌가"를 궁금해할 지점. **여기까지만** — "이런 관점을 덧붙이면 좋다" 식 필러 제안은 하지 않는다(공백을 짚기만).
4. **문장력** — 명백한 비문·중의성만. "더 우아하게 쓸 수 있다" 류는 하지 않는다.

각 관찰은 "어느 문장/문단의 무엇이 왜 아쉬운지" 한두 줄로 구체적으로. 추상적 총평("전반적으로 더 깊었으면") 금지. 관찰이 없는 축은 리포트에서 줄을 안 쓴다.

### 등급

정확성 전제 하에 **검증 가능한 축**만으로 매긴다 — 코드-설명 사실 정합성, 표기 컨벤션, 구조 완결성(빈 필드 없음). 프로즈의 문장력·통찰·논증 엄밀성은 등급 대상이 아니다(LLM 초안이든 사람 글이든) — 비자명 포스트면 위 `### 심화 관찰`에서 등급과 별개로 관찰만 낸다.

| 등급  | 기준                                                                                                                                                                      |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S** | **사람이 직접 쓴** 아이디어에 이 문제만의 통찰(왜 이 방법이 성립하는지, 놓치기 쉬운 함정)이 있고 나머지도 A. `review-post`가 채운 초안 단계에선 안 나온다 — 흔해선 안 됨. |
| **A** | (기본값) 코드-설명 불일치 없음, 표기 이슈 없음, 빈 필드 없음.                                                                                                             |
| **B** | 표기 이슈 1~2건, 또는 경미한 코드-설명 불일치.                                                                                                                            |
| **C** | 표기 이슈 3건 이상, 또는 로직 수준의 코드-설명 불일치(아이디어가 설명한 알고리즘과 코드가 실제로 다름).                                                                   |

사람이 쓴 `1. 아이디어`의 표기 이슈로 B/C가 나오는 건 정상이다 — agent가 고치지 않고 리포트만 하므로(1단계 참고) 이 신호가 등급에 그대로 남는다. "사용자가 다듬을 거리 N건"을 뜻하지 품질 실패가 아니다.

코드 자체 품질(더 나은 알고리즘 여부 등)은 `review-code`의 몫 — 두 스킬은 서로의 판단을 참조하지 않는다.

## 규칙

- **PS 레포 소스 코드는 절대 안 건드림** — 이 스킬은 드래프트 `.md` 파일 하나만 보고 끝나 PS 레포 경로에 접근하지 않음.
- **태그는 여기서 안 다룸** — `review-code`가 후보만 언급, 적용은 사용자가 대화 중 요청했을 때.
- **게이트 아님** — 등급이 낮아도 `publish`는 막지 않음. 결과는 대화로만 전달, 파일로 저장 안 함(다음 수정 한 번에 stale해져 저장 실익이 없음).
