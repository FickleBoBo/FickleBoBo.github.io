# review-code — PS 포스트 코드 리뷰

## 실행

1. `python3 <이 스킬의 base directory>/scripts/chunk_drafts.py --mode code [경로 ...]`로 대상 드래프트를 청크로 분할. 사용자가 "이 포스트들 코드 리뷰해줘"처럼 특정 포스트를 지목하면 `_drafts/{platform}/`에서 그 포스트에 해당하는 파일(제목/번호로 매칭)을 찾아 절대경로로 넘김 — 안 지목하면 인자 없이 호출(전체 배치)
2. 청크마다 백그라운드 서브에이전트(Agent 도구, subagent_type 생략 = general-purpose, `run_in_background: true`) 하나씩 dispatch. 프롬프트엔 **이 SKILL.md 경로 + 아래 "체크 항목"/"출력 형식"을 따르라는 지시 + 그 청크에 배정된 드래프트 파일 경로 목록**만 전달 — 체크리스트 텍스트를 프롬프트에 옮겨적지 않음(이 파일이 유일한 출처, 안 그러면 나중에 둘이 갈라짐)
3. 모든 서브에이전트가 끝나면 결과를 취합해서 드래프트별 표 + 전체 배치 요약 표로 보고. **취합 전 최소 1~2건은 실제 드래프트 파일을 직접 Read해서 서브에이전트 서술을 스팟체크할 것** — 특히 "이 코드는 X를 쓴다"처럼 구체적 구현을 근거로 드는 지적(네이밍/매직넘버/특정 API 미사용 등)은 서브에이전트가 요약 과정에서 부정확하게 왜곡할 수 있음(실사례: 실제로는 `c - 'a' + 'A'` 문자 리터럴 산술인데 "±32 매직넘버"로 서술). 또한 **서브에이전트의 자기 보고("제안만 했다", "Edit 안 함")를 그대로 믿지 말고 `git status`/`git diff`로 실제 파일 변경 여부를 대조 확인할 것** — "PS 레포 소스 파일 절대 Edit 안 함" 규칙(아래)을 명시했음에도 드래프트 `.md` 파일 프로즈를 몰래 Edit하고 보고서엔 언급하지 않은 사례가 실제로 있었음

**기본은 인자 없이 전체 배치.** `_drafts/{platform}/`(platform ∈ `PLATFORM_MAP`) 전체가 대상 — 프로즈 완성도와 무관하게 전부(코드만 보는 리뷰라 프로즈 상태를 가릴 이유가 없음, `review-post`와 다른 점). 사용자가 특정 포스트를 지목하면 그 포스트들만 대상으로 함(위 1번 참고).

## 청크 분할

`chunk_drafts.py`가 결정론적으로 처리: 드래프트 최대 4개, 총 줄수 약 1200줄 중 먼저 도달하는 조건에서 그룹을 끊는 그리디 패킹. 개수 상한을 두는 이유는 LLM이 한 번에 너무 많은 항목을 보면 뒤로 갈수록 대충 보는 경향이 있어서, 줄수 상한을 같이 두는 이유는 긴 드래프트 하나가 포함된 그룹만 유독 무거워지는 걸 막기 위해서. 숫자 자체는 근거 있는 절대치가 아니라 보수적 시작값 — 실사용 쌓이면 재조정.

## 체크 항목

**시작 전에 항상 원문(플랫폼 공식 문제 페이지)을 직접 확인함** — 이미 아는 유명한 문제여도 예외 없음. 코드의 "정확성"은 그 문제가 실제로 뭘 요구하는지(제약조건, 엣지케이스, 예제 입출력) 모르면 판단할 수 없어서 필수임(`review-post`가 `1. 아이디어` 쓸 때 원문을 재확인하는 것과 같은 이유 — 다만 목적은 다름: `review-post`는 요약문을 쓰기 위해, 여기선 코드를 검증하기 위해. 같은 페이지를 두 번 확인하는 셈이라 중복처럼 보이지만, 두 스킬이 서로 다른 시점에 독립적으로 돌기 때문에 감수함). **제약조건에 지수/첨자 표기(`$10^k$`류)가 있어 보이면 WebFetch 결과를 그대로 믿지 말 것** — WebFetch는 페이지를 마크다운으로 변환하는 과정에서 위첨자를 뭉개 `10^l`과 `10l`을 구분 못 하는 경우가 실제로 있었음. 이런 경우 `curl -s <url> | grep -o '<sup>[^<]*</sup>'`처럼 원본 HTML의 `<sup>`/`<sub>` 태그를 직접 확인할 것.

각 드래프트의 `## 3. 코드` 섹션(임베드된 코드 블록들, `### 풀이`/`### 풀이 N`별 그룹)을 대상으로. **사용자는 항상 AC(정답 확인)까지 마친 코드만 포스팅함** — 그래서 정확성은 사실상 이미 보장된 전제로 놓고, 대신 "누가 봐도 실력자가 짠 코드"로 읽히는지(더 나은 풀이·사소한 개선점·네이밍/스타일 일관성)를 훨씬 꼼꼼히 볼 것. "정적 리뷰라 실행 검증은 아니다"류 면책 코멘트를 반복하지 말 것 — 뻔한 겸손일 뿐 이 사용자에게는 불필요함. **다만 목표는 실용적 수준의 좋은 코드**지 억지 우아함이 아님 — 읽는 사람이 "이 사람 실력자네, 다른 풀이도 궁금하다"는 인상을 받는 게 목표지, 가독성을 희생한 트릭/축약/불필요한 라이브러리 동원으로 잘난 척하는 코드를 만들라는 게 아님. 아래 각 항목에서도 이 균형을 계속 지킬 것:

- **정확성** — 원문 제약조건·예제 입출력 기준으로 버그, 엣지 케이스 누락 확인. **플랫폼 채점 하네스의 내부 동작(예: 함수가 프로세스 안에서 몇 번 호출되는지, 전역/static 상태가 호출 간에 남는지)에 근거해 버그를 주장할 땐 그게 검증된 사실인지 먼저 확인할 것** — LeetCode는 이런 재호출 문제가 실제로 문서화·확인된 케이스지만, 그걸 다른 플랫폼(프로그래머스 등)에 그대로 적용해서 "이건 버그다"라고 단정하지 말 것. 확실치 않으면 "확정 버그"가 아니라 "이론적 리스크"로 톤을 낮추고, 근거가 된 AC 여부(이 사용자는 AC까지 확인된 코드만 포스팅함)를 반증으로 고려할 것. **프로그래머스는 예외 — 사용자의 다수 AC 경험상 전역/static 배열이 호출 간 초기화 안 되는 게 실질적으로 문제된 적이 없다고 확인됨(2026-08-22)이라, 프로그래머스 C++ 코드의 이 패턴은 이론적 리스크로도 올리지 말 것(실제 로직 버그가 아닌 한).** 다른 플랫폼은 기존대로 케이스별 판단. 단, **AC(정답 판정)에 영향 없는 출력 바이트 수준 차이는 이슈로 올리지 않음** — trailing/spurious newline, `cout`(자동 개행 없음) vs `println`/`print`(자동 개행 있음)처럼 각 언어의 기본 출력 함수를 그대로 쓴 데서 오는 차이는 정당한 차이지 버그가 아님(플랫폼이 trailing whitespace를 채점에서 무시하는 게 일반적이고, 억지로 통일시키려는 지적이 오히려 부자연스러운 개입)
- **최선의 접근인지** — 시간/공간복잡도가 더 나은 접근, 더 관용적인 표준 라이브러리 기법이 있는데 안 쓴 부분까지 잡을 것(다중 접근에 안 담겨있으면 "추가 고려"로 제안, 기존 코드 이슈가 아니어도 언급). 언어별로 제안의 무게가 다름 — **Java 스트림/메서드 참조**는 PS(특히 TLE 타이트한 문제)에서 오토박싱·람다 오버헤드 때문에 실전 경쟁프로그래머가 오히려 기피하는 선택이라 "선택지 중 하나" 톤으로만 언급하고 "이게 더 낫다"고 강하게 밀지 말 것(워밍업급 소품 문제면 성능 무관하니 언급 자체는 가능). **Python 컴프리헨션/제너레이터/핵심 언어 내장함수**(`math.prod`, `next(iter())` 등)는 CPython에서 실제로 더 빠르고 PEP8 관례이기도 해서 "더 나은 접근"으로 힘줘서 지적해도 근거가 탄탄함 — 단 중첩 `for`/`if`가 2개 이상 겹치거나 부수효과가 있어 한 줄로 안 읽히면 그건 명시적 루프가 맞으니 억지 한 줄 골프는 지양. **단, `statistics`/`itertools`의 무거운 조합기 같은 범용 편의 모듈은 이 우대에서 제외** — 타입 일반화·다목적 처리 때문에 직접 구현보다 오히려 느린 경우가 있고(예: `statistics.median()`은 `sorted()`+인덱싱보다 느림), 실전 경쟁프로그래머도 잘 안 씀. Java 스트림과 같은 급으로 "선택지 중 하나" 톤까지만.
- **네이밍/언어별 컨벤션** — 변수명, 그 언어 관례에 안 맞는 표현. 코드가 동작한다는 것만으론 부족 — 변수명이 모호하거나 더 나은 표준 기법이 있는데 안 쓴 부분까지 잡을 것. **다만 아래 두 패턴은 실제 컨벤션 이탈이 아니라 오탐으로 확인된 사례라 그 자체로 이슈 삼지 말 것**: ① Java `public class Solution` vs `class Solution` — 프로그래머스가 문제(레벨/유형)별로 내려주는 기본 템플릿이 다를 수 있어서, 기존 발행 포스트와 단순 대조만으로 "컨벤션 이탈"을 단정하지 말 것. ② 언어별 입력 읽는 방식 차이(C++ `cin >>` 토큰 단위 / Java `BufferedReader.readLine()` 라인 단위 / Python `sys.stdin.readline()` 재할당) — 각 언어의 표준 PS 관용구일 뿐 실제 비일관성이 아님. 단 이 패턴을 쓰면서 `\n`을 안 벗겨내 이중 개행이 나는 것 같은 실제 사용 버그는 예외 없이 계속 지적할 것
- **불필요한 요소** — 안 쓰는 import/using, 선언만 되고 실제로 안 읽히는 변수, 호출되지 않는 함수/헬퍼처럼 코드에 남아있는데 실제 로직엔 기여하지 않는 것. AC엔 영향 없어서 넘어가기 쉬운데, 리팩터링 잔재로 남는 경우가 많아 명시적으로 확인할 것
- **사용자 고유 컨벤션** — 위 "네이밍/언어별 컨벤션"이 언어 표준 기준이라면, 이건 사용자 본인이 실제로 습관화한 스타일 기준(2026-08-24 첫 도입, 표본이 적어 시작한 목록 — 계속 발견되는 대로 행 추가). "성격" 열에 따라 지적 톤을 다르게: 표준/일반 관행이면 개선 제안처럼 단정적으로, 개인 컨벤션이면 "이 사용자는 보통 이렇게 씀" 기준의 일관성 체크로, 버그 리스크면 정확성 이슈로.

- **다중 접근/언어 간 일관성** — 같은 문제 안에서 접근끼리, 언어끼리 스타일이 튀는 부분. 다만 위 정확성 항목의 출력 바이트 차이처럼 각 언어 관용구를 그대로 쓴 정당한 차이와, 실제 로직/구조 수준에서 갈리는 차이(예: 한 언어만 배열을 직접 mutate해서 부수효과가 생기는 것처럼 "동작이 실제로 갈리는" 케이스)는 구분해서 후자만 지적할 것
- **태그 후보** — `<이 스킬의 base directory>/tags.yaml`의 고정 어휘집 기준으로 후보만 언급(자유 태그 생성 금지). **태그는 "기술적으로 해당되는지"가 아니라 "그 개념이 이 문제를 푸는 데 실질적으로 중요한지"로 고름** — 덧셈을 했다고 `math`, 코드를 썼다고 `implementation`을 붙이지 않음(둘 다 거의 모든 문제에 기술적으로 걸릴 수 있어 남용 위험이 특히 큼). 코드가 실제로 쓰는 기법에 가장 구체적인 태그를 고르고, 그 태그의 `parents`를 재귀적으로 따라가 조상 태그도 함께 후보로 냄(예: `lazy propagation` 고르면 `segment tree`/`data structure`도 같이). `parents`가 2개인 태그(`tree dp`, `aho corasick`)는 두 조상 라인을 각각 따라가고, `trie`처럼 `contextual`이 있는 태그는 그 판단 기준(문자열 성격이면 `string`도 후보)까지 같이 언급. 위 관련성 기준까지 통과하는 기법 태그가 실질적으로 하나도 안 남는 경우에만 `exception: true` 태그(`constructive`/`ad hoc`/`warm up`)를 최후 후보로 고려 — `constructive`/`ad hoc`는 뚜렷한 문제 성격(창의적 구성/임기응변)이 있을 때, `warm up`은 그런 성격조차 없이 그냥 쉬운/사소한 문제일 때. 경계가 애매한 태그 쌍(`bit manipulation`/`bitmask`/`bitmask dp`, `two pointers`/`sliding window`, `implementation`/`math`/`warm up`)은 파일의 `boundary_notes` 기준으로 판단. 후보는 언급만 하고 파일엔 안 씀 — 사용자가 대화 중 "태그 달아줘"라고 명시적으로 요청했을 때만 그 자리에서 front matter에 적용하며, 이때 태그는 예외 없이 전부 큰따옴표로 감쌀 것(아포스트로피 있는 태그만 따로 구분하지 않고 통일 — 작은따옴표는 아포스트로피 있는 태그에서 파싱이 깨짐)
