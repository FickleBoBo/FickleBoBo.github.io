# review-code — 서브에이전트 처리 절차

`review-code` 서브에이전트가 읽는 절차서다(오케스트레이터가 하는 일은 [`SKILL.md`](SKILL.md)). 배정된 포스트마다 아래 두 축을 보고 `## 출력 형식`대로 보고한다.

1. **코드·풀이 품질** — 이 풀이가 문제의 정석적이거나 더 나은 방법인지, 다른 접근이 있는지, 비효율이 있는지.
2. **태그 후보** — 풀이가 해당하는 태그를 `tags.yaml` 어휘집에서 고른다.

파일은 수정하지 않는다 — 이슈와 제안만 보고한다(`## 규칙`).

## 입력

- 배정된 포스트 절대경로 목록과, 각 포스트의 **문제 원문 파일 경로**(오케스트레이터가 미리 받아 둔 것, 없으면 "원문 미확인"으로 명시되어 있다).
- 리뷰 대상은 포스트의 `## 3. 코드` 섹션(`### 풀이`/`### 풀이 N`별 그룹)이다. SQL 전용 포스트는 `## 2. 쿼리`(헤딩 텍스트·번호가 다름, `ps/SKILL.md`) — 같은 절차를 쓴다.
- 코드는 전부 AC까지 확인된 것이다. **정확성은 보장된 것으로 놓고, 표준적이거나 더 나은 방법이 있는데 안 썼는지**를 본다. 실용 수준이 목표지 억지 우아함이 아니다. "정적 리뷰라 실행은 안 했다"류 면책은 생략한다.

## 시작 전 — 원문 읽기

각 포스트의 원문 파일을 **먼저 읽는다** — 유명한 문제여도 예외 없음(제약조건·엣지케이스·예제 입출력을 모르면 정확성을 판단할 수 없다). 원문 파일이 없으면 "원문 미확인"이라 보고하고, 원문 제약에 기댄 지적(버그·엣지케이스 누락 등)은 하지 않는다. BOJ 지문의 그림(`<img>`)은 원문 파일에 로컬 사본 경로가 적혀 있으면 그 파일을 Read로 연다.

## 축 1 — 코드·풀이 품질

**스타일은 검사하지 않는다.** 변수명, 표기(천 단위 구분자·`1 + n` 같은 패딩 크기 표현 등), 동치인 관용구 중 무엇을 골랐는지(`import` vs `from ... import`, 스트림 vs 수동 배열, 안 쓰는 변수 `_` 마스킹 여부 등) 같은 취향 수준의 선택은 어느 방향으로도 지적하지 않는다. 그 선택이 실제 버그를 부르면(내장명 섀도잉) 그건 정확성 이슈다.

경계가 애매하면 "이게 실력 없어 보이나"가 아니라 **"더 나은 구체적 대안을 댈 수 있나"**로 판단한다 — 동치인 대안뿐이면 지적하지 않는다.

**설명이 그럴듯한지가 아니라 실제 코드와 맞는지** 코드를 직접 열어 대조한다. 직전 배치에서 지적됐던 축으로 점검 범위를 좁히지 말고 매번 아래 전체를 돈다.

### 정확성

- 원문 제약조건·예제 입출력 기준으로 버그, 엣지케이스 누락.
- 채점 하네스 내부 동작(함수 재호출, 전역/static 상태 잔존 등)을 근거로 버그를 단정하지 않는다 — 검증 안 된 추측이면 "이론적 리스크"로 톤을 낮추고 AC를 반증으로 고려한다.
- **프로그래머스 예외**: 전역/static 배열이 호출 간 초기화 안 되는 패턴은 프로그래머스 C++ 코드에서 이론적 리스크로도 올리지 않는다(문제된 사례가 확인되지 않음). 실제 로직 버그면 예외.
- **AC에 영향 없는 출력 바이트 차이는 이슈로 올리지 않는다** — trailing/spurious newline, `cout`(자동 개행 없음) vs `println`/`print`(자동 개행 있음)처럼 각 언어 기본 출력 함수를 그대로 쓴 차이는 정당하다.
- **내장명 섀도잉**: Python에서 `list`/`sum`/`max`/`id` 등 내장명을, C++에서 `using namespace std;` 상태로 `std::` 함수명과 겹치는 이름을 변수로 쓰면 그 스코프에서 원래 심볼이 가려진다. 이후 그 이름을 함수로 호출하면 실제 버그(C++은 컴파일 에러)라 정확성 이슈, 호출하는 곳이 없으면 이론적 리스크로만 낮춘다.

### 최선의 접근인지

- 시간/공간복잡도가 더 나은 접근, 더 관용적인 표준 라이브러리 기법이 있는데 안 썼으면 잡는다(다중 접근에 없으면 "추가 고려"로 제안).
- **Java 스트림/메서드 참조**: 취향이라 그 자체로는 지적하지 않는다. 성능이 실제 병목인 자리(큰 배열을 매번 스트림으로 도는 등)에서만 "선택지 중 하나" 톤으로 언급한다.
- **Python 컴프리헨션/제너레이터/핵심 내장함수**(`math.prod`, `next(iter())` 등): CPython에서 실제로 더 빠르고 PEP8 관례라 "더 나은 접근"으로 힘줘서 지적해도 된다. 단 중첩 `for`/`if`가 2개 이상 겹치거나 부수효과가 있어 한 줄로 안 읽히면 명시적 루프가 맞다 — 억지 한 줄 골프는 지양.
- **범용 편의 모듈**(`statistics`, `itertools`의 무거운 조합기 등)은 직접 구현보다 느릴 수 있어 이 우대에서 제외 — Java 스트림과 같은 "선택지 중 하나" 톤까지만.

### 언어별 관용 · 오탐 주의

- 그 언어에서 비관용적이라 실력자 코드로 안 읽히는 부분(더 관용적인 표준 기법이 있으면 "최선의 접근"과 같이).
- **오탐으로 확인된 패턴 — 그 자체로 이슈 삼지 않는다**:
  - Java `public class Solution` vs `class Solution` — 프로그래머스가 문제별로 다른 기본 템플릿을 내려준다. 기존 발행 포스트와의 대조만으로 "컨벤션 이탈"을 단정하지 않는다.
  - 언어별 입력 읽는 방식 차이(C++ `cin >>` 토큰 단위 / Java `BufferedReader.readLine()` 라인 단위 / Python `sys.stdin.readline()` 재할당)는 각 언어의 표준 PS 관용구다. 단 `\n`을 안 벗겨 이중 개행이 나는 실제 사용 버그는 지적한다.
  - LeetCode follow-up은 문구가 요구하는 수준까지만 본다 — 문구가 요구하지 않은 더 강한 조건(더 낮은 복잡도 등)을 안 지켰다고 지적하지 않는다.
  - BOJ 포스트의 언어 구성이 제각각인 것(Java 단독·C++ 단독·Java+C++), Codeforces 포스트에 Java/Python 풀이가 없는 것(C++ 단독으로 싣는다) — "언어 누락"으로 지적하지 않는다. PS 레포 코포 폴더에서 `Main.java`/`Main.py`가 삭제돼 있어도 의도된 것이다.

### 불필요한 요소

안 쓰는 import/using, 선언만 되고 읽히지 않는 변수, 호출되지 않는 함수/헬퍼. AC엔 영향 없어 넘어가기 쉬운데 리팩터링 잔재로 남는 경우가 많으니 명시적으로 확인한다.

### 다중 접근/언어 간 일관성

접근끼리·언어끼리 **실제 로직/구조가 갈리는** 차이(한 언어만 배열을 직접 mutate해 부수효과가 생기는 등 동작이 실제로 갈리는 케이스)만 지적한다. 각 언어 관용구를 그대로 쓴 정당한 차이(출력 바이트 등)나 표면적 스타일 차이는 넘어간다.

## 축 2 — 태그 후보

**정본은 `tags.yaml`**(어휘집 + 헤더 주석의 사용법 0~6단계 + `boundary_notes`)이다. 읽고 그대로 따른다. 자유 태그 생성 금지, 후보만 언급한다. 요지:

- 코드가 실제 쓰는 기법에 가장 구체적인 태그를 고르고, `parents`를 재귀로 따라가 조상까지 후보로 낸다(다중부모면 두 라인 다, `contextual`이면 그 판단 기준까지).
- `math`/`implementation`/`warm up` 경계는 `boundary_notes`의 `[implementation, math, warm up]` 항목을 직접 읽고 판정한다.
- 다중 접근이면 접근별로 나눠 제시한다(`풀이 1: warm up / 풀이 2: math`). front matter에 들어갈 건 합집합이다.
- SQL 전용 포스트는 `sql` 하나다.
- `greedy`처럼 코드 구조만으론 가려지지 않는 판정은 포스트의 `## 1. 아이디어` 서술이 있으면 함께 읽는다(`tags.yaml` `boundary_notes` 참고).

## 출력 형식

포스트별로 아래 표를 쓴다. 이슈 없는 구분은 행을 넣지 않고, `태그 후보` 행은 항상 낸다. 코드·풀이 이슈가 하나도 없으면 표 위에 `이상없음` 한 줄을 쓴다.

| 구분        | 위치          | 내용 |
| ----------- | ------------- | ---- |
| 버그/정확성 | 풀이 2 · Java | ...  |
| 언어 관용   | 풀이 1 · C++  | ...  |
| 접근 제안   | —             | ...  |
| 태그 후보   | —             | ...  |

- 위치는 `풀이 N · 언어`(단일 접근이면 `풀이 · 언어`), 포스트 전체에 걸리면 `—`.
- 구현 세부를 근거로 든 지적(특정 API 미사용·매직넘버 등)은 **코드의 해당 줄을 글자 그대로 인용**한다(백틱 안에, `&gt;`·`&amp;` 같은 HTML 이스케이프 없이 — 오케스트레이터가 `grep -F`로 검증한다).
- 원문을 못 받았으면 맨 위에 `원문 미확인`을 적는다.

마지막에 청크 요약:

| 포스트              | 결과     |
| ------------------- | -------- |
| Programmers #154538 | 이상없음 |
| LeetCode #42        | 이슈 2건 |

결과 열은 코드·풀이 이슈 건수 기준이다(태그 후보는 세지 않는다).

## 규칙

- **PS 레포 소스 파일과 포스트 `.md`를 수정하지 않는다.** 이 스킬은 포스트에 임베드된 코드 블록만 읽고 PS 레포 경로에 접근하지 않는다. 수정은 사용자가 PS 레포에서 하고(AC 재확인 포함), 포스트 반영은 `sync`다.
