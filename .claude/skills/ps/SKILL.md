# ps — PS 포스트 스캐폴드 생성

**스코프**: 파일명 + front matter + 코드 섹션(완전 자동)까지. description/아이디어/복잡도 셀 값은 사람이 채우거나(비어있으면 `review-post`가 대신 채움) 빈 값만 생성. 회고/참고는 스캐폴드에 아예 안 생성(아래 표 참고). 스켈레톤 설계 근거(구분선 소유권, 코드 라벨을 안 쓰는 이유, IAL 처리 등)는 `scripts/resolve_filename.py`/`scripts/clean_code.py` 주석에 있음 — 여기서 반복 안 함.

## 실행

**배치(인자 없이):**

```
python3 <이 스킬의 base directory>/scripts/resolve_filename.py
```

`PS_REPO` 전체를 스캔해서, 블로그 개설일(2026-08-17) 이후 존재하는 풀이 중 이 블로그에 아직 포스트/드래프트가 없는 것(front matter `slug` 기준) 전부를 스캐폴드로 생성함. 이미 있는 건 안 건드림(`--force` 자체를 안 받음). 폴더 하나가 실패해도 그 폴더만 에러로 보고하고 나머지는 계속 처리함. 같은 (플랫폼, 번호)가 서로 다른 day 폴더에 중복이면 스캐폴드를 만들지 않고 "충돌"로만 보고(사람이 직접 확인).

출력: `생성함: {경로}` / `에러({폴더}): {이유}` / `충돌(slug=...): ...` 목록 + 마지막에 총계 한 줄.

**특정 폴더 하나만:**

```
python3 <이 스킬의 base directory>/scripts/resolve_filename.py <PS레포 문제 폴더 절대경로> [--force]
```

예: `python3 .claude/skills/ps/scripts/resolve_filename.py /Users/mwzz6/Desktop/github/PS/2026-09/src/day_01/prms_42586`

스켈레톤 구조가 바뀌어서 재생성하고 싶을 때 씀. 성공하면 stdout엔 쓴 파일의 절대경로만 출력.

두 모드 다 이 레포의 `_drafts/{platform}/`(소문자, 예: `programmers`)에 씀 — **`_posts/`가 아님**(`publish` 스킬이 옮기기 전까진 초안, 사이트에 노출 안 됨). 이미 같은 이름 파일 있으면 기본적으로 거부(사람이 채워둔 프로즈를 보호), 단일 폴더 모드에서만 `--force`로 재생성 가능. 실패하면 이유가 담긴 예외를 그대로 보고 — 재시도나 임의 보정 하지 말 것.

로컬에서 초안 미리보기: `bundle exec jekyll serve --drafts` (`_config.yml`에 `show_drafts: true`를 넣는 방식은 쓰지 말 것 — 프로덕션 빌드에도 적용돼 초안이 실제 배포 사이트에 노출됨).

## 본문 구조

| 섹션                     | 채워지는 방식                                                                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 문제 링크(`prompt-info`) | 결정론적                                                                                                                                  |
| 1. 아이디어              | 사람이 직접(또는 비어있으면 `review-post`)                                                                                                |
| 2. 복잡도                | 행 구조는 결정론적(코드 섹션과 동일한 접근법 그룹), 셀 값은 사람/`review-post`                                                            |
| 3. 코드                  | 완전 결정론적                                                                                                                             |
| 회고 / 참고              | 스캐폴드엔 기본적으로 아예 안 생성(2026-08-27 확정) — 실제로 쓸 내용이 생겼을 때만 사람이 "## 회고"/"## 참고" 헤딩(번호 없음)을 직접 추가 |

**아이디어 섹션**: 서술(풀이 해설) 중심 — 제약조건을 표로 따로 정리하지 않음(표는 이런 규모의 문제엔 과하고 스포일러성도 있음). **대상 독자 전제(2026-08-22 확정)**: 해당 알고리즘/자료구조의 기본 개념(DP가 뭔지, 이분탐색이 뭔지 등)은 안다고 전제하고 매번 재설명하지 않음 — 이 블로그가 대량(수백~수천 개 예상) 발행을 목표로 해서, 포스트마다 기초 개념을 반복 설명하면 오히려 루즈해지고 중복만 쌓임(개념 자체를 다루고 싶으면 언젠가 별도 허브/개념 정리 포스트 스코프로, 개별 풀이 포스트는 아님). 대신 **이 문제에 특화된 추론 과정은 생략 없이 친절하게** 씀 — 왜 이 점화식/접근이 성립하는지, 초기값·경계 처리를 왜 그렇게 했는지까지 풀어써서 "정확하지만 압축된 서술"에 그치지 않도록 함. 제약 수치가 풀이 근거로 실질적으로 중요하면 문장 안에 자연스럽게 녹여쓰고, 안 중요하면(사소한 워밍업 문제 등) 생략해도 됨. 서브헤딩 없음, 지문 원문은 복붙하지 않음(저작권 — 자기 말 요약). **어투는 다체(평서체 — "~이다", "~된다")로 통일** — 합니다체(존댓말)를 섞으면 포스트마다 어투가 갈려서 눈에 띔(2026-08-22 review-post 배치에서 실제로 서브에이전트별로 갈렸던 사례 있음). `review-post`가 빈 아이디어를 대신 채울 때도 이 어투를 따를 것. **시제는 섹션이 아니라 문맥 기준으로 구분** — 왜 필연적으로 성립하는지 논증하는 문장(알고리즘 근거)은 현재형(`~한다`/`~된다`), 여러 방법 중 이걸 택했다는 서술(구현/전략 선택)은 과거형(`~했다`)으로 씀. `1. 아이디어`든 `3. 코드` 블록 아래 설명이든 이 기준은 동일하게 적용(발행된 `#120808`/`#181945`/`#181946`/`#120813` 등에서 이미 이 기준대로 쓰이고 있던 걸 뒤늦게 확인해 문서화). `해주다`(`~해줬다`) 계열은 방향과 무관하게 항상 캐주얼해서 배제. **백틱과 `$...$`(수식)는 역할이 다름** — 백틱은 코드에 실제로 등장하는 리터럴/변수/함수명(`array`, `solution` 등)에만, 코드에 그 형태 그대로 없는 수식·파생 표현(예: `2ab`, `a ⊕ b`처럼 서술 편의상 만든 표기)은 `$2ab$`, `$a \oplus b$`처럼 `$...$`로 씀(발행된 #120808 분수의 덧셈에서 이미 이 구분을 따르고 있었음 — 2026-08-22에 문서화되지 않은 채 지켜지고 있던 걸 뒤늦게 확인). 같은 원칙으로 좌표 표현(`(i, j)`, `(1, 1)` 등)도 코드에는 `dp[i][j]`처럼 배열 인덱싱으로만 등장하지 튜플 형태 그대로 없으므로 백틱이 아니라 `$(i, j)$`, `$(1, 1)$`처럼 수식으로 씀(2026-08-22 등굣길/정수 삼각형 드래프트에서 정정된 사례). **변수가 코드에 실제로 등장해도 그 변수를 쓴 공식/유도 전체는 수식으로 통일**(2026-08-27 확정) — 예를 들어 `k`가 실제 코드 변수여도 "총 `k` $= (n + 1) / 2$개"처럼 한 표현 안에서 백틱과 수식을 쪼개 쓰지 않고 "총 $k = (n + 1) / 2$개"처럼 그 식 전체를 수식으로 씀(`#181935` 정정 사례) — 공식/유도 맥락에서는 백틱-수식 혼용이 어색해 보이므로. 복잡도가 $O(1)$이 아니라서 변수가 필요한 경우, 그 변수가 뭘 가리키는지는 여기서 설명하지 않고 `2. 복잡도` 섹션에 적음(아래 "복잡도 섹션" 참고). **알고리즘/풀이 레벨의 아이디어만 씀 — 언어별 구현 차이(이 언어는 이 내장 함수가 있어서, 저 언어는 반복문으로 대신 등)는 여기서 비교하지 않고 `3. 코드` 섹션(코드 블록 아래 설명)으로 보냄**(아래 "코드 섹션 다중 접근" 참고). 여러 언어가 같은 알고리즘을 그대로 옮긴 정도면 언어별 차이 자체를 언급할 필요도 없음.

**복잡도 섹션**: 셀 값이 $O(1)$이 아니라 변수가 들어가면(`$O(N)$`, `$O(N \log N)$` 등) 표 아래에 그 변수가 뭘 가리키는지 짧게 프로즈로 덧붙임(예: "($N$ = 문자열 길이)"). 변수명은 대문자 관용($N$, $M$ 등) — PS 문제 제약 표기 관례를 따름. 이 설명은 원래 아이디어 섹션에 있었는데, 아이디어 섹션에서 표를 빼면서 여기로 옮김. **곱셈 결합 표기(2026-08-24 확정)**: 두 요소가 곱으로 묶이면 `\times`로 통일 — `\cdot`나 그냥 붙여쓰기(`$O(NM)$`)는 안 씀(예전엔 파일마다 갈렸었는데 발행분 포함 전수 정정함). 단 `\log`가 끼면 예외: **맨몸 변수 하나 × log는 그냥 붙여씀**(`$O(N \log N)$`, `$O(N \log R)$` — CS 관용 표기라 `\times` 안 넣음), **맨몸 변수 두 개가 곱해질 때만 그 사이에 `\times`**(`$O(N \times M)$`), 변수곱과 log가 섞이면 변수곱에만 `\times`를 넣고 log 앞뒤는 붙여씀(`$O(N \times M \log K)$`이지 `$O(N \times M \times \log K)$`가 아님). **이항 연산자 공백(2026-08-27 확정, 복잡도 섹션뿐 아니라 수식 전체에 적용)**: `+`/`-`/`/`(나눗셈)는 지수(`n^2`)나 아래첨자처럼 항상 붙여쓰는 표기가 아닌 한 항상 양쪽에 공백을 둠 — `$N/2$`가 아니라 `$N / 2$`, `$(i-1, j)$`가 아니라 `$(i - 1, j)$`. `\times`는 위 곱셈 규칙을 그대로 따름. **천단위 콤마(2026-08-27 확정, 수식 전체에 적용)**: 제약조건 등에 나오는 1,000 이상 숫자는 `{,}`로 묶어 콤마를 넣음(`$10000$`이 아니라 `$10{,}000$`) — 그냥 `,`만 쓰면 KaTeX가 콤마 뒤에 여백을 넣어 어색해짐. 단 연도처럼 애초에 콤마를 안 쓰는 표기는 예외.

**코드 섹션 다중 접근**: 같은 언어 파일이 폴더에 여러 개면(`Main.java`+`Main2.java`) 파일명 끝자리 숫자로 접근법을 나눠 `### 풀이`/`### 풀이 N`으로 그룹핑(`group_by_approach`). 헤딩엔 그 접근법에 존재하는 언어를 `[Java][C++]`로 표시. 접근법 이름(`풀이 2: DP` 등)은 스크립트가 안 채움 — 헤딩을 직접 수정(2026-08-27 최초 적용: `#120831`/`#120836`). **단, `2. 복잡도` 표의 "접근" 열은 `풀이:`/`풀이 N:` 접두어 없이 이름만 씀**(`직접 순회`/`등차수열 합 공식`처럼) — 접두어+이름 조합은 코드 섹션 헤딩에서만 쓰고 표는 짧게 유지. **코드 블록을 자기 접근법 섹션 밖으로 옮기면 `sync`가 못 찾음.** `### 풀이 N` 헤딩 바로 아래(첫 코드 블록 위)에 쓰는 설명은 그 접근법의 모든 언어에 공통 적용되는 내용, 각 코드 블록 바로 아래에 쓰는 설명은 그 언어 코드에만 해당하는 내용 — 위치로 스코프를 구분함. 언어별로 특징적으로 설명할 게 있으면 이 위치에 직접 프로즈를 넣어도 됨(`sync`는 fence 블록을 헤딩 구간 안에서 정규식으로 찾아 교체할 뿐 주변 텍스트는 안 건드리므로 안전함).

| `title`         | 결정론적 — `"[{Platform}] #{번호} - {제목} [{언어1}][{언어2}]..."`                                                                                                                                                  |
| `date`          | 결정론적 — 폴더 `day_{DD}`에서 뽑은 날짜만                                                                                                                                                                          |
| `categories`    | 결정론적 — `[PS, {platform}]`                                                                                                                                                                                       |
| `tags`          | 빈 배열 — 사람이 직접 작성                                                                                                                                                                                          |
| `description`   | 빈 문자열 — 사람이 직접 작성(또는 비어있으면 `review-post`). **사실상 필수** — Chirpy가 부제목/홈 목록 미리보기/SEO `<meta description>` 3곳에 그대로 씀, 비우면 각각 더 지저분한 값으로 폴백(부제목은 통째로 생략) |
| `slug`          | 결정론적 — `{platform}-{번호}` 소문자                                                                                                                                                                               |
| `media_subpath` | 결정론적 — `/assets/img/posts/{slug}/`                                                                                                                                                                              |
| `math`          | 결정론적 — 항상 `true` (복잡도 표가 `$O(1)$` 등 항상 `$...$` 수식을 쓰므로 수식 없는 포스트가 구조적으로 없음)                                                                                                      |
| `mermaid`       | 기본 `false` — 본문에 다이어그램 있으면 직접 `true`로                                                                                                                                                               |

## 규칙

- 블로그 개설일(2026-08-17) 이전 풀이는 완전히 무시(스크립트가 자동 거부)
- 게시 선별 없음 — 스코프 안이면 전부 포스팅 대상
- 파일명 금지 문자(`/ : ? * " < > \ |`)는 육안 구별 어려운 유니코드로 자동 치환됨. **파일명에만 적용** — front matter의 `title`/`description`은 원문 그대로
- **결과 보고 시 판단을 얹지 않음** — 필수 인자(PS 레포 문제 폴더 절대경로)가 빠져 실행 못 하면 AskUserQuestion 같은 선택지 UI로 후보를 조사해 골라주지 말고, 그냥 경로가 필요하다고 평문으로 말하고 기다릴 것. 참고 정보(예: 아직 포스트 없는 폴더 목록)를 텍스트로 곁들이는 것까진 괜찮지만 "이 중에 골라라" 형태는 안 됨. 스크립트 출력을 보고할 때도 "괜찮아 보인다"/"무시해도 될 듯" 같은 평가를 섞지 말고 스크립트가 뱉은 사실만 그대로 전달 — 결정론적 스킬이라 판단은 전적으로 사람 몫
